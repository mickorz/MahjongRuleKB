# xc-ui-flow 聊天框复刻方案（Rule Studio 工作台）

- 文档版本：v1.0
- 日期：2026-11-28
- 参考项目：`thirdparties/xc-ui-flow`（= game-workbench，Apache-2.0，REF-010，junction 本地目录）
- 目标：把它的聊天框**完整复刻**到 Rule Studio 的单文件 vanilla 工作台（`server/viewer.ts`），
  含**SSE 步骤流**
- 结论先说：可行，但"完整"= 约 3,900 行 TSX + 1,348 行契约 + 168 条 CSS 的**结构复刻**，
  不是代码搬运（React 19 + Vite vs 我们零构建 vanilla）
- 范围：见 §5「裁剪清单」—— 砍掉 14 项（约 1,600 行 + 3 个依赖），保留 7 项核心交互

## 2. 我们与它的差距

| 维度 | xc-ui-flow | 我们（当前） |
|---|---|---|
| 传输 | SSE 事件流 + 游标重连 | 一次性 JSON（`/api/assistant`） |
| 数据 | `ThreadItem[]`，工具调用是一等公民（status/arguments/output/truncated/fileDiff） | `tool_calls: [{name, ok, code?, ms}]`，无参数/输出 |
| 渲染 | 工具组折叠 + 人话摘要 + 展开明细 + 失败态 + thinking | 一行「查了 N 次：工具名」 |
| 错误 | 错误码 → 人话 + 诊断行 | 纯文本 `message` |
| 输入 | 附件 / @引用 / 命令菜单 / 队列 | 单行 textarea + 改稿开关 |
| 技术栈 | React 19 + Vite + bun | 单文件 vanilla，零构建 |

## 3. 复刻原则

1. **只复刻结构、交互与文案，不搬 React 代码**。搬代码要引构建链，等于重演 PiBot 的教训。
2. **沿用我们已有视觉语言**：`.asst-*` / `.badge` / `.c-btn` / 纸色令牌，不引入它的 CSS 变量体系。
3. **事件先落地再谈渲染**：没有 SSE 就没有"实时步骤"。
4. **不做与 KB 无关的**：`turn-changes`（文件 diff/撤销）、`workspace.*` 事件、`mcpToolCall`、
   `playtest`、`publish.*` 一律不做；`attachments`/`images` 只做"显示已有"，不做上传通道。
5. License：Apache-2.0，允许复制；本方案只借鉴结构，如后续照搬函数体，须在 `thirdparties/REFERENCES.md` 记录并在仓库加 NOTICE 段。

## 4. 目标结构（我们这边）

### 4.1 契约层：`studio/assistant/events.ts`（新增）

```ts
export const assistantEventTypes = [
  "run.started",        // { sessionId, variant, messages }
  "step.started",       // { index, tool, args }
  "step.finished",      // { index, tool, ok, code?, ms, summary, citations[] }
  "tool.rejected",      // { index, tool, code, message }  ← 预算/白名单/超时
  "claim.checked",      // { claims: CheckedClaim[] }      ← grounding 结果
  "answer.delta",       // { text }                        ← 正文流（模型支持流式时）
  "answer.completed",   // { text, claims, grounded, mode, rounds, budgetExceeded, injectedIds }
  "run.failed",         // { code, message }
] as const;
```

约定：每个事件 `{ id: number; type: ...; data: ... }`，`id` 单调递增供前端游标去重（对齐参考项目的 `cursor`）。

### 4.2 Runtime 事件化：`studio/assistant/runtime.ts`（改造）

加 `onEvent?: (event: AssistantEvent) => void`，在现有循环里打点：

| 打点位置 | 事件 |
|---|---|
| 进入 `runAssistant` | `run.started` |
| 工具执行前 | `step.started` |
| 工具执行后（含失败/超时/预算拒绝） | `step.finished` / `tool.rejected` |
| `groundAnswer()` 之后 | `claim.checked` → `answer.completed` |
| 异常 | `run.failed` |

**不改变现有返回值**（`RuntimeResult` 保留），事件只是旁路，保证旧调用方不破。

### 4.3 SSE 端点：`POST /api/assistant/stream`

```
POST /api/assistant/stream  (同源 + X-Rule-Studio)
→ text/event-stream
   event: run.started
   data: {"id":1,...}

   event: step.finished
   data: {"id":3,...}
```

- 复用 `readBody` + CSRF 校验；写审计与 `/api/assistant` 一致
- 响应头：`content-type: text/event-stream`、`cache-control: no-store`、`connection: keep-alive`
- 结束时补 `answer.completed` 再 `res.end()`
- 保留非流式 `/api/assistant`（回归用、脚本用）

### 4.5 人话摘要（抄它的思路，词表换我们的）

```ts
const STEP_CATEGORY = {
  search_rules: "检索", get_rule: "读取规则", get_config: "查询配置",
  list_unresolved: "查未决项", read_evidence: "读证据", compare_rules: "对比玩法",
};
// "检索了 2 次、读取规则 3 次、查询配置 1 次（1 次失败）"
```

规则（对齐 `toolGroupSummary`）：

1. 连续 step 合并成一组，非工具的正文另起
2. 只统计**成功**的按类别聚合；失败单独计数并追加「N 次失败」
3. 全部失败时不出类别，直接「N 次调用失败」
4. 单条类别用「一次」措辞（"检索了 1 次"），不用复数

## 5. 裁剪清单（明确不做的东西）

复刻范围不是"它的聊天框全部"，下面按「直接砍掉 / 保留但降级 / 保留」三档逐项登记。
砍掉的合计约 **1,600 行 TSX + 3 个第三方库**，这是工期从 3~5 天收敛到 1.5~2 天的原因。

### 5.1 直接砍掉（不做，且不用替代）

| 能力 | 参考实现 | 体量 | 为什么不做 |
|---|---|---|---|
| 本轮文件改动 + 撤销 | `turn-changes.tsx`、`ChangeCounts`、`FileDiff` | 657 + 89 + 18 行 | 它是「改代码工程」的产物视图；我们的产物是规则文档与 Proposal，没有 workspace 文件 diff 概念；Proposal 的对照用现有 `.asst-action` |
| `workspace.*` 事件 | `workspace.restored/undone/reapplied` | 3 类事件 | 同上，我们没有 workspace 回滚 |

### 5.5 "不砍、直接 import 它的代码"可行性实测

用脚本从入口文件做**传递闭包**（跟随相对 import，统计本地模块数、行数、外部依赖）：

| 复用范围 | 本地模块 | 行数 | 外部依赖 |
|---|---|---|---|
仅 `agent-timeline.tsx`（时间线） | 69 | 18,612 | 9（react、react-dom、react-markdown、remark-gfm、i18next、@solar-icons…） |
`agent-timeline` + `composer` | 104 | 22,587 | 10 |
`agent-timeline` + `composer` + `project-shell` + `message-queue` | **181** | **38,937** | **49**（含 `@supabase/supabase-js`、`@xyflow/react`、`react-arborist`、`typebox`、`i18next` 等） |

原因：聊天组件 import 了 `shared/contracts.ts`（1,348 行）、`agent-error-presentation`、`api.ts`（1,594 行）、
`locales/zh-CN.ts` + `locales/en.ts`（合计 5,822 行）等，闭包迅速膨胀。

**结论：不能"直接 import 整个聊天框"而不砍。** 这是物理事实，不是偏好：
- 只要引时间线 → 必须先有 React + Vite + react-markdown + remark-gfm + i18next + 图标库
- 还要把我们的 SSE 事件映射成它的 `ThreadTurn / ThreadItem` 契约（等于重写一遍 daemon 事件层）
- 且要接受每次上游更新后的 re-sync

### 5.6 可以真正复用的部分（纯逻辑，无 React 依赖）

三个模块的**算法**是纯函数，可以移植（换成我们的类型与文案），这才是"复用代码"与"零构建"能同时成立的交集：

| 模块 | 行数 | 复用什么 | 移植代价 |
|---|---|---|---|
`work-items.ts` | 119 | 连续调用合并分组 + 按类别生成人话摘要 | 类型换成我们的 `RuntimeToolCallLog[]`；文案换成六个工具的中文词表 |
`turn-display.ts` | 153 | turn → 展示投影（完成态缓存、失败态聚合） | 我们的消息结构更简单，可裁到 ~60 行 |
`agent-error-presentation.ts` | 41 | 错误码 → 首行标题 + 正文的结构，以及"诊断行"的组织方式 | 码表缩到我们 8 个码 |

合计约 **300 行算法**，移植后估计 **150~200 行**。
Apache-2.0 允许复制，需在仓库根 `NOTICES.md` 保留版权声明（见 §5.7）。

**其余 UI 仍然自写**：时间线的 DOM 结构、折叠交互、步骤卡样式、Composer、队列、停止 —— 这些在 React 里是组件，在 vanilla 里是函数 + `<details>`，
照搬 JSX 没有意义（还要 JSX 转译）。

### 5.8 方案 D：把它封装成 package / 预构建 bundle 再引用（可行性评估）

这是第四条路：**不改我们的构建体系，也不 vendor 源码**，而是在参考项目侧（或其 fork）把聊天框
打成一份预构建产物（ESM bundle + CSS），我们这边只 `<script type="module">` 挂载。

#### 5.8.1 为什么它比"直接 import 源码"现实

| 维度 | 直接 import 源码 | 引预构建 bundle |
|---|---|---|
我们的构建链 | 需要 Vite + React 转译 TSX | **不需要**（产物已是 JS/CSS） |
React 运行时 | 暴露给我们，版本要对齐 | 打进 bundle，内部消化 |
依赖数量 | 49 个（闭包） | 0 个进我们的 package.json |
样式 | 与我们纸色令牌冲突，需要全量改 | 关进 Shadow DOM 隔离 |

技术前提已核对：

- 聊天组件里**没有 `createPortal`**（`grep` 结果为空）→ DOM 不逃出容器，**Shadow DOM 可隔离**
- 它是 React 19.2.8 + Vite 7.3.6，`build:renderer` 已有 Vite 管线 → 加一个 `vite build --lib` 配置即可产出 ESM
- 现成 `dist/` 里已有构建产物，说明打包链路是通的

#### 5.8.2 必须做的 4 处 patch（都在参考项目侧）

| # | 位置 | 问题 | 补丁 |
|---|---|---|---|

#### 5.8.3 我们这侧要做的事

```html
<!-- server/viewer.ts 内 -->
<div id="copilot-chat"></div>
<script type="module">
  import { mountChat } from "/vendor/copilot-chat.js";
  window.__copilot = mountChat(document.getElementById("copilot-chat"), {
    language: "zh-CN",
    turns: [],                        // 初始空
    onSubmit: (text) => sendPrompt(text),   // 我们发起请求
  });
  // SSE 到达时推事件 → 适配层转成 ThreadItem/Turn
  window.__copilot.applyEvents(events);
</script>
```

需要新写的只有**契约适配层**（约 100~150 行）：我们的 8 类 SSE 事件 → `ThreadTurn/ThreadItem`：

| 我们的事件 | → ThreadItem |
|---|---|
| `run.started` | `turn` 创建（status inProgress） |
| `step.started` / `step.finished` / `tool.rejected` | `dynamicToolCall`（preparing → completed/failed） |
| `claim.checked` | 附加到 assistantMessage 上的自定义字段（或独立 item） |
| `answer.completed` | `agentMessage`（status completed） |
| `run.failed` | `error` item |

#### 5.8.4 代价与风险

| 项 | 评估 |
|---|---|
| 前置：必须 **fork** 参考项目 | 我们现行规则是"thirdparties 只读、不得修改"；fork 后须更新 `REFERENCES.md` + 根 `NOTICES.md`（Apache-2.0） |
| 产物体积 | React19+ReactDOM ≈ 45KB(gz) + react-markdown/remark ≈ 35KB + i18n ≈ 12KB + 聊天代码 ≈ 40KB + CSS ≈ 8KB → **约 140KB gzip**（不含 shiki 语法高亮，建议裁掉） |
| CSS 隔离 | 需 Shadow DOM；其组件若依赖 `:root` 变量，要在 shadow 内重建同名变量（可从我们令牌映射） |
| 契约耦合 | 上游 `ThreadItem` 字段变更即破；适配层要跟着改 |
| 上游同步 | 每次同步 = 重放 4 处 patch（量小，但必须人工） |
| 调试 | bundle 内是压缩后的 React，出问题难定位；`sourcemap` 会增加体积 |
| 工期 | **spike 1 天可判定**；通过后正式落地 **2~3 天**（含 fork、适配层、Shadow DOM、体积优化） |

#### 5.8.5 Spike 验收标准（1 天，四选三即通过）

1. `vite build --lib` 产出单个 ESM + CSS，体积 ≤ 200KB gzip
2. 在**静态 HTML**（无构建）里 `<script type="module">` 成功挂载，渲染 20 条假 turn
3. 注入到 Shadow DOM 后，工作台的纸色主题不受影响，聊天组件自身样式正确
4. 推一条 `step.finished` 事件，界面在 100ms 内出现步骤卡（验证事件驱动可用）

#### 5.8.6 Spike 实测结果（2026-11-28，已跑通）

沙盒：`dev-examples/xc-chat-spike/`（参考项目 worktree `spike/chat-lib` 分支 + `spike/` 下的入口与 lib 配置；
`dist-spike/` 为产物，整目录 gitignore，不入库）。

| 验收项 | 目标 | 实测 | 结论 |
|---|---|---|---|
| 1. lib 构建产物体积 | ≤ 200KB gzip | JS **238KB gz**（935KB raw）+ CSS **6.6KB gz**（30.7KB raw） | ⚠️ 略超（+45KB），可继续裁 |
| 2. 静态 HTML 挂载 | 渲染 20 条假 turn | 渲染 10 个 turn、11 个折叠组、无控制台报错 | ✅ |
| 3. Shadow DOM 隔离 | 宿主纸色主题不受影响 | 宿主 body `rgb(254,252,248)` vs shadow 内 `rgb(23,23,23)` | ✅ |
| 4. 事件驱动更新 | 推 `step.finished` 后界面变化 | 推 2 条 step + 1 个新 turn → `details` 11→13、`tool-*` 节点 5→9 | ✅ |

通过的 4 项里有 3 项是硬指标（挂载、隔离、事件驱动），体积一项差 45KB 未达标。

**为达标所做的裁剪（都在参考项目侧的 spike 配置里，不改其主逻辑）**：

1. 全量 `styles.css`（383KB 源，产物 1.8MB / 698KB gz）→ 按选择器前缀抽取聊天子集 **30.7KB / 6.6KB gz**（283 条规则）
2. 英文文案 `locales/en.ts`（2,950 行）→ 空对象 stub
3. 3D 预览 `model-preview` → 空组件（原会带进 `model-viewer` 1.2MB / 312KB gz 的独立 chunk）
4. 关闭 `inlineDynamicImports`，让 `shiki`（语法高亮）留在懒加载 chunk，不进主入口

**仍需的 4 处源码 patch**（与 §5.8.2 一致，实测确认全部必要）：

| patch | 文件 | 实际改动 |
|---|---|---|
| 1+2 | `agent-timeline.tsx` | 删 `getWorkspaceAsset` 导入，改为 `AssetLoaderContext` 注入；`useNearViewport` 20 行内联 |
| 3 | `i18n.ts`（不改文件，用构建插件） | `resolveId` 把 `locales/en` 映射到 stub |
| 4 | `styles.css`（不改文件，用抽取脚本） | 只把聊天相关 283 条规则注入 shadow root |

**剩余体积优化路径**（若要把 245KB 压到 200KB 以下）：
- `react-markdown + remark-gfm`（约 40~50KB gz）可以用我们已有的 `renderAsstText()` 替换 → 直接省掉
- `locales/zh-CN.ts`（113KB 源）可裁到只保留聊天用到的 key
- 图标改为内联 SVG 子集

**结论**：方案 D **可行**。相对自写方案（§5 方案，1.5~2 天、700~900 行 vanilla），它的真实成本是：
- 一次性：fork + 4 处 patch + lib 构建 + 契约适配层（约 2~3 天）
- 持续：上游每次更新重放 4 处 patch；`ThreadItem` 字段变更要改适配层

**踩到的两个坑**（已在沙盒里解决，施工时要注意）：
1. `git worktree add ../../dev-examples/...` 的相对路径是相对**参考项目仓库根**解析的，不是相对 cwd —— 会跑到 `E:/dev-examples` 去；必须给绝对路径
2. Windows 上 vite 的 `resolve.alias` 用 `fileURLToPath` 结果（含 `E:\`）会被当成相对路径拼成 `./E:\...`；要换成 `resolveId` 插件并 `replaceAll("\\", "/")`

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| SSE 在 `node:http` 里写脏（半包、断连） | 只写 `data:`+`event:`+空行；结束显式 `res.end()`；前端按 `\n\n` 切块并用 `id` 去重 |
| 长连接与既有的 `NO_STORE` 冲突 | SSE 单独设 `no-store` + `x-accel-buffering: no` |
| 前端单文件膨胀 | 组件化到函数级（`renderSteps()` / `renderStep()`），**不引入构建** |
| 事件与最终结果不一致 | `answer.completed` 携带的 claims/tool_calls 必须与事件序列自洽，F1 单测锁死 |
| 抄代码触发许可义务 | 只借结构与文案；如照搬函数体，补 NOTICE 并登记 REFERENCES.md |
| 流式中途出错 | 发 `run.failed` 后 `res.end()`；前端把已收到的步骤保留、正文标红 |

## 8. 与"能不能解决工具选错"的关系

复刻聊天框**不能**减少工具选错 —— 那是工具契约与提示词的事（已用 `hint + details.suggest` 修）。
它解决的是**可观测性**：一次浪费从"看不出来"变成"折叠摘要里明写 1 次失败、展开能看到参数"。

---

## 9. 类比理解

参考项目的聊天框像**手术室的观察窗 + 器械记录**：

- `ThreadItem` = 手术记录条目（谁、什么时候、用了哪把器械、结果如何）
- `projectWorkItems` = 把连续动作合并成「这一段在探查」
- `toolGroupSummary` = 给家属看的一句话摘要（"探查了 3 处、缝合 2 针、1 次出血"）
- `agent-timeline` = 观察窗：平时只显示摘要，想看细节再展开
- SSE = 实时直播；我们现在的实现 = 手术做完才给一张总报告

复刻的实质是：**从"事后总报告"改成"实时直播 + 可折叠的器械记录"**。
