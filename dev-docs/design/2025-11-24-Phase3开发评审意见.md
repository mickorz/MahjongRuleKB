## P0：点炮承包计算把“整体改写”实现成“原赔付再叠加”

### 规则原文

杭州原始规则及结构化卡 `HJ-P-CHENGBAO-RUZHANG` 都规定：点炮胡只由放铳者付款；当放铳者是赢家对应的承包或倒承包对方时，以原点炮分 `P` 为基数，承包按 `1 × P`、倒承包按 `2 × P` **整体改写付款额，不再另加原 P**。

### 当前实现

`calculators/contract.ts` 先执行：

```ts
scores[payer] -= r;
scores[input.winner] += r;
```

随后又对承包关系叠加：

```ts
scores[c.provider] -= r;      // 承包
scores[c.holder] -= 2 * r;    // 倒承包
```

因此：

| 情形 | 正确付款额 | 当前实现 | 当前 Gold Set 期望 |
| --- | ---: | ---: | ---: |
| 点炮 + 承包 | `P` | `2P` | `2P` |
| 点炮 + 倒承包 | `2P` | `3P` | `3P` |

例如 `TC-P-CONTRACT-006` 当前断言放铳者 `-16`（P=8），正确值应为 `-8`；`TC-P-CONTRACT-007` 当前断言 `-24`，正确值应为 `-16`。

**修复要求**：点炮分支先识别放铳者与赢家的关系，再只写入最终改写付款额；抢杠胡保留“原赔付 R + 各项承包叠加”的现有语义，不能和点炮共用这条逻辑。

## P1：39 条 P1/P2 Gold Set 是占位式数据，却标记为 verified

60 条数量达标，但 P1/P2 中大量条目由脚本生成，存在以下问题：

- `fan-stack.yaml` 多数输入只有 `scenario` 文本，输出只写 `selected: highest`；没有可验证的具体番型、倍率或展示结果。
- `gang-piao.yaml` 输出只写 `verified: true`，没有断言实际倍数。
- `lou-peng-hu.yaml`、`chi-jinshou.yaml`、`youcai.yaml`、`piao-restriction.yaml`、`wall-end.yaml` 有部分真实布尔断言，但来源统一为泛化的“人工核对原始规则文档”，而非具体规则条目或原始章节。
- 上述用例多数标记 `verification.status: verified`，但没有逐条可审计的人工验证证据。

这重复了此前已经识别的风险：“测试通过不等于测试有效”。

**修复要求**：

1. 将缺少具体输入/期望值的用例降为 `verification.status: draft`，或补齐可判定期望。
2. 每条 verified 用例在 `source` 中写到具体规则 ID 和章节，例如 `HJ-K-FANXING-HUCHI / 2.3.4.2`。
3. `fan-stack.yaml`、`gang-piao.yaml` 应至少断言最终倍率（例如 8、16、32、128）。
4. 判定类尚未实现自动执行器时可以保留 Gold Set，但必须明确是人工验收，不能把 `automation.status: automated` 指向一个没有逐条消费该 YAML 用例的通用测试。

## P1：基础内容指纹不能独自强制“规则修改必须升版本”

新增 `content_hash` 可以检测“内容变了但 hash 仍是旧值”的情况，这是有价值的。

但如果维护者同时更新 `content_hash`、忘记提升 `manifest.version`，当前编译仍通过。因此它不能单独满足执行计划中“基础规则任何变更必须升版本”的强制承诺。

**建议**：目前不再引入复杂 Git 基线机制；把约束降为“内容 hash 防止遗漏更新”，并在发布/PR 流程中要求版本评审。若要自动强制，需要保存上一个已发布 `version → content_hash` 基线，比较版本与 hash 的组合——这应作为后续发布流程，不阻塞当前 Phase 3 修复。

## P2：计算器的 TypeScript 类型检查尚未纳入通过门槛

本次独立运行 `npx tsc --noEmit` 发现多处错误（主要是 `unknown`、ConfigItem 联合类型，以及测试中的不安全强转）；而 `npm test` 使用 Node type stripping，运行时不会暴露这些类型错误。

**修复要求**：

- 将 `npm run typecheck`（`tsc --noEmit`）加入 `package.json`。
- 修复现有类型错误，至少保证 `npm run typecheck` 通过。
- 后续验收须同时报告 test、validator、compile、typecheck 四项结果。
