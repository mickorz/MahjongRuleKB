我建议你把它建设成一个独立的 **「麻将规则知识库（Mahjong Knowledge Base）」**，而不是简单地把杭州麻将、萧山麻将的 Markdown 文档放进一个 LLM Wiki。

你的想法实际上涉及一个很有价值的技术方向：

**以杭州麻将为基础规则，通过差异化规则描述，自动派生出萧山麻将、桐庐麻将、绍兴麻将等不同地方玩法。**

这和普通的知识库有一个本质区别：

- 普通知识库：存储和检索规则文档。
- 结构化规则知识库：存储规则、判定条件、状态、计算公式、时序和配置。
- 规则派生系统：根据不同地方麻将的差异，生成一套完整、独立、可验证的新麻将规则。

我更推荐第三种。

而且，这套系统以后不仅可以给 AI Agent 查询，还可以直接服务于你的 PrdGameSkill，生成游戏 PRD、规则判定代码、结算逻辑和测试用例。

- 萧山麻将：《好友房规则-结构化》

其实，你已经无意中做出了第一版知识库的雏形。

这种设计非常有价值。

### 1. 现有结构已经具备可复用的领域分类

萧山麻将文档已经把规则拆成了九类：

| 一级分类 | 二级分类     | 主要内容         |
| ---- | -------- | ------------ |
| 规则   | 配置       | 底分、局数、财神、封顶  |
| 规则   | 判定       | 庄家、吃碰杠胡、特殊判定 |
| 规则   | 时序       | 小局流程、响应顺序    |
| 状态   | 计数       | 牢数、吃牌次数      |
| 状态   | 记录       | 漏碰、漏胡、飘财     |
| 算分   | 公式       | 庄闲倍率、跟庄、胡牌分  |
| 算分   | 查表       | 番型、七对、连杠     |
| 算分   | 入账分配     | 赔付、承包、拖底     |
| 界面   | 静态、交互、动效 | 展示、按钮、动画     |

这九类我建议保留。

它们比简单按照麻将玩法（吃、碰、杠、胡）划分更适合后续工程化，因为它们不仅包含玩法，还包含运行时状态、计算逻辑和客户端表现。

### 2. 目前还存在一个关键问题

现在的萧山文档使用：

- 沿用
- 修改
- 新增

来描述相对于杭州麻将的差异。

例如：

**杭州麻将基础规则**

(基线)

- 笃三老庄，固定三牢。
- 首局随机坐庄。
- 流局原庄连庄。
- 补杠可以抢杠胡。

---

**萧山麻将差异**

(新增 / 修改)

- 新庄从二牢起步。
- 连庄逐局增加牢数。
- 掷骰满足条件额外加一牢。
- 补杠不允许抢杠胡。

这种方式适合人阅读，但还不是一个完整的机器可执行知识结构。

主要有三个问题：

1. 差异引用依赖杭州文档，单独拿出萧山文档不一定能还原全部规则。
2. 规则之间存在引用关系，例如庄家状态影响胡牌资格，胡牌资格又影响番型和结算。
3. 新增规则可能影响多个模块，不能只修改一处文字。

所以，我建议在现有设计上增加一个核心概念：

**规则继承与派生（Rule Inheritance & Derivation）。**

---

## 二、推荐的整体架构

我建议采用四层架构，而不是直接建设一个大型 RAG 系统。

**第四层：麻将规则派生引擎**

根据基础规则 + 地方差异，生成完整规则集

**杭州麻将**

基础规则集

**萧山麻将**

差异规则集

**第二层：结构化规则知识层**

配置 · 判定 · 时序 · 状态 · 公式 · 查表 · 入账 · 界面

**第一层：原始资料层**

原始 PRD · 策划文档 · 规则说明 · 录屏 · 规则裁决记录

---

**第五层：应用与交付**

Agent 查询 · PRD 生成 · 规则代码生成 · 测试用例生成

这里有一个设计原则：

**原始资料是证据，结构化规则是事实，派生引擎负责组合，AI 负责理解和辅助维护。**

不能让 AI 每次回答问题时，重新阅读杭州和萧山的全部文档，再临时推导规则。

应该把规则编译成一份明确、完整、可以校验的结果。

## 三、核心：规则应该如何结构化？

我建议不要只把规则做成 Markdown，而是引入一套统一的规则数据模型。

### 1. 规则原子化

一条规则只描述一个相对独立的行为。

例如杭州麻将的庄闲放铳：

**R-HU-01 庄闲放铳** (规则原子)

| 字段 | 内容             |
| -- | -------------- |
| 类型 | 判定规则           |
| 触发 | 玩家打出弃牌         |
| 条件 | 庄闲双方，且满足三牢条件   |
| 否则 | 不提供点炮胡         |
| 结果 | 符合条件的玩家可以胡     |
| 依赖 | 庄家状态、实际牢数、胡牌资格 |
| 验收 | 实际牢数为 2 时不能点炮  |

一条规则可以关联：

- 其他规则
- 状态变量
- 计算公式
- 适用配置
- 原始资料
- 测试用例

这样，规则就不再是孤立的文字，而是一个有关系的知识节点。

### 2. 建立统一的规则数据模型

建议每条规则使用如下字段：

| 字段           | 作用      |
| ------------ | ------- |
| rule_id      | 唯一编号    |
| name         | 规则名称    |
| category     | 规则分类    |
| scope        | 适用范围    |
| trigger      | 触发条件    |
| conditions   | 判定条件    |
| branches     | 分支及否则逻辑 |
| effects      | 执行结果    |
| state_reads  | 读取的状态   |
| state_writes | 修改的状态   |
| formula_refs | 关联计算公式  |
| dependencies | 依赖规则    |
| timing       | 生效时机    |
| examples     | 判定示例    |
| tests        | 验收用例    |
| sources      | 原始依据    |

其中，\`state_reads\` 和 `state_writes` 很重要。

例如：

萧山麻将的跟庄规则：

- 读取：当前圈四张弃牌、玩家座位、实际财神。
- 触发：四名玩家依次打出牌。
- 判断：前面三张相同，第四张相同或为财神。
- 修改：产生一笔跟庄结算。
- 后续：刷新四家累计分，再处理弃牌响应。

这样就可以让 AI 理解一条规则对整个游戏运行过程的影响。

### 3. 规则之间建立关系

不要只做 Markdown 的双向链接。

建议明确关系类型：

| 关系         | 含义   |
| ---------- | ---- |
| depends_on | 依赖   |
| overrides  | 覆盖   |
| extends    | 扩展   |
| reads      | 读取状态 |
| writes     | 修改状态 |
| calculates | 使用公式 |
| validates  | 对应验收 |
| references | 参考来源 |

## 四、杭州麻将和萧山麻将应该如何继承？

这是整个系统最重要的设计。

我不建议复制一份杭州麻将文档，然后在里面修改成萧山麻将。

也不建议让萧山麻将永远只保存差异文档。

我推荐采用：

**基础规则集 + 差异规则集 + 编译后的完整规则集。**

### 1. 三种数据

**A. Base Rules：杭州麻将基础规则**

(基础规则集)

存储杭州麻将完整的规则定义。

```
base/hangzhou/
  rules/
  states/
  formulas/
  fan-tables/
  timing/
  ui/
  tests/
```

**B. Variant Rules：萧山麻将差异**

(差异规则集)

只存与杭州不同的地方。

```
variants/xiaoshan/
  manifest.yaml
  overrides/
  additions/
  disabled/
  tests/
```

**C. Compiled Rules：完整萧山麻将**

(编译产物)

将杭州基础规则和萧山差异合并，形成完整、独立的规则集。

```
compiled/
  hangzhou-v1/
  xiaoshan-v1/
```

### 2. 差异不只是沿用、修改、新增

我建议扩展成五种操作：

| 操作        | 说明     | 示例    |
| --------- | ------ | ----- |
| inherit   | 沿用基础规则 | 白板财神  |
| override  | 修改原规则  | 连庄牢数  |
| add       | 新增规则   | 掷骰加庄  |
| disable   | 关闭原规则  | 抢杠胡   |
| configure | 修改配置参数 | 底分、局数 |

这样能够避免一个问题：关闭某个功能和修改某个功能并不是一回事。

例如萧山麻将关闭抢杠胡，不应该把整套补杠流程复制过来，只需要明确关闭抢杠响应，并保留其他补杠逻辑。

## 五、LLM Wiki 到底适不适合？

我的结论是：

(推荐使用，但不作为核心规则引擎)

我查了一下目前的 Microsoft LLM Wiki。

GitHub：microsoft/llmwiki

它的架构很值得参考。

它有三个核心层：

| 层           | 功能                        |
| ----------- | ------------------------- |
| Raw Sources | 原始资料，不允许 AI 随意修改          |
| Wiki        | AI 生成和维护的 Markdown 知识页面   |
| Schema      | 通过 AGENTS.md 规定知识库结构和维护规范 |

另外还支持 MCP，让不同 Agent 可以访问同一套知识库。

这和你目前的需求有很高的契合度。

但是，它解决的是知识的积累、组织、关联和检索问题，并不天然提供麻将规则的继承、冲突裁决、确定性计算和规则验证。

### 我对几种技术的评价

| 技术                | 适合承担的职责        | 我的建议  |
| ----------------- | -------------- | ----- |
| LLM Wiki          | 知识整理、关联、问答     | 可以用   |
| Markdown + YAML   | 规则存储与人工维护      | 核心    |
| JSON Schema / Zod | 规则结构校验         | 必须    |
| TypeScript        | 规则合并、编译、验证     | 核心    |
| SQLite            | 索引、关系、版本元数据    | 后续加入  |
| QMD               | 大量 Markdown 检索 | 后续加入  |
| Neo4j             | 复杂知识图谱查询       | 暂时不需要 |
| 向量数据库             | 语义检索           | 暂时不需要 |

我还找到了另一个值得关注的项目：

llm-wiki：arronKler/llm-wiki。

它采用 Markdown + SQLite + FTS5 + Zod，提供 Agent Skills 和 Obsidian 集成，可以参考它的本地知识管理方式。

### 我的技术选型

我会组合两种设计思想：

- 借鉴 Microsoft LLM Wiki：原始资料、知识页面、Schema、MCP。
- 借鉴结构化数据工程：规则原子化、类型校验、规则继承、确定性编译和测试。

也就是说：

**LLM Wiki 负责让知识越来越丰富，麻将规则引擎负责让知识变成准确、完整、可执行的规则。**

不需要为了这个项目先搭建向量数据库、Neo4j 或复杂的 RAG 服务。

**麻将规则知识库**

**MahjongRuleKB**

杭州、萧山、桐庐、绍兴等地方麻将的结构化规则

**PrdGameSkill**

1. **规则查询**

   查询当前项目使用的麻将规则集。

这就不只是一个麻将知识库了，而是一个麻将游戏规则生产系统。

## 八、第一阶段应该怎么做？

我不建议一开始就把所有麻将地方玩法都录入，也不建议先开发一个复杂的知识库平台。

**先用杭州麻将 + 萧山麻将验证规则继承机制。**

我建议分四个阶段。

### Phase 1：建立规则标准

(第一优先级)

目标：把目前两份文档转成统一的结构化规则。

具体任务：

1. 建立九大规则分类标准。
2. 定义 Rule、State、Formula、Table、Timing 等数据模型。
3. 将杭州麻将整理为基础规则集。
4. 将萧山麻将整理为差异规则集。
5. 为每条规则增加唯一 ID。
6. 保留原始资料引用和人工裁决记录。

**验收标准：** 杭州和萧山规则都可以通过 Schema 校验。

### Phase 2：实现规则派生引擎

目标：能够自动合并基础规则和差异规则。

实现：

- 规则继承。
- 规则覆盖。
- 新增规则。
- 规则禁用。
- 依赖检查。
- 冲突检测。
- 完整规则导出。

**验收标准：** 不需要 AI 重新阅读原始文档，就能通过编译器生成完整萧山麻将规则。

### Phase 3：建立规则测试体系

目标：确保派生后的规则准确。

重点测试：

- 杭州麻将规则是否完整。
- 萧山麻将是否正确继承杭州规则。
- 修改一个规则是否影响相关规则。
- 结算公式是否能计算出正确结果。
- 多条规则同时触发时是否存在冲突。

特别是你已经积累的麻将 Gold Set，可以逐步纳入这套测试体系。

### Phase 4：接入 Agent

目标：让 pi-agent、OpenCode、PrdGameSkill 都能使用。

提供统一的查询接口：

```
get_ruleset()
get_rule(rule_id)
get_rule_dependencies(rule_id)
compare_rulesets()
compile_variant()
validate_ruleset()
generate_test_cases()
```

可以通过 MCP 暴露这些能力。

这样不同 Agent 不需要了解底层文件结构，只需要调用工具即可。

## 九、我最终建议的技术决策

| 决策项      | 推荐方案                  |
| -------- | --------------------- |
| 知识库形态    | 独立 Git 仓库             |
| 原始资料     | Markdown，保持不可变        |
| 规则存储     | Markdown + YAML       |
| 数据校验     | JSON Schema / Zod     |
| 规则继承     | 自建 TypeScript 编译器     |
| 知识整理     | 参考 Microsoft LLM Wiki |
| 搜索       | 初期全文检索，后续 QMD         |
| 关系管理     | 显式规则 ID + 依赖关系        |
| 数据库      | 第一阶段不需要               |
| Agent 接口 | 后续 MCP                |
| 自动化测试    | Vitest + Gold Set     |

### 有一个非常重要的设计提醒

你的杭州麻将文档和萧山麻将文档已经包含了复杂的状态、公式、时序和交互规则。

例如萧山麻将的跟庄、拖底、漏碰、漏胡，并不是简单增加几个配置项就能解决的。

因此，不要把所有规则都抽象成：

```
key: xxx
value: true
```

要区分：

- 配置型规则：开关、数值、局数。
- 判定型规则：触发、条件、分支、结果。
- 状态型规则：初始化、更新、重置。
- 计算型规则：公式、查表、入账。
- 时序型规则：事件顺序和阶段转换。

这五种规则需要不同的数据结构。

## 十、我想强调的最终目标

我认为这个项目应该独立于 PrdGameSkill。

它的定位应该是：

**麻将领域知识基础设施，而不是某个麻将游戏的策划文档仓库。**

未来它可以服务于：

- AI 麻将游戏定制开发。
- 不同地方麻将规则快速复用。
- 麻将游戏 PRD 自动生成。
- 麻将规则代码生成。
- 麻将规则自动化测试。
- 不同地方麻将玩法对比分析。

这也能成为你未来 AI 游戏定制开发的一项核心资产。

### 我建议下一步先确定三个架构决策

**1. 知识存储方式**

纯 Markdown + YAML，简单易维护

Markdown + YAML + JSON Schema（推荐）

直接使用 SQLite / 数据库

---

**2. 地方麻将继承方式**

基础规则 + 差异覆盖 + 完整规则编译（推荐）

每种麻将独立保存完整规则

通过知识图谱动态组合规则

---

**3. 第一阶段知识范围**

先支持四人好友房（推荐）

从一开始支持二人、三人、四人及不同房间模式

[确认架构决策，继续设计]

我的倾向是先把这三个选择定下来，然后正式整理 `MahjongRuleKB` 的架构设计文档。第一阶段只验证杭州麻将和萧山麻将，不扩张成通用麻将平台。
