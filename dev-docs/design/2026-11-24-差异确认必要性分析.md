# 差异确认的必要性分析：为什么「差异待确认」不该是默认状态

> 触发问题：规则方已经给出萧山玩法的差异文档，据此生成的差异卡本身就是「已经确定的事」。为什么生成出来的每一段还要挂着「差异待确认」等人工再审一遍？
>
> 分析日期：2026-11-24｜状态：分析结论，待评审后转为设计修订条目
>
> **修订记录（2026-11-25）**：本文第六节建议「把 `diff_status` 从默认候选反转为检查器输出」。该建议在《基座与变体需求文档工作流执行计划 v1.0 评审》中被判定为改变既有字段语义、与 D0 冻结原则冲突（P0-1），**已撤回**。现行方案见执行计划 v1.1： 保持「差异是否经人工确认」原义，机器检查结果写入独立字段 ，人工审查写入独立 ，三维各管一件事。本文第一至第五节的分析结论（逐段确认不可执行、三类风险应机器判定）仍然有效。

## 一、结论先行

1. **逐段人工确认没有必要。** 当前实现让 229 个片段全部进入 `candidate`，这个量级的人工签核不可能发生；即使发生了，签的也是「我看过了」，不是「我验证了什么」。这是审计剧场。
2. **但「差异不需要任何校验」也不成立。** 真实风险不在规则内容，而在**我们把原文结构化成卡片的这一步**：归类错了（新增实为改写）、改写丢信息（杭州卡有的槽位变体卡没有）、重复表达（杭州已有规则换个 ID 写成新增）。这三类可以机器判定，不需要人逐段读。
3. **建议改法：把「默认待确认」反转成「默认通过」，只把机器判不出的少数告警交给人。** 保留三维模型，只改 `candidate` 的产生来源：从「全量初始值」改成「检查器产出的告警」。
4. **当前设计没有错到必须推翻。** 设计 v1.8 只规定了 `diff_status` 的取值与来源（"Allow Change Segments 的人工确认状态"），**没有规定初始占比**。所以这是一次实现层修订，不是契约变更。

## 二、当前实现到底在确认什么（现状事实）

| 事实 | 位置 |
| --- | --- |
| `modified` / `added` 一律置 `candidate` | `studio/pipeline/generate-variant.ts` |
| `changes.json` 条目同样硬编码 `candidate` | `studio/pipeline/changes-json.ts` |
| 除人工写的 `diff-review.yaml` 外，没有任何路径能改成 `confirmed` | 全仓库检索无其他写入点 |
| `change_type` 由卡作者写在 front matter，**不是机器比对得出** | 例：`rulebook/specs/variants/xiaoshan/guize/xs-r-zhuangjia-02.md` |

关键在最后一行。设计文档里 `diff_status` 的本意是给"机器推断出的候选差异"兜底 —— 但实现中 `change_type` 从头到尾都是人写的。**兜底对象不存在，兜底动作却保留了下来**，于是它退化成一句恒真的"还没人签"。

这是一个典型的遗留：字段语义来自一个未采用的方案（AI 自动比对），实现却沿用了该方案的默认值。

## 三、规则方给的差异文档已经回答了哪些问题

把"谁回答了哪个问题"分开看，很多重复劳动就显形了：

| 问题 | 谁回答 | 需要再确认吗 |
| --- | --- | --- |
| 萧山和杭州在玩法上哪里不同 | **规则方原文**（差异文档） | 否，这是输入 |
| 这条差异落在哪张卡、哪个槽位 | 规则卡 `front matter` + 正文（`sources` 指向原文小节） | 部分需要，属结构化质量 |
| 卡片字段与引用是否自洽 | `compiler/validator.ts`（必填槽位、`base_rule_ref` 闭合、`depends_on` 闭合） | 否，已自动校验 |
| 算分结果对不对 | `tests/gold-set/`（60 条，27 条 verified）+ `calculators/` | 否，已自动校验 |
| 文本是否忠实原文 | `source_evidence_refs`（片段级溯源到原文小节） | 抽查即可，不必逐段 |
| **这条改写是否丢掉了杭州侧的约束** | 无人回答 | **应由机器回答** |
| **这条"新增"是否是杭州规则的重复表达** | 无人回答 | **应由机器回答** |
| **这条归类（修改/新增/继承）是否正确** | 部分：`validator` 只查 `base_rule_ref` 指向存在 | **应加强** |

只剩三行没人回答，而这三行恰好都是**结构化质量问题**，不是规则语义问题。语义问题规则方在原文里已经答完了。

## 四、逐段确认的成本与收益

| 项 | 全量逐段确认（现状） | 机器检查 + 少量告警 |
| --- | --- | --- |
| 人工工作量 | 229 段（萧山），每条要读、要判断"差异是否成立" | 只处理告警条目，预计个位数到十几条 |
| 判断依据 | 无清单，凭感觉 | 每条告警有明确原因（缺槽位 / 疑似重复 / 归类矛盾） |
| 出错方式 | 批量点"确认"，等于没签 | 告警不去看就会重新报警 |
| 可回归 | 无法回归：新生成的文档要全部重签 | 可回归：检查器随代码演进，历史结论可复算 |
| 审计价值 | 低（签的是"我看过"） | 高（签的是"我裁决了这条具体矛盾"） |

结论：逐段确认在这个量级上不是"更严格"，而是"更不可执行"。不可执行的严格等于没有严格。

## 五、真正该拦的三类风险

### R1 改写丢信息（`modified` 卡信息缺失）

杭州卡有的槽位，变体卡应有对应交代或显式声明不适用。若杭州卡有「中断」「结束」，变体卡只有「结果」，读者会丢失边界条件。

**可机器判定**：取基座卡槽位集合与变体卡槽位集合的差集；差集非空即告警，列出缺失槽位名。

### R2 新增实为重复表达（`added` 卡与杭州既有规则重合）

`XS-K-FANXING` 与 `HJ-K-FANXING-HUCHI` 是典型易混：如果一张卡声明 `added` 却没有 `base_rule_ref`，而它的名称或正文与某张杭州卡高度重合，那它不是新增，是改写（或干脆是重复）。

**可机器判定**：对 `added` 卡计算与杭州卡的名称相似度与正文相似度（简单字符 n-gram 足够，不需要模型）；超过阈值即告警，附上最相近的杭州卡 ID 供人裁决。

### R3 归类矛盾（`change_type` 与溯源字段不自洽）

| 声明 | 必须 | 不得 |
| --- | --- | --- |
| `inherited` | 有 `base_rule_ref` | 有自己的改写正文（否则应判 `modified`） |
| `modified` | 有 `base_rule_ref`，`compares_to` 非空 | 正文与基座卡完全一致（否则应判 `inherited`） |
| `added` | 无 `base_rule_ref` | 有 `compares_to` 指向基座卡 |

**可机器判定**：纯字段约束 + 正文一致性比较。现有 `compiler/validator.ts` 只做了"`base_rule_ref` 指向存在"，且有一处空转分支（`meta.change_type === "inherited" ? baseIds : baseIds`，三元两边相同），说明这块约束当初没写完。

### 已有但不在本讨论范围

- `base_rule_ref` 悬空（基座升级后失效）→ 已由 `studio/pipeline/base-upgrade.ts` 覆盖
- 未决项与发布阻塞 → 已由 `unresolved.yaml` + 渲染层「待裁决」覆盖
- 数值正确性 → 已由 Gold Set 覆盖

## 六、建议方案

### 6.1 状态初始值反转

| 检查结果 | `diff_status` | 渲染标记 |
| --- | --- | --- |
| 继承（无差异可比） | `not_applicable` | 无 |
| 修改 / 新增，三类检查全部通过 | `confirmed` | 只显示「修改」/「新增」 |
| 修改 / 新增，任一项检查报警 | `candidate` + `review_reason` | 「差异待确认」+ 具体原因 |

关键差别：`candidate` 从"默认值"变成"检查器的输出"。它重新获得了信息量 —— 看到它就说明**有一条具体的、可命名的问题**，而不是"还没人看"。

### 6.2 告警清单成为唯一人工入口

`documents/<变体>/diff-review.yaml` 从"逐条签核表"改为"告警裁决表"：

```yaml
# 只需裁决检查器报警的条目
decisions:
  - rule: XS-K-FANXING
    reason: added-similar-to-base(HJ-K-FANXING-HUCHI, 0.87)
    decision: 确认是独立番型表，非重复
    by: 规则方
  - rule: XS-F-HUPAI-GANGFEN
    reason: missing-slots(中断, 结束)
    decision: 萧山该条无中断概念，接受
    by: 规则方
```

无告警即无待办。人工工作量从 229 降到告警数。

### 6.3 检查器落点

新增 `studio/pipeline/diff-checks.ts`，纯函数，输入「基座卡 + 变体卡」输出告警列表；由 `generate-variant.ts` 调用并写入 `diff_status` / `review_reason`。不写盘、不依赖 AI，可单测。

## 七、为什么这不是推翻设计 v1.8

| 设计条目 | 原文 | 本次是否违反 |
| --- | --- | --- |
| 三维标记（I-38） | 必须按 `lineage` / `decision_status` / `diff_status` 同时记录 | 不违反，三维都保留 |
| `diff_status` 取值 | `candidate` / `confirmed` | 不违反，取值不变 |
| AD-37 | P1 才生成 `changes.json` | 不违反 |
| AC-25 | 每条都有 `lineage`，`diff_status` 按实际状态记录 | **本次更符合**：把 `candidate` 从"全量"改成"实际有问题的" |

真正的偏差在于：设计没有规定 `candidate` 初始占多少，而实现把"全部"当成了默认。本次修订补上的是这条语义边界。

## 九、需要规则方拍板的点

1. **R2 相似度阈值**：名称/正文相似度超过多少算"疑似重复"需要告警？建议先松（0.85 名称 或 0.6 正文），宁可多报，人再裁决。
2. **R1 槽位差集是否一律报警**：变体规则常有"该玩法不存在此概念"的合理缺失（如萧山无"中断"），是否需要卡内提供「不适用声明」槽位才能消警？建议需要 —— 否则消警靠口头，无法回归。
3. **历史结论怎样继承**：`diff-review.yaml` 里已有的人工确认结论，在检查器上线后如何处理？建议保留为"人工裁决覆盖"，即人工结论优先于检查器。

## 十、类比

现在的做法像**给每份体检报告的每个指标都盖一个"未见异常"的章**：章盖得越多，越没人看；真出问题那一个也没人注意。

应该做的是一台**只亮异常的机器**：正常的不吭声，报警的必须写清"哪一项、偏多少、建议怎么办"。人的时间应该花在那几个红点上，不是花在 229 个绿点上。
