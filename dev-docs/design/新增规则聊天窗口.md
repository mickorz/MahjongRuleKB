### 2. 支持三种引用方式

我认为引用能力是这个产品的核心，不应该只做一个普通的 `@` 输入框。

**第一种：引用规则卡**

例如策划点击：

`HJ-R-BANK-02 连庄与换庄`

点击「引用到对话」，聊天窗口自动附带：

- 规则 ID
- 规则名称
- 当前规则完整内容
- 当前规则版本

AI 可以直接针对这张规则卡讨论和修改。

**第二种：引用原始资料**

例如策划选择：

`sources/hangzhou/hangzhou-core-flow.md`

选中其中某一段，点击引用。

AI 获得：

- 原始文件路径
- 原始章节
- 引用内容
- 来源定位

这样 AI 修改规则时，可以保留证据链。

**第三种：引用其他规则集**

例如：

「参考萧山麻将的财神处理方式，调整杭州麻将。」

AI 可以同时读取：

- 杭州财神规则
- 萧山财神规则
- 两者的差异
- 对应原始资料

然后提出修改建议。

这里需要特别区分现有 Schema 中的三种引用：

| 引用 | 意义 |
| --- | --- |
| `base_rule_ref` | 继承关系 |
| `compares_to` | 规则对照 |
| `depends_on` | 实际规则依赖 |

不能把这三种关系混为一谈。

## 五、规则修改必须有 Diff 和审批

这是整个功能最重要的安全机制。

例如：

策划输入：

「杭州麻将的三摊承包结算规则需要调整，承包者还需要承担反承包情况下的某种费用。」

AI 不应该立即改 Markdown。

应该产生一个结构化变更提案：

**规则修改提案** · (等待确认)

目标：杭州麻将 · 基础规则

**修改对象**

`HJ-P-CONTRACT-01`

**修改原因**

补充三摊承包与反承包情况下的结算分配逻辑。

---

**变更内容**

原规则

原有承包结算条件和分配规则。

建议修改

补充反承包触发条件、责任承担者及各参与方的分配计算公式。

---

**修改前检查**

原始来源 · (已关联)

规则依赖 · (待检查)

派生规则影响 · (待分析)

Gold Set · (待执行)

---

示意提案，并非已经核实的具体规则内容。

继续讨论 · 确认并应用

这里还有一个重要规则：

**基础规则发生变化，不代表所有地方变种都自动跟着修改。**

因为你已经设计了基础版本锁定机制。

例如：

- 杭州从 1.0.0 升到 1.1.0。
- 萧山仍然锁定杭州 1.0.0。
- AI 分析萧山哪些 `inherited` 规则受到影响。
- `modified` 规则需要检查是否仍然完整有效。
- 策划决定是否升级萧山的基础版本。

这可以避免修改杭州规则时，意外破坏其他地方麻将。

当前只有一个本地用户，数据本身已经是结构化文件。没有必要为了聊天记录和规则搜索引入一整套数据库基础设施。

- 保存会话和提案状态。
- 释放文件锁。
- 清理过期临时文件。
- 不删除尚未处理的提案。

本地服务必须绑定 `127.0.0.1`，不能默认监听 `0.0.0.0`。

另外需要有 Origin 校验、CSRF 防护、路径白名单和 API Key 服务端隔离，避免浏览器页面或其他本地网页借助这个服务访问任意文件。

## 5\. Rule Domain：知识库访问层

这是我认为整个项目最值得优先设计的模块。

不能让 Agent 自己通过文件路径随意读取和修改 Markdown。

需要建立一个统一的规则访问层。

### 5.1 RuleSet Registry

负责发现和管理所有规则集。

例如：

```text
rulesets/
└── hangzhou/

variants/
├── xiaoshan/
├── tonglu/
└── shaoxing/
```

启动时扫描 Manifest，构建规则集注册表：

```ts
interface RuleSetDescriptor {
  rulesetId: string;
  name: string;
  kind: "base" | "variant";
  version: string;
  baseRulesetId?: string;
  baseVersion?: string;
  idPrefix: string;
  rootPath: string;
}
```

主要能力：

- 获取全部规则集。
- 判断基础规则集与地方变种。
- 获取版本信息。
- 获取基础规则依赖关系。
- 检查规则集是否可编译。
- 查找地方变种依赖的基础版本。

这里有一个当前代码需要先修正的问题。

现在的 `schemas/rule.ts`、`schemas/config.ts`、`schemas/unresolved.ts` 都把规则 ID 限定为 `HJ` 和 `XS`。

如果以后增加桐庐、绍兴，不能每次都修改 Schema。

我建议在 Manifest 中增加：

```yaml
ruleset_id: tonglu-friends-4p
id_prefix: TL
version: 0.1.0
```

Schema 使用通用 ID 格式，Validator 再根据对应 Manifest 检查前缀。

这样以后新增地方麻将，不需要改动程序代码。

### 5.2 Rule Repository

统一读取规则。

建议提供以下接口：

```ts
interface RuleRepository {
  listRules(rulesetId: string): Promise<RuleMeta[]>;

  getRule(ruleId: string): Promise<RuleDocument | null>;

  getConfig(
    rulesetId: string,
    configId: string
  ): Promise<ConfigItem | null>;

  getManifest(rulesetId: string): Promise<Manifest>;

  getUnresolved(rulesetId: string): Promise<UnresolvedEntry[]>;

  getRuleSource(ruleId: string): Promise<SourceReference[]>;
}
```

Agent 不需要知道规则卡实际放在哪个目录。

它只需要知道：

「我要读取 HJ-R-BANK-02」。

Repository 负责定位文件、读取元数据和正文。

### 5.3 Rule Search Index

第一阶段不需要向量数据库。

目前杭州已经有 60 张规则卡，规模很小。

先建立本地内存索引：

| 索引字段 | 用途 |
|--------|--------|
| ID | 精确查找 |
| name | 规则名称 |
| type | 类型过滤 |
| body | 正文关键词搜索 |
| scope | 适用范围 |
| status | 状态过滤 |
| sources | 来源定位 |
| base\_rule\_ref | 继承关系 |

检索方式：

1. ID 精确匹配。
2. 名称匹配。
3. 关键词搜索。
4. 依赖关系扩展。
5. 原始资料章节匹配。

索引在服务启动时生成，知识库发生修改后增量更新。

不需要引入 Qdrant、Milvus 或其他向量数据库。

后续规则规模增长到数千张，再评估 QMD 或全文检索引擎。

### 5.4 Source Reader

这是另一个独立模块。

它只能读取：

```text
sources/
```

禁止修改原始资料。

支持：

- 读取整个原始文档。
- 根据章节读取。
- 根据引用定位读取。
- 根据规则卡的 `sources` 反查证据。
- 返回文件路径和章节信息。

引用对象建议统一成：

```ts
interface RuleReference {
  type: "rule" | "source" | "config";

  id?: string;

  source?: string;
  section?: string;

  title: string;
  excerpt: string;
}
```

这样聊天消息可以同时引用规则卡和原始文档。

## 6\. Rule Agent：AI 聊天引擎

我建议采用一个主 Agent，不要一开始就做多个 Agent 协作。

目前业务复杂度没有必要引入 Master-Worker。

主 Agent 只负责理解策划意图、调用工具、生成提案。

### 6.1 Agent 内部模块

```text
Rule Agent
│
├── Intent Resolver
│   ├── 规则查询
│   ├── 规则讨论
│   ├── 规则新增
│   ├── 规则修改
│   ├── 规则集派生
│   └── 规则对比
│
├── Context Builder
│   ├── 当前规则集
│   ├── 聊天历史
│   ├── 用户引用
│   ├── 相关规则
│   └── 原始证据
│
├── Tool Runtime
│   ├── Knowledge Tools
│   ├── Analysis Tools
│   └── Proposal Tools
│
└── Response Renderer
    ├── 普通回答
    ├── 规则引用
    ├── 变更提案
    └── 未决问题
```

### 6.2 Agent 的上下文管理

这里不建议每次把整个麻将知识库发送给模型。

应该采用按需加载。

例如：

策划：

「萧山麻将的财神和杭州麻将有什么区别？」

Context Builder 只加载：

```text
当前目标规则集：
xiaoshan

基础规则集：
hangzhou

加载内容：
1. HJ-C-JOKER
2. XS-C-JOKER
3. 对应的原始杭州资料
4. 对应的原始萧山资料
5. 两个 Manifest
6. 相关未决项
```

而不是加载 60 张杭州规则卡和所有原始资料。

聊天历史也应该分层：

- System Context：固定规则维护规范。
- Conversation Context：当前对话。
- Rule Context：当前引用和检索到的规则。
- Proposal Context：当前修改提案。

当对话变长时，可以压缩聊天历史，但不能丢失尚未解决的修改提案、用户确认结果和规则引用。

### 6.3 Agent 工具定义

建议分为三个权限等级。

**A. Knowledge Tools：只读**

```ts
search_rules()
read_rule()
read_config()
read_manifest()
read_source()
compare_rulesets()
find_rule_dependencies()
```

**B. Analysis Tools：分析**

```ts
analyze_rule_conflict()
analyze_rule_impact()
analyze_rule_completeness()
analyze_variant_difference()
```

**C. Proposal Tools：生成修改建议**

```ts
create_rule_proposal()
update_rule_proposal()
create_config_proposal()
create_variant_proposal()
resolve_unresolved_proposal()
```

这里我建议不向 Agent 暴露：

```ts
write_file()
delete_file()
execute_shell()
apply_patch()
```

Agent 没有直接修改文件的能力。

它只能生成符合 Schema 的结构化提案。

真正的文件写入由 Mutation Service 负责。

这样即使模型输出错误，也不会直接破坏知识库。

### 6.4 模型适配层

建议不要把 GLM、DeepSeek 或其他模型直接写进 Agent 逻辑。

抽象为：

```ts
interface LLMProvider {
  chat(
    messages: ChatMessage[],
    tools: ToolDefinition[],
    options?: ChatOptions
  ): AsyncIterable<LLMEvent>;
}
```

配置示例：

```yaml
provider:
  type: openai-compatible
  base_url: ${LLM_BASE_URL}
  model: ${LLM_MODEL}
  api_key_env: LLM_API_KEY

generation:
  temperature: 0.1
  max_tokens: 8192
  tool_calling: true
  streaming: true
```

第一阶段优先要求模型支持 Tool Calling 和结构化输出。

Streaming 用于改善体验，不应该成为规则正确性的前提。

## 7\. Proposal Engine：规则变更提案系统

这是最重要的业务模块。

我建议所有规则变更都采用统一的 Proposal 数据结构。

### 7.1 提案数据结构

新增 `schemas/proposal.ts`：

```ts
interface RuleChangeProposal {
  id: string;

  targetRuleset: string;

  baseRevision: {
    files: Record<string, string>;
    rulesetVersion: string;
  };

  changes: RuleChange[];

  rationale: string;

  evidence: RuleReference[];

  impactAnalysis: ImpactAnalysis;

  validation: ValidationResult[];

  status:
    | "draft"
    | "needs_clarification"
    | "ready"
    | "approved"
    | "applied"
    | "rejected"
    | "stale"
    | "failed";

  createdAt: string;
  updatedAt: string;
}
```

`RuleChange` 使用受限的操作联合类型：

| 操作 | 用途 |
|--------|--------|
| `create_rule` | 新增规则卡 |
| `update_rule` | 修改规则卡 |
| `create_config` | 新增配置 |
| `update_config` | 修改配置 |
| `create_unresolved` | 新增未决项 |
| `resolve_unresolved` | 处理未决项 |
| `update_manifest` | 更新规则集版本等元数据 |

第一阶段不支持删除规则。

因为删除一张规则卡可能破坏其他规则的引用关系。后续可以增加专门的废弃和迁移机制。

### 7.2 提案生命周期

1. **Draft：生成提案**
   
   Agent 产生结构化修改建议。
2. **Review：人工审核**
   
   查看修改原因、证据、Diff 和影响范围。
3. **Validate：预验证**
   
   在临时工作区执行 Schema、引用和规则校验。
4. **Approve：用户确认**
   
   用户明确点击确认应用。
5. **Apply：正式写入**
   
   Mutation Service 修改本地文件。
6. **Verify：最终检查**
   
   更新索引、检查工作区和测试结果。

### 7.3 三种修改情况

**情况一：普通规则修改**

例如修改杭州麻将的杠开判定。

- 读取 `HJ-R-...`
- 生成完整规则卡
- 展示 Diff
- 检查引用和必填槽位
- 用户确认
- 写入文件

**情况二：新增地方规则**

例如新增萧山麻将特有的玩法。

AI 需要判断：

- 杭州是否存在对应规则？
- 是新增还是修改？
- 是否有基础规则依赖？
- 是否影响结算？
- 是否需要新增配置？

对应选择：

```yaml
origin: variant
change_type: added
```

**情况三：修改继承规则**

例如：

「萧山麻将沿用杭州的杠开规则，但增加一项特殊限制。」

AI 需要把它转为：

```yaml
origin: variant
change_type: modified
base_rule_ref: HJ-R-GANG-01
```

而且必须生成一张完整有效的萧山规则卡，不能只写一句差异说明。

这完全遵循你目前 v3.2 执行计划的规则。

### 7.4 冲突与未决处理

如果原始资料存在矛盾，AI 不能擅自选择一个答案。

例如：

- 萧山配置表说沿用白板财神。
- 萧山术语表说由翻财神决定。

AI 应该产生：

```yaml
status: disputed
release_blocker: true

candidates:
  - white_dragon
  - flipped_joker
```

然后要求策划确认。

规则判定、算分和结算金额相关的不确定内容，不允许通过简单默认值变成已确认规则。

## 8\. Mutation Service：受控文件写入

这一层是 Proposal Engine 和真实文件之间的安全边界。

我建议分成四个模块。

| 模块 | 职责 |
|--------|--------|
| Path Resolver | 根据规则 ID 确定允许修改的文件 |
| Revision Guard | 检查文件是否被外部修改 |
| Transaction Manager | 管理多文件写入和回滚 |
| Workspace Writer | 执行最终文件写入 |

### 8.1 文件路径不能由 AI 决定

例如：

```ts
resolveRulePath(
  "xiaoshan",
  "XS-R-BANK-02"
);
```

服务端根据规则集 Manifest、规则类型和 ID 推导路径。

AI 只传：

```json
{
  "rulesetId": "xiaoshan",
  "ruleId": "XS-R-BANK-02"
}
```

不能让 AI 自己提供任意的绝对路径。

### 8.2 Revision Guard

这是本地单人场景仍然需要的机制。

因为策划可能同时使用 VS Code 修改 Markdown。

提案生成时保存文件 Hash：

```text
XS-R-BANK-02
SHA256: abc123...
```

点击确认时再次计算。

如果发生变化：

(提案已过期)

要求重新读取文件、合并最新内容并生成新的 Diff。

不允许直接覆盖。

### 8.3 文件事务与回滚

建议流程：

```text
Apply Proposal
      |
      v
获取写入锁
      |
      v
检查文件 Hash
      |
      v
构建临时工作区
      |
      v
应用所有候选修改
      |
      v
执行 Schema + Validator
      |
      v
执行 Compiler + Gold Set
      |
      v
全部通过？
   /       \
  否         是
  |          |
回滚       备份原文件
             |
             v
         原子替换文件
             |
             v
         写入事务日志
             |
             v
         更新规则索引
             |
             v
           完成
```

多文件写入不能假设操作系统提供真正的跨文件原子事务。

因此 `.rule-studio/transactions/` 需要记录：

- 事务 ID。
- 变更文件列表。
- 原始文件 Hash。
- 新文件 Hash。
- 备份位置。
- 当前执行状态。

服务意外退出时，下一次启动可以检查未完成事务并恢复。

**Git 只负责历史版本管理，不代替事务管理。**

另外，第一阶段应用提案后只修改本地工作区，不自动提交 Git，更不自动 Push GitHub。策划可以继续检查差异，再决定何时提交。

## 10\. 本地数据持久化

单人模式下，我建议第一阶段完全不引入数据库。

通过文件持久化即可。

目录：

```text
.rule-studio/
│
├── sessions/
│   ├── session-001.jsonl
│   └── session-002.jsonl
│
├── proposals/
│   ├── proposal-001.json
│   └── proposal-002.json
│
├── staging/
│   └── proposal-001/
│
├── transactions/
│   └── transaction-001.json
│
└── cache/
    └── rule-index.json
```

各自职责：

| 数据 | 存储方式 | 原因 |
|--------|--------|--------|
| 聊天消息 | JSONL | 追加写入、易恢复 |
| 工具执行记录 | JSONL | 方便追溯 |
| 修改提案 | JSON | 保存完整状态 |
| 临时文件 | 普通文件 | 预验证 |
| 事务记录 | JSON | 故障恢复 |
| 搜索索引 | 可重建缓存 | 不作为事实源 |

### 聊天记录结构

```json
{
  "session_id": "session-001",
  "role": "assistant",
  "content": "我找到了相关规则。",
  "references": [
    {
      "type": "rule",
      "id": "HJ-C-JOKER"
    }
  ],
  "proposal_id": null,
  "timestamp": "2026-11-24T10:00:00+08:00"
}
```

### 提案独立于聊天记录

这是一个重要的设计。

聊天只是交流过程，提案才是真正的修改对象。

例如：

一个聊天会话可以产生多个提案。

用户可以：

- 继续讨论第一个提案。
- 创建第二个提案。
- 暂停当前提案。
- 关闭聊天窗口。
- 明天重新打开提案继续处理。

因此不能将提案只保存在聊天消息中。

### 模型配置

建议：

```text
.rule-studio/
└── settings.json
```

保存非敏感设置，例如 Provider、模型名称和 API 地址。

API Key 使用本地环境变量或 `.env.local`，加入 `.gitignore`，绝不能返回给前端。

如果以后需要更完善的本地凭证管理，再接入 Windows Credential Manager 或系统密钥链。

## 12\. Workflow Observability：AI 执行过程可观察

这部分我建议从第一天就做好。

不能只在界面上显示：

「AI 正在思考……」

策划需要知道 AI 到底执行了什么操作。

我建议采用 SSE 事件协议：

```ts
type StudioEvent =
  | { type: "run.started" }
  | { type: "context.search.started" }
  | { type: "context.search.completed"; count: number }
  | { type: "tool.started"; tool: string }
  | { type: "tool.completed"; tool: string }
  | { type: "tool.failed"; tool: string; error: string }
  | { type: "assistant.delta"; text: string }
  | { type: "proposal.created"; proposalId: string }
  | { type: "validation.completed"; passed: boolean }
  | { type: "run.completed" }
  | { type: "run.failed"; error: string };
```

前端展示：

**当前任务：分析萧山财神规则**

(执行完成)

1. **搜索规则**
   
   找到杭州 1 条、萧山 1 条
   
   (完成)
2. **读取原始资料**
   
   读取杭州、萧山对应章节
   
   (完成)
3. **规则差异分析**
   
   发现财神定义存在冲突
   
   (完成)
4. **生成修改提案**
   
   生成 1 项待裁决内容
   
   (等待策划)

特别注意：不要依赖模型是否支持 JSON Schema 流式输出。

工具调用参数、结构化提案都由服务端完整解析后，再向前端发送执行状态和结果摘要。大型 JSON 内容可以折叠查看。

这样即使模型一次性返回很大的结构化结果，策划也能知道当前任务处于哪个阶段。

## 13\. 规则验证体系

Rule Studio 不能自己再造一套规则验证器。

直接复用现有知识库的质量体系。

建议统一成：

**Proposal Quality Gate**

1. **Schema Validation**
   
   YAML / Markdown 元数据是否合法。
2. **Rule Validation**
   
   必填槽位、ID、引用关系是否正确。
3. **Consistency Validation**
   
   基础规则、变种规则、配置之间是否冲突。
4. **Compilation**
   
   基础规则与差异规则能否合并。
5. **Gold Set**
   
   规则判定、计算公式和结算逻辑是否通过测试。

---

(全部通过才允许应用)

如果存在 release blocker，提案可以保存和讨论，但不能将规则集标记为可发布。

这里有两个不同的概念：

- **可以保存**：规则草稿可以存在，即使存在未决项。
- **可以发布**：必须满足规则集的发布门槛。

不应该因为某个规则存在争议，就不允许策划保存其他已经确认的工作。

## 14\. 基础规则与地方变种的影响分析

这是麻将知识库区别于普通 Markdown 编辑器的地方。

假设：

```text
杭州麻将 v1.0.0
      |
      ├── 萧山麻将
      |
      ├── 桐庐麻将
      |
      └── 绍兴麻将
```

杭州基础规则修改时，系统必须分析下游变种。

例如修改：

`HJ-R-GANG-01`

系统需要检查：

1. 哪些地方规则集锁定了杭州旧版本？
2. 哪些地方规则卡通过 `base_rule_ref` 继承这条规则？
3. 哪些规则通过 `depends_on` 引用了它？
4. 哪些规则是 `modified`，可能需要重新检查？
5. 哪些 Gold Set 受到影响？

建议新增：

```ts
interface ImpactAnalysis {
  changedRules: string[];

  affectedVariants: {
    rulesetId: string;
    pinnedVersion: string;
    affectedRules: string[];
    impactType:
      | "inherited"
      | "modified"
      | "dependency";
    requiresReview: boolean;
  }[];

  affectedTests: string[];

  blockers: string[];
}
```

举个例子：

杭州从 `1.0.0` 升到 `1.1.0`。

萧山仍然锁定 `1.0.0`，不自动升级。

Rule Studio 可以提示：

- 杭州新版本已产生。
- 萧山当前仍使用旧版本。
- 发现 3 张相关规则卡。
- 需要检查 2 张 modified 卡。
- 建议重新编译和执行 Gold Set。

由策划决定是否升级萧山。

**不要让 AI 自动升级所有地方麻将。**

## 15\. 本地运行安全边界

虽然只有一个人使用，但本地 Web 服务并不等于没有安全风险。

建议明确以下约束：

| 安全项 | 决策 |
|--------|--------|
| 网络监听 | 仅 `127.0.0.1` |
| 前后端 | 同源访问 |
| 文件访问 | 项目目录白名单 |
| 原始资料 | 只读 |
| API Key | 仅服务端 |
| Agent 文件权限 | 只读 + 提案 |
| Agent Shell 权限 | 不开放 |
| 正式写入 | 人工确认 |
| Git 操作 | 不自动 Push |
| 写入并发 | 单写入锁 |
| 外部文件修改 | Hash 检查 |

前后端采用同源部署，可以减少跨域复杂性。

同时，服务端需要校验 Origin、Fetch Metadata 和状态变更请求的 CSRF 防护。MDN 对 CSRF 防护提供了 Token、Fetch Metadata 等方案；Chrome 也有关于本地网络访问的安全指导。citeturn937085search2turn937085search3turn937085search0

这里不需要让 Agent 拥有电脑的任意文件访问能力。

它只应该能够访问 MahjongRuleKB 允许的规则资源。

## 17\. 当前架构需要特别修正的三个问题

在正式开发之前，我认为有三个地方必须处理。

**问题一：Validator 与文件目录绑定过紧。**

目前 `compiler/validator.ts` 通过：

```ts
const isVariant = rs.dir.startsWith("variants");
```

判断规则集类型。

但是 Rule Studio 需要在 `.rule-studio/staging/` 下验证候选规则，临时目录不一定以 `variants/` 开头。

建议改为显式传递：

```ts
validateRuleset({
  ruleset: candidate,
  kind: "variant",
  baseRuleset: base
});
```

让 Validator 不再依赖具体文件路径。

**问题二：规则 ID 不能继续硬编码 HJ 和 XS。**

需要改成 Manifest 驱动，支持未来任意地方麻将。

**问题三：修改提案必须支持版本快照。**

不能只保存：

```text
修改了哪张规则卡
```

还必须保存：

```text
修改前的版本
修改后的版本
修改依据
来源证据
验证结果
应用状态
```

否则后续很难追踪 AI 为什么修改了一条规则。

## 四、最重要的交互设计：不要让 Agent 直接修改规则文件

这一点我建议继续沿用上一版架构。

PiBot 本身有文件读写工具、权限审批和审计机制，但普通工具审批不等于麻将规则的业务审批。

所以要分成两个层次：

**第一层：Agent 可以做什么**

(自动执行)

- 搜索规则。
- 读取规则。
- 比较杭州与萧山。
- 分析继承关系。
- 生成规则修改提案。
  ---
  **第二层：策划可以批准什么**
  (人工确认)
- 确认新增规则。
- 确认修改规则。
- 查看完整 Diff。
- 执行 Schema 验证。
- 执行 Compiler。
- 执行 Gold Set。
- 正式写入知识库。

建议禁止麻将助手使用通用 `write_file`、`apply_patch` 和 Shell 工具直接修改知识库。

正式修改只能经过：

`Proposal → Diff → Validate → Approve → Apply`

这样 PiBot 的 Agent Runtime 负责智能，Mahjong Capability 负责规则正确性。

另外，PiBot 的工作区变更恢复能力并非所有平台都相同，README 特别提到了 macOS 的自动检查点恢复。因此 Windows 下的文件事务备份、Hash 检查和回滚，我们仍然需要自己实现。

## 我的最终判断

(建议采用 PiBot 作为底座)

我认为这次选型能够显著减少重复开发。

但有一个原则：

**不要开发一个麻将版 PiBot，而是开发一个使用 PiBot 技术底座的麻将规则工作台。**

我们应该把精力集中在三个真正有价值的地方：

- AI 能否理解麻将规则。
- AI 能否正确维护基础规则和地方变种。
- AI 修改规则后能否通过完整的规则验证。

这三个才是 MahjongRuleStudio 的核心竞争力。

下一步我建议先做一次 **PiBot Fork 技术可行性与裁剪评审**：确定哪些原有 Capability 保留、哪些禁用、哪些需要扩展，再把上一版完整架构改写成真正基于 PiBot 的 `MahjongRuleStudio Architecture v1.0`。
