# 《需求全文生成 v1.3 修订清单》评审意见（第 3 轮）

> 日期：2026-11-24
> 被评审文档：`dev-docs/planning/2026-11-24-需求全文生成v1.3修订清单.md`（v1）
> 交叉核对：v1.2 设计文档、第 2 轮评审意见、主需求文档 v2.0、需求覆盖与补齐设计
> 处理结论：清单升 v2（见被评审文档的修订记录与「第 3 轮评审补充」章节）

## 一、总体评价

方向通过，需要小幅修订。

上一轮提出的 4 个内部冲突、4 个架构问题、3 个验收问题和 4 个设计补充，基本都已经转化成了明确的修改任务。

尤其认可三个决定：

1. **不修改 Compiler**：文档生成层负责处理配置差异，不破坏现有编译器边界。
2. **提案统一存储**：文档提案和规则提案共用 `.rule-studio/proposals/`，避免出现两套审批机制。
3. **暂不冻结 JSON Schema**：先统一设计文档，评审通过后再单独冻结 Schema。

不过还有几个问题，如果直接把当前清单交给 Agent 执行，可能会留下新的设计漏洞。

## 二、建议修改的 6 个问题

### 1. A-3 没有覆盖所有旧字段引用（P0 必须修改）

A-3 目前只要求修改 FR-38 和 AC-32。但 v1.2 中还发现两处：

- 6.2 标题仍使用「不合并成一个 `source_refs`」。
- 8.4 仍要求修改段落时列全 `source_refs`：

  > 修改段落时 AI 必须列全 source_refs 供用户确认改哪几个来源

  这与新模型的四类引用不一致。建议将 8.4 改成：列出 `requirement_refs` 确认关联的原子需求；列出 `rule_refs` 确认关联规则卡；列出 `config_refs` 确认关联配置；列出 `source_evidence_refs` 确认原始证据。

另外，A-3 验收要求 `source_refs` 为零命中，但 G 自检又允许废弃说明中出现，两处口径需要统一。

### 2. A-4 遗漏了 Stage 4 的五种标记（P0 建议修改）

v1.2 第五节仍然是「Stage 4：五种标记判定」，但 A-4 只列出 I-23、FR-31、3.2，没有覆盖 Stage 4。建议统一改成「Stage 4：三维状态判定」，并保留三维独立判断：

| 维度 | 判断什么 |
| --- | --- |
| lineage | 内容从哪里继承或产生 |
| decision_status | 规则是否已经裁决 |
| diff_status | 差异是否经过人工确认 |

五种展示标签只是 UI 表现，不再作为底层数据模型。

### 3. C-2 的六态覆盖语义还不完整（P0 必须修改）

上游《需求覆盖与补齐》定义六种状态：已覆盖、部分覆盖、提取缺失、原文缺失、原文冲突、明确排除。但 C-2 建议的 AC-24 只有「正文表达 / 待裁决 / 明确排除 / 未决项」。

容易产生一个问题：**部分覆盖和提取缺失不能因为有记录，就被认为已经完成覆盖。** 建议 AC-24 明确六态与全文落点的关系：

| 覆盖状态 | 全文落点 |
| --- | --- |
| 已覆盖 | 正文规则表达 |
| 部分覆盖 | 正文 + 缺失细节记录 + 补齐任务 |
| 提取缺失 | 补齐任务，不能假装已有规则 |
| 原文缺失 | 未决项 |
| 原文冲突 | 待裁决清单 |
| 明确排除 | 明确排除清单 |

还需要区分两个指标：需求**是否有落点**、需求**是否已经完整覆盖**。两者不能混为一谈。否则 AI 可以通过把所有问题登记到待处理列表，让一份实际上还有大量缺口的需求文档通过完整性验收。

### 4. B-3 的 ID 生命周期仍然缺少匹配机制（P0 必须修改）

这是整个设计中技术风险最高的一项。清单目前规定：`block_id` 使用确定性分配器；先匹配 `logical_block_id`；再匹配 `segment_id`；拆分和合并记录 `segment_lineage`。

但确定性 ID 分配器只能解决新 ID 怎么分配，不能解决：**第二次生成时，如何识别新旧内容属于同一个逻辑块？** 尤其是第一次 `BLOCK-001` 含 `SEG-001`、`SEG-002`，第二次合并为 `SEG-003` 时，如何确认 `SEG-003` 与它们的关系？

建议补充三个约束：

1. 持久化逻辑身份映射，不允许每次生成时重新推断 ID。
2. `segment_lineage` 明确支持一对多、多对一关系，记录 split、merge 等关系类型。
3. 如果无法确定身份对应关系，不自动迁移人工修改，原修改进入「失效待处理」。

这里不要求实现语义匹配算法，符合 F 部分「明确不做」的范围。但必须定义一个**可执行的身份映射机制**，否则 FR-52 无法真正验收。

### 5. B-4 的产物目录存在遗漏（P0 建议修改）

清单规定 `documents/<variant>/` 只保留 `document.json`、`editorial-overrides.yaml`、`history/`，但 v1.2 原本还有 `需求全文.md`、`provenance.json`、`changes.json`，D-2 又明确规定后两者是派生文件。

需要决定它们究竟放在哪里：保留在 `documents/<variant>/` 作为可重建产物，还是移动到 `.rule-studio/workflow/<taskId>/stage-N/` 作为运行产物。不能一边要求目录只保留三项，一边又要求维护派生文件。

另外还有一个细节：`document.json` 是生成文档块的事实源，但 `editorial-overrides.yaml` 保存人工表达修改，也是独立的权威输入。建议明确：

- `document.json`：生成内容及结构的事实源。
- `editorial-overrides.yaml`：人工表达修改的事实源。
- `provenance.json`：派生索引。
- `changes.json`：派生差异索引。
- `需求全文.md`：渲染产物。

这样不会把人工修改错误地归类为派生数据。

### 6. 统一提案还需要定义文档提案的数据契约（P0 必须修改）

B-4 目前只说「统一 `proposals/<id>.json`，新增 `type: document`」。方向正确，但还不够。主需求文档 10.2 原来的提案结构主要服务于规则卡、配置和 Manifest 修改，文档提案需要额外支持：

```json
{
  "type": "document",
  "targetVariant": "xiaoshan",
  "basedOnDocumentVersion": 3,
  "target": {
    "blockId": "DOC-XS-000123",
    "segmentId": "SEG-000456"
  }
}
```

这只是结构示意，还需要明确：

- 文档提案如何记录修改前后的内容。
- 如何记录目标文件 Hash。
- 如何校验 `based_on_document_version`。
- 如何复用现有 Proposal 状态机。
- 如何进入现有事务写入和回滚机制。

尤其是文档提案必须**同时支持文档版本校验与文件 Hash 校验**。否则虽然文件统一了，但实际还是两套不同的提案实现。

## 三、另外两个小问题

1. **编号范围存在错误。** 总览写 `AD-34 至 AD-38`，但 E-1 实际只定义了 AD-34、AD-35、AD-36、AD-37，缺少 AD-38。建议将范围改为 AD-34 至 AD-37，并同步 G 自检。
2. **AC-48 的 `diff_status` 口径不明确。** D-4 规定 P0-A 不做差异引擎，但 AC-48 只要求「没有 `diff_status: confirmed`」，意味着理论上仍可能出现 `diff_status: candidate`。杭州基座没有变体差异，建议明确 P0-A 中 `diff_status` 应当缺省、为 `null`，或采用明确的 `not_applicable` 状态，并同步 Schema 约束。

## 四、最终执行建议

不建议重新设计 v1.3，而是把上述问题补充到当前修订清单中。执行顺序：

1. **先修订修订清单**：补齐 A-3、A-4、C-2、B-3、B-4 等问题，以及编号和 P0-A 状态定义。
2. **Agent 执行 v1.3 文档修改**：同步修改需求全文设计文档和 RuleStudio 主需求文档，按 E-2 更新进度。
3. **重新评审 v1.3**：重点检查 Document Block、ID 生命周期、提案结构、目录边界和六态验收。
4. **最后冻结 JSON Schema**：设计评审通过后，再进入 Schema 和 CLI 内核实现。

## 五、额外建议

这次不要让 Agent 顺手开始实现代码。

RuleStudio 有两条能力主线：① 规则知识库维护、需求原子化、覆盖与补齐；② 结构化规则生成完整需求文档、变体差异追溯、AI 对话编辑。第二条依赖第一条的产物，两条线的接口、数据结构和验收边界必须先确定。

**当前最重要的是保证 Document Block 将来能够长期稳定使用，而不是尽快把 Markdown 生成出来。** 只要 Block 身份、片段来源、差异状态和提案回流这几个基础设计没有问题，后面增加 Web 编辑器、AI 对话修改、增量重生成，都可以在这个基础上扩展。

结论：当前修订清单大方向通过，但建议先补充以上问题，再交给 Agent 执行。不需要扩大本次开发范围。
