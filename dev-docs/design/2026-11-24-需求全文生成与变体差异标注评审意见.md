# 《需求全文生成与变体差异标注》v1.1 评审意见

> 日期：2026-11-24
> 被评审文档：`dev-docs/design/2026-11-24-需求全文生成与变体差异标注.md`（v1.1）
> 评审对象版本：v1.1（提交 `1f5c1e8`）
> 说明：文中图片与产品截图（示意图）此处省略，文字内容完整保留。

## 评审对象

我看了仓库这份最新的《需求全文生成与变体差异标注》设计文档（v1.1）。

先说结论：**这版已经基本把我们之前讨论的三个方向合并到了一套完整架构中，而且整体技术路线是可行的。**

尤其是这次加入的 Document Block 和对话式段落编辑，方向是正确的。它解决了一个关键问题：全文不是一次性生成的 Markdown，而是有结构、有身份、有来源关系、可以持续修改的文档。

我认为目前可以进入工程设计评审，但还不建议直接按现有文档开工。还有几个数据模型和工作流边界需要收紧，否则后面实现对话编辑和增量生成时容易返工。

## 一、这版设计做对了什么

| 设计点 | 评审意见 |
| --- | --- |
| 复用现有 Compiler | 正确，不重复实现规则继承 |
| Stage 0～7 | 合理，阶段职责比较清晰 |
| 章节映射层 | 必须有，解决规则分类与策划阅读顺序不同的问题 |
| 五种差异标记 | 很有价值，尤其区分明确继承与默认继承 |
| Rule Change Segments | 正确，解决整张卡标橙色但不知道具体改了什么的问题 |
| Document Block | 必须采用，不能从 Markdown 反向识别段落 |
| 四种对话编辑行为 | 正确，避免文字修改直接改变规则事实 |
| Proposal + 门禁 | 应复用现有规则修改机制 |
| 增量重生成 | 必须支持，不能每次编辑都全量执行 |

特别认可文档中的这条原则：

> AI 可以通过对话修改需求，但不能绕过结构化规则知识库直接修改最终事实。

这应该成为整个 Mahjong Rule Studio 的核心不变量。

## 二、必须修改的 6 个问题

### P0-1：杭州与萧山必须使用同一套文档章节结构（必须修改）

这是我最在意的一个问题。

目前文档第 3.1 节定义：

- 杭州：游戏概述、名词、开局、行牌、承包、算分、番型、结算……
- 萧山：杭州基座继承内容、萧山修改规则、萧山新增规则、萧山专属配置……

这两套结构不一致。

但真实需求是：切换杭州、萧山时，看到的是同一份需求文档结构，只是具体内容发生变化，并且明确标注差异。

建议修改为：

- 杭州（基础版本）：第 1 章 游戏规则概述（杭州基础规则，基座规则）；第 2 章 开局与发牌（杭州开局规则）；第 3 章 轮庄规则（杭州轮庄规则）……
- 萧山（派生版本）：第 1 章 游戏规则概述（杭州基础规则，基座沿用）；第 2 章 开局与发牌（杭州开局规则，默认继承）；第 3 章 轮庄规则（庄家自摸或流局时原庄继续坐庄 —— 萧山修改；闲家自摸时由赢家接庄 —— 萧山新增）

这样才是真正的全文变体切换。建议：

1. 所有麻将变体共享同一套 Document Template。
2. `section_id` 在不同变体之间保持一致。
3. 通过 Compiler 得到有效规则集，再按照相同章节映射组织内容。
4. 差异标记属于正文的展示属性，不改变章节组织方式。
5. 变体专属配置、待裁决事项可以作为对应章节内容或附录。

**不要按照规则来源重新组织萧山全文。** 这项建议应修改第 3.1 节和 Stage 2。

### P0-2：P0 的实施范围与上游需求补齐计划冲突（必须修改）

对照上游文档 `2026-11-24-RuleStudio需求覆盖与补齐.md`，存在明确冲突：

| 文档 | 第一阶段范围 |
| --- | --- |
| 需求覆盖与补齐 | 只完成 2.3.3 算分规则单章节实验 |
| 全文生成设计 | P0 就要求杭州 61 张卡、25 项配置全部生成完整全文 |

而全文生成设计又明确规定：「覆盖未完成的变体不得宣称『全文完整』」。这三个要求目前无法同时满足。

建议调整为：

| 阶段 | 任务 | 验收 |
| --- | --- | --- |
| P0-A | 以 2.3.3 算分规则跑通 Document Block 全流程 | 单章节生成、来源追溯、覆盖验证 |
| P0-B | 扩展杭州全部章节的需求覆盖，生成杭州完整需求全文 | 61 张卡、25 项配置及原子需求全部完成映射 |
| P1 | 萧山变体全文与差异标注 | 相同章节结构，文字级差异可追溯 |
| P2 | 对话式段落编辑 | 修改提案、审核、增量重生成 |

这样不会出现一份看起来完整、实际原始需求还没有全部核对的文档。

另外，**AC-24 不能只检查 61 张卡和 25 项配置是否进入全文，还必须检查原子需求是否被完整表达**。否则仍然可能出现卡片全部进入文档，但某个需求细节在生成时丢失的问题。

### P0-3：五种差异标记实际上混合了两个维度（必须修改）

当前五种标记：

- 基座沿用
- 变体修改
- 变体新增
- 默认继承
- 待裁决

这里存在一个数据模型问题。前四种表示的是**规则来源关系**，而「待裁决」表示的是**规则状态**。两者并不是互斥的。

例如一条萧山修改规则，既可以是：来源 = 变体修改、状态 = disputed、release_blocker = true。如果只能选择五种标签中的一种，就会丢失其中一部分信息。

建议拆成三个独立维度：

| 维度 | 取值 |
| --- | --- |
| 来源关系 lineage | explicit_inherited / default_inherited / modified / added |
| 规则状态 decision_status | confirmed / unresolved / disputed |
| 差异审核 diff_status | candidate / confirmed |

展示时组合，例如「萧山修改 / 规则状态：待裁决 / 差异审核：待人工确认」。实际展示中可以同时存在多个标记，而不是强制选择一个。

还有一个细节：文档提到差异对照模式支持「删除」，但目前 Compiler 的 `compileVariant` 并没有定义 `removed` 处理机制，它目前处理的是 `inherited`、`modified`、`added`。因此需要明确：

- 第一阶段不支持规则删除，就从当前能力描述中移除删除标记。
- 如果确实需要删除，未来单独设计规则废弃或排除机制。

不要让展示层宣称支持底层并不存在的能力。

### P0-4：来源追踪必须连接原子需求，而不只是规则卡

当前 Document Block 的 `source_refs` 主要描述规则卡和配置项。但已经有一套独立的需求原子化系统，因此实际应形成这样的追溯关系：

原始资料 → 原子需求（`HZ-F-001`、`HZ-F-002`）→ 结构化规则（`HJ-F-ZHUANGXIAN-BEILV`）→ Document Block（`DOC-HZ-OPENING-003`）

这样未来才能回答：

- 原文这项需求最终写进了哪一段？
- 这段文字由哪些规则卡组成？
- 这张规则卡覆盖了哪些原子需求？
- 修改某个原子需求后，哪些文档段落需要重新生成？

建议 Document Block 增加：

```json
{
  "requirement_refs": ["HZ-F-001", "HZ-F-002"],
  "rule_refs": ["HJ-F-ZHUANGXIAN-BEILV"],
  "config_refs": [],
  "source_evidence_refs": []
}
```

四种引用各司其职，不要混在一个 `source_refs` 里。

还有一点：`provenance.json` 和 `document.json` 都包含来源关系，需要明确一个是事实源，另一个是索引或派生产物，避免两份数据被分别修改后产生不一致。

### P0-5：Document Block 的 ID 设计还不够稳定

当前 AD-22 写的是「`block_id` 用稳定编号（章节 + 序号）」。这个设计有隐患。

例如 `DOC-XS-OPENING-003`，假设以后用户要求把这个段落从开局章节移动到结算章节，那么：

- 原来的 `block_id` 是否改变？
- 原来的人工修改记录是否还能关联？
- 原来的对话引用是否还有效？

如果 ID 包含章节信息，移动章节就可能导致 ID 变化。

建议：

```json
{
  "block_id": "DOC-XS-000123",
  "section_id": "settlement",
  "segment_id": "SEG-000456",
  "document_version": 3
}
```

规则：

- `block_id` 永久稳定，不随章节移动、文字修改而变化。
- `section_id` 独立维护。
- `segment_id` 用于句子或文本片段级编辑。
- 需要跨变体识别同一逻辑段落时，再增加 `logical_block_id`。

另外，未来对话框如果支持选择段落中的一句话，应该把以下信息一起传给 AI：`block_id`、`segment_id`、`document_version`、`selected_text`、`source_refs`。这样可以避免用户选择的内容已经被重新生成，但 AI 仍然拿旧文本进行修改。

还有一个容易遗漏的地方：`editable` 不应该只有块级控制。例如一个普通段落可能同时包含文字说明和 8 倍、16 倍等规则数值。不能因为它属于 paragraph，就允许 AI 自由修改数值。建议把可编辑性进一步下沉到片段级，数值与公式由确定性数据渲染。

### P0-6：文档编辑层也需要明确的事务和版本控制

目前设计已经规定：规则修改走既有 Proposal；文字表达修改写入 `editorial-overrides.yaml`；章节调整写入章节映射层。

方向没问题，但还需要补一个约束：**三个修改通道都必须经过人工确认，不能让 AI 直接写文件。** 建议复用主需求文档中已经设计的提案、Diff、事务和 Hash 校验机制。

尤其要考虑：假设用户打开文档 V3，选择某个段落发起修改，AI 生成提案的过程中，其他操作已经将文档更新到了 V4。此时不能直接应用基于 V3 的修改。应该检查：

```
proposal.based_on_document_version == current.document_version
```

不一致就要求重新审核或重新生成提案。

## 三、另外两个值得补充的工程问题

### 1. AI 生成的可复现性

FR-37 要求相同输入能够复现相同文档，但 LLM 自然语言生成存在非确定性。

建议 Stage 0 的 `input-manifest.json` 记录：

- 基座与变体版本、内容 Hash
- 原子需求覆盖结果版本
- 文档模板版本
- Prompt 版本
- 模型及版本
- 规则生成器版本

同时明确两种行为：

- 读取历史生成结果：完全复现。
- 重新调用模型生成：不保证文字字节级一致，但结构、规则事实和数值必须通过验证。

AC-30 要求未受影响的章节字节级不变，这一点应通过缓存和依赖 Hash 实现。

### 2. 公式与计算案例

AD-19 已经规定数值、倍数、配置值使用确定性模板渲染。建议再明确：

如果对话要求「帮我补充上一局三牢时，下一局如何计算的案例」，AI 不能自己推算后直接写入正文。应该调用确定性的公式计算逻辑生成案例，再由 AI 组织解释文字。

这样既能补充案例，又不会让数字变成 AI 的自由发挥。

## 四、最终评审结论

对 v1.1 的判断：**架构方向可行，但需要完成上述修订，才能进入正式执行计划。**

建议保留目前的主体结构，不需要推倒重写。具体修改位置：

| 文档位置 | 修改内容 | 优先级 |
| --- | --- | --- |
| 3.1 | 杭州与萧山使用相同章节模板 | P0 |
| 3.2 | 差异来源、规则状态、差异审核拆成独立维度 | P0 |
| 5 | 调整 P0 与上游需求覆盖阶段的关系 | P0 |
| 5、6 | 补充原子需求到 Document Block 的追溯关系 | P0 |
| 6 | 稳定 ID、片段 ID、版本模型 | P0 |
| 7、8 | 编辑提案、版本冲突、事务应用 | P1 |
| 15 | 补充相应架构决策 | P0/P1 |
| 16 | 补充对应验收标准 | P0/P1 |

参考文件：

- 当前全文生成设计 v1.1
- Rule Studio 主需求文档
- 需求覆盖与补齐设计

最想强调的是：**不要把这个功能做成一个 Markdown 生成器，再外挂一个 AI 聊天窗口。** 应该从第一天就把它当作一个有来源追踪、有版本、有差异、有审核机制的需求文档工程系统。这样后面接入对话框时，不需要推翻前面的生成架构。
