## 一、三个文档的定义

| 名称 | 定义 | 来源 |
| --- | --- | --- |
| `base_old` | 上次正式生成的**基座**文档 | `documents/hangzhou/document.json` 的历史快照（`history/vN`） |
| `base_new` | 用当前基座规则重新生成的**基座**文档 | 重新运行 `run-w1` 的产物 |
| `current` | 当前正式**变体**文档 + 人工表达层 | `documents/xiaoshan/document.json` + `editorial-overrides.yaml` |

变体候选文档 `variant_new` = 用 `base_new` 与当前变体规则重跑 `run-w2` 的产物。

**关键前提**：人工表达修改只存在于 `editorial-overrides.yaml`，不写进 `document.json`。因此比较必须**分层**：

```
生成层：document.json         ← 生成器的产物，可比对
表达层：editorial-overrides   ← 人工的产物，优先级最高
```

只比 `document.json` 会漏掉人工改动，只比 override 会漏掉生成变化。两层都要看。

## 二、六个维度的处理

| # | 维度 | 识别方法 | 处理 |
| --- | --- | --- | --- |
| 1 | 生成内容变化 | `base_new` 与 `base_old` 中同一规则（`rule_refs`）的片段文本集合不同 | 受影响的继承片段用新内容替换 |
| 2 | 人工表达修改 | `editorial-overrides.yaml` 中 `segment_id` 命中 | 保留人工文本，**任何情况都不得被生成内容覆盖** |
| 3 | Segment 身份变化 | 片段 id 在 `variant_new` 中不存在 / 新增 | 消失的片段：若有人工修改 → 冲突；无人工修改 → 直接移除 |
| 4 | Block 拆分 / 合并 | 同 `logical_block_id` 下的片段集合变化 | 保守策略：不自动拆合，整块标记需人工确认 |
| 5 | 章节移动 | `section_id` 与 `block_id` 的对应关系变化 | 继承片段的块位置随之移动；变体自有片段位置不变 |
| 6 | 删除 / 隐藏 | 片段在 `base_new` 中不存在，或被标记隐藏 | 有 override → 冲突；无 override → 移除并在报告中列出 |

## 三、三方合并的判定表

对每个片段取三元组 `(old, current, new)`：

| old 存在 | current 有 override | new 存在且不同 | 结论 |
| --- | --- | --- | --- |
| 是 | 否 | 否 | 保持（无变化） |
| 是 | 否 | 是 | 采用 `new` |
| 是 | 是 | 否 | 保留 `current` |
| 是 | 是 | 是 | **冲突**：`conflict(override-vs-regeneration)` |
| 否 | — | 是 | 新增片段，直接采用 `new` |
| 是 | 是 | 否（`new` 中已删除） | **冲突**：`conflict(override-vs-removal)`（人工改过的内容不能被静默删除） |
| 是 | 否 | 否（`new` 中已删除） | 移除 |
| 否 | 是 | 否 | **冲突**：`conflict(orphan-override)`（override 指向已不存在的片段） |

**硬规则**：

1. 双边都变 → 必须报冲突，**禁止**自动取任一边
2. 人工修改优先于生成结果；只有「新生成确实删除/改名了该片段」时才升级为冲突
3. 身份变化导致无法定位人工修改时，不猜：报 `orphan-override`

## 四、冲突报告结构

```json
{
  "conflict_id": "CFL-001",
  "kind": "override-vs-regeneration",
  "segment_id": "SEG-000123",
  "base_rule_ref": "HJ-R-LUNZHUANG",
  "old_text": "…",
  "new_text": "…",
  "override_text": "…",
  "suggested": "keep-override | take-regeneration | manual",
  "section_id": "opening"
}
```

`suggested` 只是建议，UI 必须让人三选一（取左 / 取右 / 手改）。

## 五、增量重生成的执行顺序

```
1. 重跑基座：run-w1 → base_new（升 base document_version）
2. 影响分析：impact(base_old, base_new) → 受影响规则/片段/章节
3. 重跑变体候选：run-w2（绑定 base_new）→ variant_new
4. 三方合并：merge3(base_old, current+overrides, variant_new)
5. 分三类输出：自动采用 / 保留人工 / 冲突
6. 冲突由人在 Web 工作台解决后，再次合并直到 0 冲突
7. 应用新版本：写 document.json + 更新 overrides + 记 audit + 升版本
8. 归档变更包（CHG-xxx）
```

第 3 步之前不得改动 `current`：整个流程在候选产物上进行，最后一步才落盘。

## 六、与既有契约的关系

| 契约 | 用法 |
| --- | --- |
| `Segment.segment_id` | 合并的身份锚点；继承片段跨版本保持不变 |
| `Segment.base_segment_ref` | 变体 modified 片段指向被改写的基座片段，是「哪个基座变化会影响我」的唯一依据 |
| `editorial-overrides.yaml` | 人工层，合并时优先级最高 |
| `document_version` | 每次落盘 +1；合并前后的版本号写进冲突报告，便于回溯 |
| `identity-map.json` | 拆合导致的身份迁移记录，合并时作为辅助（不作为唯一依据） |

## 七、明确不做

| 不做 | 理由 |
| --- | --- |
| 自动语义合并（AI 猜哪边对） | 与「人工修改优先」冲突，且不可回归 |
| 自动拆合 Block | 拆合涉及读者结构，机器判断风险高于收益 |
| 跨变体合并 | 变体之间互不影响，不存在合并场景 |
| 自动升级基座版本 | 必须人工确认（AGENTS.md 第 4 条） |

## 八、W5-1 已实现的部分

`studio/pipeline/impact.ts`：

- `diffBaseDocuments(base_old, base_new)` → 变化规则（新增/移除/修改）、变化片段、受影响章节
- `analyzeVariantImpact(variantDoc, baseImpact)` → 受影响的继承片段、受影响的 modified 片段（按 `base_segment_ref`）、需重查的 added 规则（按依赖）
