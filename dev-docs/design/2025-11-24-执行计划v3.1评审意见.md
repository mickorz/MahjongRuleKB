## 二、P0：三个关键问题

### P0-1 Manifest 和 Config 对财神的定义冲突

杭州 Manifest `scope` 含 `joker: white_dragon`，萧山 Manifest 只声明 `player_count`、`room_type`，按继承规则编译后萧山 Manifest 得到 `joker: white_dragon`。

但萧山 Config 里 `XS-C-JOKER` 标 `status: disputed, release_blocker: true`。

Config 知道财神有争议，Manifest 却把白板财神当无争议有效配置输出。Agent 若优先读 Manifest，会错误理解萧山玩法。

建议：

- Manifest 的 `scope` 只保留规则集适用范围（人数、房间类型）
- 财神、底分、局数等实际玩法参数统一由 `config.yaml` 管理
- 不在 Manifest 和 Config 重复定义同一玩法参数，避免两个事实源

### P0-2 unresolved.md 没有机器可解析的状态

P2-C.7 要求扫描 `unresolved.md`，但当前表格只有「卡 | 处数 | 内容 | release_blocker」，没有 `status`。发布门槛条件是 `release_blocker = true 且 status != confirmed`，编译器无法按统一条件判断未决清单。

建议 unresolved 条目结构：

| 字段 | 含义 |
| --- | --- |
| id | 未决问题 ID |
| card_ref | 关联规则卡 |
| description | 问题描述 |
| status | unresolved / confirmed |
| release_blocker | 是否阻塞发布 |
| resolution | 裁决结果 |

Manifest 争议项也要明确如何表达状态。

### P0-3 编译后引用闭合定义不准确

`base_rule_ref: HJ-R-BANK-02` 和 `compares_to` 不重写是对的，但 `compiled/xiaoshan/` 不含被替换的杭州原始卡，所以这两个字段指向的 ID 在编译产物里找不到。这与「编译后所有规则引用闭合」语义冲突。

建议分两个验证范围：

| 引用 | 验证要求 |
| --- | --- |
| depends_on | 必须在编译后规则集中闭合 |
| 正文依赖引用 | 必须在编译后规则集中闭合 |
| base_rule_ref | 必须在原始基础规则集中存在 |
| compares_to | 必须在原始基础规则集中存在 |

依赖引用要求编译后闭合，溯源引用允许指向原始规则集。`rule-index.json` 保留溯源关系。既保证编译产物独立使用，又不丢继承历史。

## 三、四个实现细节建议

| 问题 | 建议 |
| --- | --- |
| Gold Set 仍保留旧 `status: draft / verified / automated` 描述 | 删旧定义，只保留 `verification.status` 和 `automation.status` |
| inherited 配置项含 `value`，但编译器忽略它 | 要求 `value` 与基础配置一致，或不允许填；争议值用候选字段 |

## 五、最终结论

MahjongRuleKB 已完成最重要的架构收敛。定位：麻将规则的结构化知识库 + 地方麻将差异派生工具 + 可验证的规则数据。不扩张成数据库平台、知识图谱平台或通用麻将引擎。

结合 PrdGameSkill，未来最有价值的接口只有三个：

1. 根据玩法获取完整规则集
2. 根据规则 ID 获取规则及其依赖
3. 根据 Gold Set 验证生成的游戏规则实现

这三个足以支撑 Cocos Creator 杭州麻将 Vertical Slice。

修完 3 个 P0 后正式冻结，开始 Phase 1。不要再做架构评审。现在最重要的是把杭州麻将规则真正结构化出来，让它开始为第一个可玩的游戏服务。
