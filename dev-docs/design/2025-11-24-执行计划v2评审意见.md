# 执行计划 v2 评审意见

> 评审对象：`dev-docs/planning/2025-11-24-执行计划.md`（v2）
> 评审日期：2025-11-24
> 结论：架构方向通过，执行前需修订为 v3。P0 四项可能直接导致编译结果错误。

## 一、总体评价

v2 已落实上一轮核心意见：Phase 2.6 最小编译器、`variants/xiaoshan/` 与 `compiled/xiaoshan/`、`base_rule_ref` 与覆盖范围、4 领域 11 类型、Gold Set 改 YAML 加 Vitest、规则状态四值、`release_blocker`、编译产物入库。

整体方向符合最初需求：杭州麻将作为基础规则，萧山麻将通过差异继承形成一套完整、独立的规则集。

但不建议现在直接执行，v2 还有几个容易导致后期返工的技术细节。

## 二、P0：四个必须修改的问题

### P0-1 基础规则不应标记为 `change_type: added`

Phase 1 规定「杭州卡 change_type 固定为 added，base_rule_ref 留空」，不合理。`added` 的含义是相对于杭州基础规则某地方麻将新增了一条规则；杭州本身就是基础规则，不存在相对于杭州新增的问题。

建议区分 `origin` 和 `change_type`：

杭州规则卡：

```yaml
id: HJ-R-BANK-02
origin: base
type: judgment
name: 连庄与换庄
status: confirmed
```

萧山规则卡：

```yaml
id: XS-R-BANK-02
origin: variant
type: judgment
name: 连庄与换庄
change_type: modified
base_rule_ref: HJ-R-BANK-02
status: confirmed
```

只有萧山差异卡才使用 `inherited` / `modified` / `added`。这样 Zod Schema 和编译器职责更清晰。

### P0-2 `override_scope: full` 与原始差异文档表达方式冲突

萧山文档约定「原文未点名的能力仍按杭麻，本文不另写」，本质是差异文档。但萧山卡中的「杭麻」槽只是比较信息，不代表萧山卡已包含杭州规则的所有有效内容。

例如一条杭州规则有触发条件、前置条件、特殊情况、处理结果、例外情况，萧山可能只改其中两个。直接整卡替换，其他未修改的内容会丢失。

建议第一阶段只支持 `full`，但加强制规范：**所有 `modified` 卡必须整理成完整的萧山有效规则**，而不是差异说明：

1. 保留原始杭州行为作为对照信息
2. 把杭州未修改的必要条件补入萧山有效规则
3. 修改的条件采用萧山规则
4. 最终卡片不依赖杭州原文就能独立理解

同时删除 MVP 中的 `override_scope: slots`、`override_slots: []` 和 `override.test.ts`。风险章节已明确第一阶段只实现 `full`，就不要在 Schema、测试和任务里同时保留尚未实现的 `slots`。某张卡无法整理成完整规则时，再单独讨论槽位级继承。

### P0-3 编译器遗漏配置合并

Phase 2.6.1 写「读取 rulesets 和 variants 下全部卡与 config」，但 2.6.2 的合并算法只描述规则卡，没说配置怎么合并。

麻将关键参数（底分、局数、人数、财神、封顶、禁杠张数、拖底额度）如果不合并，生成的萧山规则集就不完整。

建议配置合并规范：

| 差异类型 | 配置处理 |
| --- | --- |
| inherited | 保留杭州配置 |
| modified | 用萧山配置替换 |
| added | 新增萧山配置 |
| 未提及 | 默认继承杭州配置 |

杭州 `HJ-C-BASE-SCORE value: 1`，萧山 `XS-C-BASE-SCORE value: 1, change_type: modified, base_rule_ref: HJ-C-BASE-SCORE`，最终编译到 `compiled/xiaoshan/config.yaml`。

`manifest.yaml` 也要定义继承语义：杭州 scope 有 `player_count`、`room_type`、`round_count`、`joker`，萧山只声明前两个，编译后应继承未声明的 `round_count` 和 `joker`，而不是丢失。`config.ui.yaml` 第一阶段纯继承。

### P0-4 必须明确规则 ID 在编译后的处理方式

当前编译器设计最大的技术空白。杭州 `HJ-R-BANK-02` 被萧山 `XS-R-BANK-02` 替换后，其他杭州规则可能仍引用 `HJ-R-BANK-02`，编译产物里若已没有它，引用就悬空。

萧山的 `inherited` 卡究竟是再生成一张 XS 卡、还是直接用 HJ 卡、是否保留对应关系，目前都没定。

建议增加**有效规则 ID 映射表**：

| 差异 | 编译后处理 |
| --- | --- |
| 未提及 | 使用 HJ 原规则 |
| inherited | 使用 HJ 原规则，保留 XS 对应关系 |
| modified | 使用 XS 修改后的规则，建立 HJ → XS 映射 |
| added | 直接加入 XS 新规则 |

```json
{
  "rule_aliases": {
    "HJ-R-BANK-02": "XS-R-BANK-02",
    "XS-R-BANK-01": "HJ-R-BANK-01"
  }
}
```

可存放在编译报告或独立 `rule-index.json`。编译时需要：生成映射 → 解析规则间引用 → 被替换规则的引用解析到最终有效规则 → 检查所有有效规则的引用都能找到目标。

**特别增加测试：编译后所有规则引用必须闭合。**

## 三、P1：四处需要调整

### P1-5 未决项数量统计错误

计划声称 16 处，表格相加只有 15 处。A-GZ 应为 2 处不是 1 处：「加庄」字和骰子的停留时长、四家飘分是同时播放还是只飘首出者，是两个独立问题。

### P1-6 Gold Set 需要玩法标识

当前 Gold Set 只用 `rule_refs` 区分，但 Gold Set 要同时验证杭州和萧山。建议增加 `ruleset_id`：

```yaml
- id: TC-F-BANK-001
  ruleset_id: hangzhou-friends-4p
  rule_refs: [HJ-F-BANK]
```

```yaml
- id: TC-F-BANK-002
  ruleset_id: xiaoshan-friends-4p
  rule_refs: [XS-F-BANK]
```

细节：杭州庄闲倍率固定 8，萧山是 2^牢数。只测三牢两边都是 8 倍，无法证明差异规则生效。测试必须包含二牢、四牢等能体现差异的边界值。

建议增加 `schemas/gold-set.ts`，不只验证 Rule ID，还要校验 Gold Set 自身的输入和预期输出结构。

### P1-7 Phase 3 自动化验收标准不一致

计划写「四个确定性计算函数各有 calc 测试覆盖 Gold Set 全部 P0 用例」，但 P0 是庄闲倍率、承包赔付、拖底分配；跟庄赔付对应的是 P1。

建议改为：所有 P0 Gold Set 必须有自动化测试；四个确定性计算函数都必须有对应测试；跟庄赔付覆盖全部相关的跟庄 Gold Set；未决规则不允许提前标记 `verified`。

### P1-8 必填槽位校验机制没定义清楚

Phase 1 写「校验 ID 唯一、引用闭合、必填槽位、config 可解析」，但 `schemas/rule.ts` 只描述 YAML 元数据，规则内容在 Markdown 正文。

建议增加 `schemas/slot-definitions.ts`，按 11 种类型定义必须出现的槽位。例如判定类：

```ts
const judgmentSlots = ["差异", "杭麻", "触发", "条件", "否则", "结果", "验收"];
```

校验脚本检查 Markdown 正文是否包含对应槽位。否则必填槽位校验最后只检查了 YAML，没检查规则内容完整性。

## 四、固定编译器处理流程

避免后续开发 Agent 自己理解编译逻辑，建议在 Phase 2.6 明确执行顺序：

**麻将规则派生编译流程**

1. 加载基础规则 `rulesets/hangzhou/`
2. 加载地方差异 `variants/xiaoshan/`
3. 确定性合并：
   1. 校验基础版本锁定
   2. 建立规则 ID 映射
   3. 处理继承、修改、新增
   4. 合并玩法配置
   5. 合并 Manifest 作用域
   6. 解析并检查规则引用
   7. 检查未决项和发布阻塞
4. 输出完整规则集 `compiled/xiaoshan/`
5. 自动校验 + Gold Set：验证完整性、引用闭合、计算正确性

编译器只负责确定性的数据处理，不让 LLM 在编译过程中重新理解和决定规则。

## 五、编号问题

Phase 2 任务 2.6（翻财神归属裁决）与 Phase 2.6（最小规则编译器）编号冲突，执行 Agent 容易混淆。建议调整 Phase 2 任务编号，或给编译阶段用独立编号如 `P2-C.1`。

## 七、最终结论

可以进入执行准备，但先修订 v3。这套计划已从「整理麻将规则文档」进化成规则知识库工程，具备三个核心能力：基础规则标准化、地方玩法派生、规则质量验证。未来增加桐庐、绍兴、淳安、余杭等地方麻将时，理论上只需增加对应 `variants/`。

第一阶段最终验收只看五件事：

1. 杭州规则卡完整，能够独立读取
2. 萧山差异卡全部有明确的继承关系
3. 一条命令生成完整萧山规则集
4. 编译后的规则不依赖原始杭州文档，所有引用闭合
5. 核心 Gold Set 验证通过，未决问题不会被误认为已确认

不要在这一阶段增加数据库、MCP、LLM Wiki 或 Web 管理界面。

先把上述修改合并成 v3，然后停止架构讨论，正式执行 Phase 0～Phase 3。
