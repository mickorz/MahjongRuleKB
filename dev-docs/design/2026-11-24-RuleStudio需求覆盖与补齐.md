## 一、方向调整的结论

上一轮的设计方向是「泛化的知识库质量审计工具」（检查规则卡是否结构完整、引用是否闭合）。这个方向**不够**：它只能证明「已有的卡写得合规」，回答不了「原文里的要求有没有漏掉」。

真正需要的是 **需求补齐（Requirement Completion）**：

> 原始麻将规则已经被拆成几十张规则卡，但拆分结果可能不完整。系统需要对照原始资料与现有规则文件，明确指出哪些需求没有被提取、哪些规则描述不完整，以及应该往哪个文件补什么内容。

重点不是报错，而是给出**可以直接执行的补齐任务**。

> 定位澄清：这不是与规则结构化并列的第二条开发线路。两条线从同一份原文出发、产物不同、在覆盖分析处汇合，且需求必须独立从原文提取（见下一节与 I-21）。

### 与 Schema 校验的本质区别

| 维度 | Schema / Validator 校验 | 需求覆盖与补齐 |
| --- | --- | --- |
| 检查对象 | 规则卡自身的结构与引用 | 原始资料里的每条要求，是否在规则库里落地 |
| 事实源 | Schema 定义 | 原始资料 + 规则卡正文语义 |
| 输出 | 通过 / 报错列表 | 六态覆盖判定 + 补齐任务（写什么、写进哪个文件、怎么验收） |
| 能发现 | 缺槽位、引用悬空、编译失败 | 原文有要求但规则库没有 / 只写了一半 / 原文本身没给 |

## 二、两条支线：规则原子与需求原子的分工

这一功能**不是**与规则结构化并列的另一条开发线路。两者从同一份原始资料出发，产物与目的不同，最后在覆盖分析处汇合：

- **A 线（规则结构化，已有，主线基础设施）**：把原始资料转成规则卡、配置项、未决项。
- **B 线（需求原子化，新增，质量检查层）**：把原始资料拆成可追踪的最小需求单元，用来验证 A 线的结果有没有遗漏。

两条线都涉及「原子化」，但原子化的**对象不同**：

| 对比 | 规则原子化（A 线，已有） | 需求原子化（B 线，新增） |
| --- | --- | --- |
| 拆解对象 | 规则行为 | 原始资料中的要求 |
| 拆解依据 | 业务逻辑与规则类型（11 类槽位） | 原文段落、表格行、条件分支 |
| 产物 | 规则卡、配置项、未决项 | 原子需求清单 |
| ID 示例 | `HJ-R-CHENGBAO`、`HJ-F-ZHUANGXIAN-BEILV` | `HZ-R-001`、`HZ-F-001` |
| 目的 | 让规则可查询、可编译、可复用 | 让每项原始要求都能被追踪与验收 |
| 解决的问题 | 规则如何组织 | 有没有漏掉规则 |

### 举例（原文 2.3.3 自摸一行）

> 闲家自摸时，庄家一笔乘 8，另两个闲家各乘 1。

- **规则原子化**：写成 `HJ-F-ZHUANGXIAN-BEILV`（庄闲倍率）里的完整计算规则。
- **需求原子化**：拆成 `HZ-F-001`（闲家自摸时庄家一笔乘 8）、`HZ-F-002`（另两名闲家各乘 1）。

两条需求都映射到同一张规则卡。所以 A 与 B 之间是**多对多**关系，不是一对一。

### 必须坚持的原则（否则功能失效）

**B 线必须独立从 `sources/` 提取需求，不能从 A 线已生成的规则卡反向拆需求。**

理由很直接：如果某一要求被 A 线漏掉了，从规则卡反推出来的需求清单也会跟着漏掉，于是「覆盖分析」永远报不出这个遗漏 —— 功能等于自证清白。

同理，覆盖判定只能**拿需求去查规则库**，不能**拿规则卡去生成需求**。

### 分工与优先级结论

结构化是基础设施，需求覆盖与补齐是质量保障。当前不应继续投入扩展结构化能力，而应把精力转向覆盖与补齐（见下节）。

## 三、开发优先级

| 优先级 | 功能 | 决策 |
| --- | --- | --- |
| P0 | 现有规则结构化体系（11 类槽位、Schema、Validator、Compiler、杭州 61 卡、萧山 47 卡） | **保持，不重做** |
| P1 | 原子需求拆解（直接读 `sources/`） | 新增 |
| P2 | 需求与规则卡 / 配置项映射（多对多） | 新增 |
| P3 | 覆盖状态分析（六态） | 新增 |
| P4 | 补齐建议生成（明确目标文件与内容要点） | 新增 |
| P5 | 补齐转提案 | 复用既有提案机制，不新建 |

为什么这样排：现在已经有 61 张杭州卡、25 项杭州配置（20 玩法 + 5 界面）、47 张萧山卡、Schema / Validator / Compiler、章节级 `coverage.md`。**缺的不是结构化工具，而是证明这些产物完整覆盖了原始资料的手段**。继续扩展结构化能力不会让「完整性」变得可证明。

## 四、现状：已有的基础与真正缺的东西

仓库现有四类基础设施：

| 现有文件或能力 | 已解决 | 尚未解决 |
| --- | --- | --- |
| `sources/` | 保存原始规则资料 | 没有原子需求清单 |
| `rulesets/hangzhou/coverage.md` | 记录原始章节对应哪些规则卡 | 不知道每个具体要求是否被完整提取 |
| `variants/xiaoshan/unresolved.yaml` | 记录原文的冲突与缺失 | 不能反映「提取遗漏」这一类问题 |
| `compiler/validator.ts`、`compiler/compile.ts` | 结构、引用、依赖、编译 | 不检查语义覆盖率 |

### 关键缺口：`coverage.md` 粒度不够

现状（实测，`coverage.md` 2.3.3 节）：

```text
#### 2.3.3 算分规则

| 表行 | 对应卡 |
| --- | --- |
| 每笔原应赔分 | `HJ-F-YUANYING-PEIFEN`、`HJ-F-ZHUANGXIAN-BEILV` |
| 自摸 | `HJ-P-ZIMO-RUZHANG` |
| 点炮胡、抢杠胡 | `HJ-P-DIANPAO-RUZHANG`、`HJ-P-QIANGGANG-RUZHANG` |
| 三摊承包、倒承包 | `HJ-P-CHENGBAO-RUZHANG` |
| 链式承包 | `HJ-P-CHENGBAO-RUZHANG` |
| 黄庄与记账 | `HJ-P-HUANGZHUANG` |
```

这只说明「整个算分章节映射到了若干张卡」，回答不了：

- 原文中每个计算公式是否都提取了？
- 每种结算方式是否都覆盖？
- 承包、反承包、链式承包是否分别覆盖？
- 每个特殊条件是否提取？
- 每个异常分支是否有描述？

点炮胡、抢杠胡、三摊承包、链式承包各自含多个独立计算条件。漏掉其中一个，章节映射仍然「看起来完整」。

另一个结构性障碍：规则卡的 `sources` 只有来源文件与章节号（如 `section: "{{IP_pc74fgkjq6}}"`），**没有精确到原文段落的需求 ID**，所以系统无法自动判断遗漏。

### 所以真正缺的是

1. **原子需求清单**（原文 → 可独立检查的需求点，带原文定位）
2. **原子需求与规则文件的逐项映射**（需求 → 卡 / 配置项 / 未决项）
3. **六态覆盖判定**（区分「我们漏了」与「原文没给」）

## 五、核心流程

```mermaid
flowchart TB
    SRC[原始资料 sources 唯一事实依据]
    SRC --> A[规则结构化 已有]
    SRC --> B[需求原子化 新增]
    A --> KB[规则知识库 卡 配置 未决项]
    B --> REQ[需求登记表 需求 ID 原文证据 位置]
    KB --> COV[需求覆盖分析]
    REQ --> COV
    COV --> GAP[缺口与补齐任务]
    GAP --> PROP[提案 到 Diff 到门禁 到人工确认 到应用]
    PROP --> KB
```

### 3.1 原子需求拆解

原文示例（杭州 2.3.3）：

> 三名对手各算一笔原应赔分。庄家自摸时，三个闲家的应赔分都乘 8；闲家自摸时，庄家一笔乘 8，另两个闲家各乘 1。

**不能**整段标成一条需求，应拆成：

| 需求 ID | 原子需求 |
| --- | --- |
| `HZ-F-001` | 自摸时三名对手分别计算赔付 |
| `HZ-F-002` | 庄家自摸时，三个闲家赔付倍率均为 8 |
| `HZ-F-003` | 闲家自摸时，庄家赔付倍率为 8 |
| `HZ-F-004` | 闲家自摸时，另外两名闲家赔付倍率为 1 |

规则：

- 原文表格的**一行可能拆成多个需求**；多个需求也可能**共同落在同一张卡**里（不要求一对一）。
- 需求 ID 形如 `HZ-<类型字母>-<序号>`（`HZ` = 杭州；萧山用 `XS`），类型字母与规则卡同一套（R/T/N/M/F/K/P/V/I/A）。
- 每条需求必须带**原文定位**：文件、章节号、行范围或表格行标识。

### 3.2 六态覆盖模型

| 状态 | 含义 | 应采取的行动 |
| --- | --- | --- |
| 已覆盖 | 已有规则完整表达原文要求 | 不处理 |
| 部分覆盖 | 有规则，但条件、分支或细节不完整 | 补充原规则卡 |
| 提取缺失 | 原文有明确要求，规则库没有对应内容 | 新增规则卡或配置项 |
| 原文缺失 | 原始资料本身没给必要信息 | 创建未决项，交规则方裁决 |
| 原文冲突 | 不同来源或章节互相矛盾 | 提交人工裁决 |
| 明确排除 | 明确不属于本期范围 | 不补充，记录排除依据 |

**这个区分是整个功能的地基**：

- `variants/xiaoshan/unresolved.yaml` 的 `XS-U-002`（飘财第 3 次及以上的豪杠飘倍数原文未给，表里只有飘 1 次、飘 2 次两列）属于**原文缺失**。它不能被判成「AI 提取遗漏」，更不能让 AI 自己编一个倍数。
- 杭州原文明确写了、却没进规则卡的，才是**提取缺失**。

两类问题必须分开处理，且「原文缺失 / 原文冲突」不产出补齐内容，只产出未决项。

## 六、输出物：需求补齐清单（不是普通审计报告）

### 4.1 汇总

示意数据（非本次对仓库的实际统计）：

| 指标 | 示意值 |
| --- | --- |
| 原子需求 | 120 |
| 已覆盖 | 100 |

### 4.2 单条缺口必须回答六件事

| # | 内容 | 说明 |
| --- | --- | --- |
| 1 | 缺了什么 | 一句话，落到具体条件或分支 |
| 2 | 为什么判定缺失 | 六态中哪一态 + 判定理由 |
| 3 | 原始资料依据 | 文件 + 章节 + 段落/表格行的原文摘录 |
| 4 | 应该补充什么内容 | 具体到触发条件、计算基数、付款方、入账结果等槽位 |
| 5 | 应该修改哪个文件 | 现有卡则给路径 + 槽位；需新建则给建议 ID、类型、依赖 |
| 6 | 补充完成后如何验收 | 可执行的验收条件（能构造的计算用例 / 能通过的校验项） |

缺口示例（示意）：

- `HZ-F-005`｜**部分覆盖**｜原文 2.3.3 算分规则｜目标文件 `jiesuan/hj-p-chengbao-ruzhang.md`｜问题：某项结算条件未在卡中明确表达｜建议补充：触发条件、计算基数、付款方、入账结果｜验收：能据补充内容构造正常与特殊场景的计算用例。
- `HZ-R-006`｜**提取缺失**｜原文某章节某段｜建议新建规则卡，给出建议 ID、类型、`depends_on`、`sources`。
- `HZ-U-007`｜**原文缺失**｜不生成规则内容，写入 `unresolved.yaml` 待规则方裁决。

### 4.3 必须支持「按目标文件分组」

这是本功能能落地的关键——策划要知道下一步改哪几个文件，而不是自己重读几十张卡：

```text
需要修改的文件
  1. jiesuan/hj-p-chengbao-ruzhang.md
     - 补充 HZ-F-005
     - 补充 HZ-F-008
  2. guize/hj-r-gang-bupai.md
     - 补充 HZ-R-012

需要新建的文件
  3. guize/hj-r-xxx.md
     - 新增 HZ-R-020

需要人工裁决
  4. unresolved.yaml
     - HZ-U-007
```

## 七、与现有 Rule Studio 的复用关系

不另起系统。现有模块已经覆盖大部分基础：

| 现有模块 | 本功能如何使用 |
| --- | --- |
| 原始资料读取（`sources/`） | 读取原文与段落定位 |
| 规则仓库（`rulesets/`、`variants/`、`compiled/`） | 读取拆分后的规则卡与配置项 |
| Parser（`parser/`） | 解析规则结构与槽位 |
| 提案引擎 | 把补齐任务转成提案 |
| 质量门禁 | 检查修改后的规则 |
| 事务写入 | 人工授权后应用 |

需要新增的核心模块只有一个：

### Requirement Analyzer（需求分析与覆盖引擎）

| 能力（工具名按 B 阶段的工具命名规范） | 作用 |
| --- | --- |
| `mahjong_extract_requirements` | 把指定原文片段拆成原子需求，带定位与证据 |
| `mahjong_analyze_coverage` | 原子需求 × 规则库逐项匹配，产出六态 |
| `mahjong_list_gaps` | 列出部分覆盖 / 提取缺失 / 原文待确认 |
| `mahjong_suggest_completion` | 生成具体补齐建议（含目标文件与验收条件） |

补齐的落地仍然走既有链路：`mahjong_propose_change` → Diff → 人工确认 → 门禁 G1-G4 → 应用。

UI 在右侧「规则」面板加一个「需求补齐」入口，三个部分：

1. **需求清单**：按原始章节查看全部原子需求与覆盖状态
2. **缺口详情**：原文、当前规则文件、遗漏内容、补充建议
3. **补齐提案**：按文件生成 Diff，人工审核后应用

## 八、硬约束

| # | 约束 |
| --- | --- |
| I-15 | 原子需求必须带原文定位（文件 + 章节 + 段落/表格行），没有定位的需求不算需求 |
| I-16 | 六态判定必须显式记录理由；「原文缺失」「原文冲突」不得产出补齐内容，只能产出未决项 |
| I-17 | 不得由 AI 编造原文没有的数值、倍率或条件；缺就是缺，写进 `unresolved.yaml` 等裁决 |
| I-18 | 本功能不修改 Schema、不修改编译器语义、不引入新数据库；需求登记表与覆盖状态存为 Rule Studio 的运行时数据（与提案同层） |
| I-19 | 补齐提案必须过既有门禁并通过人工确认才可写入；本功能自身不具备写盘能力 |
| I-20 | 「章节已映射」不等于「需求已覆盖」：覆盖判定必须到原子需求粒度，不得用 `coverage.md` 的章节映射结果直接顶替 |
| I-21 | **B 线必须独立从 `sources/` 提取需求**：不得从规则卡、配置项或 `coverage.md` 反推需求；否则 A 线漏掉的项会在需求清单里一并漏掉，覆盖分析永远无法发现遗漏 |

## 九、功能需求

| # | 需求 |
| --- | --- |
| FR-21 | 能把指定范围（先杭州）的原始资料拆成原子需求清单，每条带 ID、原文定位、原文摘录、所属章节 |
| FR-22 | 每条原子需求可关联一个或多个规则卡 / 配置项 / 未决项，形成双向映射 |
| FR-23 | 能对每条需求判定六态之一并记录理由 |
| FR-24 | 能按状态、章节、目标文件三个维度筛选与分组 |
| FR-25 | 能生成单条缺口的六要素描述（缺口、理由、依据、补什么、改哪个文件、怎么验收） |
| FR-26 | 能把一条或多条缺口转成提案（复用提案机制），并按目标文件分组展示 Diff |
| FR-27 | 覆盖状态随规则变更失效并重新判定：规则卡内容变化后，其关联需求的判定标记为待复核 |
| FR-28 | 需求登记表可增量维护：新拆出的需求追加，不得覆盖已有需求的判定历史 |

## 十、架构决策

| # | 决策 | 理由 |
| --- | --- | --- |
| AD-10 | 需求登记表存为 Rule Studio 运行时数据（`<kb>/.rule-studio/requirements/`），不进知识库主结构 | 需求拆解会随讨论反复调整，不适合混进已冻结的规则仓库结构；且不改变 Schema |
| AD-11 | 需求 ID 与规则 ID 分开（`HZ-F-001` vs `HJ-P-ZIMO-RUZHANG`） | 一条需求可能落到多张卡，也可能暂时没有卡；两者不是一对一 |
| AD-12 | 拆分与判定由 Agent 完成，但结果必须落盘为结构化记录 | 避免「每次问一遍 AI」造成的判定漂移；落盘后可比对、可追溯 |
| AD-13 | 原文定位用「文件 + 章节号 + 段落/表格行」而非行号快照 | 原文会改；章节号与表格行标识比绝对行号稳定 |
| AD-14 | **规则原子与需求原子分离**：规则原子（卡、配置项）属知识库正式数据；需求原子属 Rule Studio 追溯数据；两者 ID 独立；两者多对多映射；需求原子从原始资料独立提取，不从规则卡生成；补齐后重新计算覆盖状态 | 新增质量保障能力不得反向破坏已冻结的知识库架构，也不能让需求清单成为规则卡的影子 |

## 十四、类比理解

- **Schema 校验**像验房时量尺寸：墙是不是直的、门能不能关上。全合格，也不代表图纸上的房间都在。
- **需求覆盖与补齐**像拿原始图纸逐间对房：图纸上写了要有个储藏间，房子里没有 —— 这才是要报的问题，而且要写清「加在哪面墙、怎么验收能住人」。
- **六态模型**的关键在于分清两种「没有」：图纸上有、你没盖（**提取缺失**，该补）；图纸上根本没画（**原文缺失**，该问设计师，不能自己画一间）。
- **两条支线的分工**像「按图纸施工」与「拿图纸验收」：施工队不能拿自己盖的房子当验收基准，否则自己漏盖的房间永远查不出来（I-21）；这也是为什么需求必须直接从图纸抄，不能从房子反推。
