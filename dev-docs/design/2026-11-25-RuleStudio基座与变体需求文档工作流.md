# 一、项目背景

## 1.1 当前问题

MahjongRuleKB 已经完成杭州麻将基座规则结构化，以及萧山麻将差异规则结构化。

当前知识库具有以下内容：

- 杭州麻将基座规则卡。
- 杭州麻将基座配置项。
- 萧山麻将继承规则。
- 萧山麻将修改规则。
- 萧山麻将新增规则。
- 各规则的来源资料、依赖关系和未决事项。
- 规则编译器与变体验证能力。

现有系统已经具备将结构化规则编译为有效规则集的能力，也已经建立需求全文生成所需的 Document Block、Segment、Provenance、Proposal 和 Transaction 等基础契约。

但当前需求文档生成和审查方式仍存在产品层面的不足。

### 问题一：规则卡转文档不等于生成完整需求文档

规则卡通常按照规则类型组织。

例如：

- 定庄规则。
- 发牌规则。
- 摸牌规则。
- 出牌规则。
- 胡牌规则。
- 结算规则。

策划人员阅读需求文档时，通常希望按照完整的游戏流程理解系统，而不是按照规则卡的分类逐张阅读。

因此，需要 AI 根据结构化规则之间的关系，重新组织章节和内容，形成完整、连贯、可交付的需求文档。

### 问题二：基座和变体的维护权限需要明确

杭州麻将是基座，萧山、绍兴、桐庐、淳安等地方麻将是基于基座派生的变体。

策划日常工作主要是维护地方麻将与杭州麻将之间的差异。

不应该允许策划在维护萧山需求时，顺手修改杭州基座内容。

否则会产生：

- 萧山修改污染杭州基座。
- 多个变体之间互相影响。
- 基座升级后无法判断变体依赖的版本。
- 人工修改被后续生成流程覆盖。

### 问题三：需求审查不能变成逐条审批

当前差异生成存在大量片段处于 `candidate` 状态的问题。

如果让策划逐条确认每一个差异片段，随着文档规模增长，人工成本会迅速增加。

策划实际可能一次性修改大量内容，包括：

- 重写章节。
- 补充规则说明。
- 修改业务流程。
- 增加结算示例。
- 调整段落顺序。
- 修正 AI 生成的表达。
- 补充原有规则卡没有表达清楚的内容。

因此，需求审查必须支持大规模修改，不能将每个段落都设计成独立审批任务。

## 1.2 产品定位

Rule Studio 的需求文档能力定位为：

**AI 需求文档生成引擎 + 基座与变体管理 + Web 策划审查编辑工作台。**

核心原则：

1. 基座统一维护。
2. 变体独立维护差异。
3. 完整需求文档自动生成。
4. 策划通过 Web 页面阅读和编辑。
5. 所有修改保留来源和版本记录。
6. AI 不得擅自改变结构化规则事实。
7. 重新生成不能覆盖人工修改。
8. 基座升级必须进行变体影响分析。

# 二、核心业务原则

## 2.1 基座需求是权威基准

杭州麻将是当前知识库的基座。

基座需求文档由杭州结构化规则、配置和未决事项生成。

普通策划在日常变体维护过程中：

- 可以阅读基座需求。
- 可以查看基座规则来源。
- 可以查看基座与变体的差异。
- 不允许直接修改基座需求正文。
- 不允许通过 AI 对话绕过基座保护。
- 不允许通过 Markdown 编辑器绕过基座保护。

如果发现杭州基座需求存在问题，必须重新进入基座生成流程。

基座修改流程：

1. 修改杭州原始资料或结构化规则。
2. 执行杭州规则 Schema 和 Validator 检查。
3. 执行杭州规则编译及相关测试。
4. 重新运行杭州需求文档生成 Pipeline。
5. 生成新的 Base Document 版本。
6. 检查下游变体的影响。
7. 对受影响的变体执行增量重新生成。
8. 对冲突和无法自动合并的内容进行人工处理。

不允许通过编辑萧山文档反向修改杭州基座。

## 2.2 变体只维护自己的差异

以萧山麻将为例。

萧山完整需求文档由杭州基座与萧山差异组成。

逻辑关系：

```
杭州麻将基座需求
        |
        v
   Base Document
        |
        |
        +-----------------------+
        |                       |
        v                       v
  萧山差异规则              萧山配置差异
        |                       |
        +-----------+-----------+
                    |
                    v
             AI 变体文档生成
                    |
                    v
             萧山完整需求文档
```

策划可以阅读完整的萧山需求文档，但只能修改萧山拥有的内容。

## 2.3 内容归属和编辑权限分离

每个文档块和片段必须明确自己的来源归属。

| 内容归属               | 说明        | 普通策划权限 |
| ------------------ | --------- | ------ |
| base               | 杭州基座内容    | 只读     |
| explicit_inherited | 显式继承的杭州内容 | 只读     |
| default_inherited  | 默认继承的杭州内容 | 只读     |
| modified           | 萧山修改的内容   | 可编辑    |
| added              | 萧山新增的内容   | 可编辑    |

需要注意：

`modified` 内容是萧山最终生效的完整规则表达，而不只是修改差异的几句话。

文档可以通过差异高亮展示它与杭州基座的区别。

## 2.4 规则事实和文档表达分离

策划修改内容时，需要识别修改性质。

| 修改类型 | 示例          | 处理方式       |
| ---- | ----------- | ---------- |
| 表达修改 | 调整语句、优化描述   | 文档人工修改     |
| 结构修改 | 调整章节、移动段落   | 文档结构修改     |
| 补充说明 | 增加操作示例、补充说明 | 文档人工修改     |
| 规则修改 | 修改胡牌条件、结算倍率 | 更新变体结构化规则  |
| 基座修改 | 修改杭州通用规则    | 进入基座重新生成流程 |

规则事实修改不能只保存在文档表达层。

否则会产生文档与实际规则知识库不一致的问题。

# 三、产品使用场景

## S1：生成杭州基座需求文档

用户选择杭州麻将。

系统：

1. 读取杭州结构化规则。
2. 读取杭州配置。
3. 读取杭州未决事项。
4. 读取相关原始资料作为来源证据。
5. 编译有效规则集。
6. 通过 AI 组织章节和内容。
7. 生成完整需求文档。
8. 执行机器质量检查。
9. 输出基座需求文档。

基座生成后进入受保护状态。

## S2：生成萧山完整需求文档

用户选择萧山麻将。

系统：

1. 读取杭州基座需求文档及其版本。
2. 读取萧山结构化差异规则。
3. 编译萧山有效规则集。
4. 将萧山规则映射到统一章节结构。
5. AI 生成萧山变体内容。
6. 继承杭州未变化的内容。
7. 整合萧山修改与新增内容。
8. 生成完整萧山需求文档。
9. 展示与杭州基座的差异。
10. 执行完整性和一致性检查。

最终产物是一份完整的萧山需求文档，而不是一份只有差异内容的报告。

## S3：策划审查萧山需求

策划打开本地 Web 工作台。

可以：

- 浏览完整需求文档。
- 查看章节目录。
- 阅读继承内容。
- 查看修改和新增内容。
- 查看差异高亮。
- 查看对应规则卡。
- 查看配置项。
- 查看原始资料。
- 查看未决事项。
- 直接修改允许编辑的差异内容。

继承内容显示为只读。

## S4：策划批量修改需求

策划发现第三章、第四章、第五章存在大量表达问题。

可以：

- 使用富文本编辑器修改。
- 使用 Markdown 编辑器批量修改。
- 通过 AI 对话要求重写多个章节。

系统将修改统一转换成结构化文档变更。

不要求策划逐段创建审批任务。

保存时保留修改前后内容和来源关系。

## S5：策划发现基座规则错误

策划发现萧山继承的杭州规则本身有错误。

系统不能允许直接修改杭州继承片段。

应提示：

当前内容属于杭州基座，不能在萧山变体中直接修改。

如果只是萧山玩法不同，可以创建萧山 modified 规则。

如果杭州基座本身有误，需要修改杭州结构化规则并重新运行基座生成流程。

## S6：杭州基座升级

杭州基座从 V1 升级到 V2。

系统分析萧山当前依赖的基座版本。

找出：

- 直接受影响的继承规则。
- 受影响的 modified 规则。
- 受影响的章节。
- 受影响的文档片段。
- 可能产生冲突的人工修改。

未受影响的萧山人工修改应当保留。

不能直接覆盖整个萧山文档。

## S7：多个变体独立维护

后续增加：

- 绍兴麻将。
- 桐庐麻将。
- 淳安麻将。

各变体独立保存自己的差异。

共享杭州基座，但不互相污染。

每个变体记录自己的 Base Revision。

# 四、AI 需求文档生成系统

## 4.1 生成原则

选择 AI 生成完整需求文档的方案。

AI 不再仅仅把规则卡槽位展开为 Markdown 列表。

AI 需要理解规则之间的关系，并按照实际游戏流程组织需求。

例如：

输入：

- 定庄规则。
- 发牌规则。
- 摸牌规则。
- 出牌规则。
- 胡牌规则。
- 结算规则。

输出：

```
第一章 游戏概述
第二章 游戏流程
第三章 开局与发牌
第四章 摸牌与出牌
第五章 吃碰杠规则
第六章 胡牌规则
第七章 特殊玩法
第八章 结算规则
第九章 流局处理
第十章 房间流程
```

具体章节由 DocumentOutline 决定，不强制固定为上述示例。

## 4.2 AI 生成 Pipeline

```
Stage 0：输入版本锁定
        |
        v
Stage 1：编译有效规则集
        |
        v
Stage 2：AI 需求章节规划
        |
        v
Stage 3：AI 章节内容生成
        |
        v
Stage 4：Document Block 装配
        |
        v
Stage 5：来源、差异与身份标注
        |
        v
Stage 6：机器质量检查
        |
        v
Stage 7：生成完整需求文档
        |
        v
Stage 8：Web 审查工作台
```

### Stage 0：输入版本锁定

锁定：

- ruleset_id。
- ruleset_version。
- manifest.content_hash。
- Base Document Version。
- 配置文件 Hash。
- 未决事项版本。
- DocumentOutline 版本。
- 生成使用的模型和 Prompt 版本。

生成过程中输入发生变化，应拒绝继续使用混合版本。

### Stage 1：编译有效规则集

调用现有 Compiler。

杭州：

读取杭州基座规则和配置。

萧山：

读取杭州基座，应用萧山继承、修改、新增规则和配置。

不重新实现规则合并逻辑。

生成阶段只消费经过校验的有效规则集。

### Stage 2：AI 需求章节规划

AI 根据有效规则集和 DocumentOutline：

- 理解规则之间的依赖。
- 识别游戏流程。
- 识别规则所属章节。
- 识别跨章节引用。
- 规划内容组织顺序。
- 识别需要组合表达的规则。

DocumentOutline 是章节装配输入。

AI 可以提出大纲调整建议，但不得绕过 Outline 的保存和权限机制。

### Stage 3：AI 章节内容生成

AI 按章节生成完整内容。

要求：

1. 将相关规则整合为自然、连贯的业务描述。
2. 保留必要的触发条件、前置条件、处理过程和结果。
3. 保留规则边界和例外情况。
4. 将配置项转成明确的参数说明。
5. 对复杂流程使用表格或步骤说明。
6. 对结算规则生成公式说明。
7. 对复杂规则增加具体示例。
8. 不得擅自增加结构化规则中不存在的业务事实。
9. 不确定内容必须明确标记。
10. 每个重要内容必须有对应来源引用。

### Stage 4：Document Block 装配

将 AI 生成的内容转换为 Document Block 和 Segment。

Document Block 是底层结构化文档模型。

它不等于用户界面中的需求卡片。

一个 Block 可以包含多个 Segment。

多个规则卡可以共同支撑一个 Block。

一个规则卡也可以被多个 Block 引用。

保持 block_id、segment_id 和 logical_block_id 的稳定身份关系。

### Stage 5：来源和差异标注

每个 Segment 必须维护：

- lineage。
- decision_status。
- diff_status。
- rule_refs。
- config_refs。
- source_evidence_refs。
- 可选 requirement_refs。

`requirement_refs` 继续保持可选。

本工作流不执行原子需求提取，不创建 Requirement Registry。

变体文档需要明确展示：

- 继承内容。
- 修改内容。
- 新增内容。
- 默认继承内容。
- 未决内容。

### Stage 6：机器质量检查

检查内容：

**规则与配置覆盖**

所有适用规则卡和配置项必须有文档落点。

**来源追踪**

重要内容必须能够追溯到规则卡、配置项或原始证据。

**规则一致性**

不得出现与结构化规则冲突的描述。

**变体差异检查**

检查：

- modified 是否丢失基座必要约束。
- added 是否疑似重复基座规则。
- lineage 与 base_rule_ref 是否一致。
- 差异是否正确映射到文档。
- 继承内容是否被错误修改。

**数值和公式检查**

数值与公式不能由 AI 自由编造。

必须使用确定性计算器或可信规则数据。

**未决事项检查**

未决规则必须明确标记，不得自动变成已确认规则。

检查失败时生成机器可读报告，不得伪装成完整通过。

### Stage 7：生成完整需求文档

生成：

- `document.json`
- `document-outline.yaml`
- `需求全文.md`
- `provenance.json`
- `identity-map.json`
- `editorial-overrides.yaml`
- `history/`

P1 阶段生成 `changes.json`。

其中：

- document.json 是结构和身份唯一事实源。
- document-outline.yaml 是章节装配输入。
- editorial-overrides.yaml 是人工表达修改的权威输入。
- provenance.json 和 identity-map.json 是可重建索引。
- 需求全文.md 是渲染产物。

# 五、基座与变体文档管理

## 5.1 基座文档

杭州基座需求文档：

- 由杭州结构化规则生成。
- 作为所有变体的共同基准。
- 普通策划只读。
- 不允许通过编辑器直接写入。
- 不允许 AI 对话直接改写。
- 修改必须重新运行基座生成 Pipeline。

基座重新生成后，产生新的 document_version。

## 5.2 变体文档

变体文档必须绑定：

- base_ruleset_version。
- base_ruleset_content_hash。
- base_document_version。
- variant_ruleset_version。
- variant_ruleset_content_hash。

变体文档是完整文档。

它不是仅包含差异的增量文件。

但其内容归属必须明确。

继承内容与基座保持关联；变体修改内容和新增内容由变体独立维护。

## 5.3 变体内容权限

| lineage            | 阅读 | 编辑 | 修改后的落点           |
| ------------------ | -- | -- | ---------------- |
| base               | 是  | 否  | 基座生成流程           |
| explicit_inherited | 是  | 否  | 基座或转为变体 modified |
| default_inherited  | 是  | 否  | 基座或转为变体 modified |
| modified           | 是  | 是  | 当前变体             |
| added              | 是  | 是  | 当前变体             |

如果策划希望修改一条继承规则：

必须先明确修改是地方玩法差异还是基座错误。

地方玩法差异：创建 modified。

基座错误：进入基座修改和重新生成流程。

## 5.4 变体修改完整性

modified 规则必须保存完整的最终规则内容。

不能只保存：

```
萧山与杭州不同，增加一个限制。
```

而必须保存完整的萧山规则定义，以及基座对应规则引用。

文档生成时应呈现完整的萧山规则，同时标出与杭州不同的部分。

## 5.5 多变体扩展

后续每个变体都有自己的：

- 结构化规则。
- 配置差异。
- Document。
- DocumentOutline。
- 人工表达修改。
- 版本历史。
- 审查记录。

多个变体可以共用基座，但不直接共用彼此的修改。

# 六、Web 策划工作台

## 6.1 产品定位

Web 工作台是需求文档的主要人工审查和编辑入口。

部署方式：

- 本地运行。
- 浏览器访问 localhost。
- 第一阶段单人使用。
- 不建设多人在线协作系统。

技术路线遵循现有技术路线对比：先建设稳定的 CLI/领域内核，再叠加本地 Web 工作台。

不重新引入 PiBot 作为宿主依赖。

## 6.2 页面布局

建议采用三栏结构。

```
+-------------------+--------------------------+-------------------+
| 左侧文档导航       | 中间需求文档             | 右侧信息面板       |
|                   |                          |                   |
| 杭州麻将           | 第三章 开局与发牌         | 内容来源           |
|   第一章           |                          |                   |
|   第二章           | 3.1 定庄规则              | HJ-R-DINGZHUANG   |
|   第三章           |                          |                   |
|                   | 游戏开始后……             | 关联配置           |
| 萧山麻将           |                          |                   |
|   第一章           | 3.2 发牌流程              | 差异信息           |
|   第二章           |                          |                   |
|   第三章           | ……                       | 审查记录           |
+-------------------+--------------------------+-------------------+
```

### 左侧：文档导航

支持：

- 杭州基座和变体切换。
- 章节目录。
- 章节定位。
- 搜索。
- 章节状态。
- 差异数量统计。

### 中间：完整需求文档

支持：

- 阅读。
- 章节折叠。
- 内容搜索。
- 差异高亮。
- 直接编辑允许修改的内容。
- 查看修改历史。
- 保存编辑。
- 查看机器检查结果。

### 右侧：关联信息

支持：

- 规则卡详情。
- 配置项详情。
- 原始资料引用。
- 基座对应内容。
- 变体差异说明。
- 未决事项。
- 机器检查告警。
- 修改历史。

## 6.3 差异显示

变体文档必须提供差异阅读能力。

建议提供：

**完整模式**

展示萧山最终生效的完整需求文档。

**差异模式**

只展示与杭州基座不同的内容。

**对照模式**

并排展示杭州基座和萧山变体。

修改内容应能够定位到对应的杭州基座内容。

## 6.4 编辑权限显示

继承内容：

- 显示锁定标记。
- 禁止输入。
- 禁止删除。
- 禁止 AI 改写。
- 可以查看来源和关联规则。

变体差异：

- 显示可编辑标记。
- 允许直接修改。
- 允许 AI 修改。
- 允许 Markdown 修改。
- 保存后保留版本记录。

# 七、三种编辑方式

本项目确定需要具备 A/B/C 三种编辑能力，但暂不确定哪种作为唯一主编辑器。

三种方式必须操作同一份文档数据。

## 7.1 A：富文本编辑

面向日常策划。

支持：

- 段落编辑。
- 标题调整。
- 表格编辑。
- 列表编辑。
- 文字格式。
- 内容移动。
- 内容插入。
- 内容删除。
- 差异高亮。
- 只读区域保护。

## 7.2 B：Markdown 编辑

面向熟悉 Markdown 的策划和技术人员。

支持：

- Markdown 源码编辑。
- 实时预览。
- 批量修改。
- 表格编辑。
- 章节调整。
- 多段内容修改。

必须保护继承内容。

不能因为 Markdown 编辑器可以修改全文，就允许策划绕过内容权限。

## 7.3 C：AI 对话编辑

面向复杂修改。

例如：

```
把萧山麻将第三章重新组织一下。

要求：
1. 先介绍庄家确定规则。
2. 再介绍发牌流程。
3. 补充开局异常情况。
4. 保留原有结算规则。
5. 不要修改杭州基座内容。
```

AI 必须：

1. 识别修改目标。
2. 检查目标是否允许编辑。
3. 读取相关规则和来源。
4. 生成修改提案。
5. 展示修改前后 Diff。
6. 通过 Schema 和 Validator 检查。
7. 等待用户应用。
8. 通过 Transaction 保存。

AI 不允许直接写入正式文档文件。

## 7.4 统一编辑模型

三种编辑方式不能拥有独立文档副本。

```
富文本编辑器
      |
Markdown 编辑器
      |
AI 对话编辑
      |
      v
统一文档变更层
      |
      v
Proposal
      |
      v
Diff / Validator
      |
      v
UI Apply
      |
      v
Transaction
      |
      v
document.json / editorial-overrides.yaml
```

同一个修改结果必须能够在三种模式之间正确显示。

三种模式的具体技术选型和第一阶段优先级留待后续技术评审。

# 八、策划审查机制

## 8.1 不采用强制逐段确认

不要求策划逐个确认所有 Segment。

不要求每个差异片段都产生独立审批任务。

不要求所有继承内容重新审查。

机器检查通过也不代表人工已经审查。

## 8.2 审查粒度保持灵活

系统应支持：

- 文档级审查。
- 章节级审查。
- 具体内容定位和问题记录。

但不在第一阶段强制采用某一种固定审查粒度。

推荐初始方案：

- 文档级：记录整体审查状态。
- 章节级：可选记录审查进度。
- 段落级：用于定位修改、查看历史和记录问题，不强制逐段确认。

先通过实际策划使用验证哪种粒度最合适。

## 8.3 审查与编辑分离

编辑一个段落不代表完成审查。

审查一个章节不意味着不能继续修改。

修改完成后，可以重新进入审查状态。

系统应分别记录：

- 编辑状态。
- 机器检查状态。
- 人工审查状态。
- 最终文档版本。

不要让 `diff_status` 同时承担机器检查、差异识别和人工审查三种职责。

## 8.4 差异确认机制

差异确认必要性分析提出的 R1、R2、R3 检查应保留为候选质量检查：

R1：modified 是否丢失基座规则约束。

R2：added 是否疑似重复基座规则。

R3：lineage、base_rule_ref、change_type 是否自洽。

这些检查可以产生明确告警。

不需要为了形式而要求所有 229 个片段逐个确认。

但不能在没有证据的情况下，把机器检查通过直接解释为策划已经确认。

机器检查和人工审查必须是独立状态。

R2 相似度阈值、R1 不适用声明以及历史人工裁决继承规则，仍需独立评审。

# 九、人工修改与数据保存

## 9.1 修改分类

所有编辑操作需要被分类。

| 类型   | 内容        | 数据落点                                 |
| ---- | --------- | ------------------------------------ |
| 表达修改 | 调整措辞、说明   | editorial-overrides.yaml             |
| 结构修改 | 章节、段落组织   | document-outline.yaml 或对应结构 Proposal |
| 规则修改 | 玩法条件、结算逻辑 | rulebook/specs/variants/             |
| 基座修改 | 杭州通用规则    | 基座规则文件及重新生成流程                        |
| 补充说明 | 变体特有的需求说明 | 当前变体的文档人工修改层                         |

## 9.2 保存机制

用户希望获得接近在线文档的编辑体验。

系统应支持编辑草稿自动保存。

但必须区分：

**草稿保存**

保存未正式应用的编辑状态，不直接修改正式文档事实源。

**正式应用**

由用户明确触发 UI Apply。

系统：

1. 创建或更新 Proposal。
2. 读取 baseRevision。
3. 校验 document_version。
4. 校验目标文件 Hash。
5. 取得写入锁。
6. 通过 Transaction 原子提交。
7. 更新 document_version。
8. 保存历史记录。
9. 更新相关索引。

不得让普通 Agent 或文件工具绕过 Transaction。

## 9.3 批量修改

一次编辑会话可以包含多处修改。

例如：

策划一次性修改第三章 15 处、第四章 10 处。

系统不应该生成 25 个独立的人工审批页面。

应该支持一个编辑会话形成一组修改，再统一展示 Diff 和应用。

底层仍可以按 Proposal 记录具体修改对象，但交互上应支持批量操作。

## 9.4 历史记录

记录：

- 修改前内容。
- 修改后内容。
- 修改对象。
- 变体 ID。
- 原始来源引用。
- 变更原因。
- 创建时间。
- 应用时间。
- Proposal ID。
- Transaction ID。
- 对应文档版本。

支持查看历史版本和回滚。

# 十、基座升级与变体增量重新生成

这是系统必须解决的核心问题。

## 10.1 基座升级

假设：

杭州 Base V1 → Base V2。

系统必须能够分析：

- 哪些规则发生变化。
- 哪些变体继承了这些规则。
- 哪些 modified 规则依赖这些基座规则。
- 哪些 Document Block 引用了受影响规则。
- 哪些 Segment 需要重新生成。
- 哪些章节需要重新审查。

## 10.2 变体影响分类

| 影响类型              | 系统处理             |
| ----------------- | ---------------- |
| 未受影响的继承内容         | 保持不变             |
| 受影响的继承内容          | 重新生成             |
| 受影响的 modified 内容  | 标记冲突，要求人工检查      |
| 不受影响的 modified 内容 | 保留               |
| added 内容          | 保留，重新检查依赖        |
| 人工表达修改            | 尽可能保留，检查是否与新基座冲突 |

## 10.3 不允许覆盖人工修改

增量重新生成必须比较：

- 当前文档。
- 上次生成文档。
- 新生成文档。

识别：

1. 仅生成内容发生变化。
2. 仅人工修改发生变化。
3. 生成和人工修改同时变化。

第三种属于冲突。

不能直接采用 AI 新生成内容覆盖策划修改。

必须形成冲突报告，交给策划处理。

## 10.4 变体基座版本锁定

每个变体必须记录自己的基座版本。

不能因为杭州基座升级，就自动把所有变体升级到最新版本。

必须通过明确的升级流程完成：

- 影响分析。
- 重新生成。
- 差异检查。
- 人工处理冲突。
- 应用新版本。

# 十一、数据模型与文件职责

继续沿用 D0 冻结的数据契约。

| 文件                       | 职责                       | 是否允许人工编辑                  |
| ------------------------ | ------------------------ | ------------------------- |
| document.json            | Block、Segment、身份、版本唯一事实源 | 仅授权字段由受控事务维护              |
| document-outline.yaml    | 章节装配输入                   | 允许受控修改                    |
| editorial-overrides.yaml | 人工表达修改                   | 通过 Proposal / Transaction |
| provenance.json          | 来源追踪索引                   | 否，自动生成                    |
| identity-map.json        | 身份映射索引                   | 否，自动生成                    |
| changes.json             | 变体差异索引                   | 否，自动生成                    |
| 需求全文.md                  | 最终渲染产物                   | 不直接作为事实源                  |
| history/                 | 历史快照                     | 系统维护                      |

具体存储路径以 D0 冻结的 I-51 路径权限矩阵和后续 K0 路径注册表为准。

不得重新发明一套文件写入权限。

## 11.1 文档版本

基座文档：

- 独立 document_version。
- 绑定杭州规则版本。
- 绑定杭州规则内容 Hash。

变体文档：

- 独立 document_version。
- 绑定自己的规则集版本。
- 绑定基座版本。
- 绑定基座文档版本。

每次正式 Stage 生成或 Transaction 应用成功后，按冻结契约维护版本。

# 十二、安全与权限要求

## 12.1 基座保护

普通变体编辑上下文中：

- Base Block 只读。
- Base Segment 只读。
- Base Outline 不允许修改。
- Base 文档不允许普通编辑器写入。
- AI 不允许修改基座内容。

## 12.2 变体隔离

萧山 Proposal 只能写入萧山允许的目标。

不能写入杭州基座。

不能写入绍兴、桐庐等其他变体。

## 12.3 Agent 权限

Agent 可以：

- 读取规则。
- 阅读完整文档。
- 查询来源。
- 生成文档 Proposal。
- 生成变体修改 Proposal。
- 生成 Diff。
- 执行允许的质量检查。

Agent 不允许：

- 直接写 documents/。
- 直接修改 rulebook/specs/。
- 直接修改基座。
- 绕过 UI Apply。
- 绕过 Transaction。

## 12.4 路径安全

所有目标文件由服务端路径注册表推导。

必须拒绝：

- 绝对路径。
- `..` 路径逃逸。
- 符号链接逃逸。
- 跨变体写入。
- 不在白名单内的文件写入。

# 十四、验收标准

## AC-01：杭州基座生成

输入杭州有效结构化规则与配置。

能够生成一份完整需求文档。

文档按业务流程组织，而不是简单按照规则卡类型逐条拼接。

## AC-02：杭州基座保护

普通策划尝试通过富文本、Markdown、AI 对话修改杭州基座内容。

系统必须拒绝正式写入。

## AC-03：萧山完整文档生成

输入杭州基座和萧山差异。

输出完整萧山需求文档。

继承内容、修改内容和新增内容均有明确标记。

## AC-04：差异编辑

策划能够直接修改萧山 modified 和 added 内容。

修改不能影响杭州基座。

## AC-05：继承内容只读

策划尝试修改继承内容。

系统阻止修改，并提供两种正确处理方向：

- 创建当前变体的 modified 内容。
- 进入基座修改流程。

## AC-06：来源追踪

任意重要需求内容可以定位：

- 对应规则卡。
- 对应配置项。
- 原始证据。
- 基座对应内容。

## AC-07：多种编辑模式

同一文档可以由富文本、Markdown、AI 对话三种方式访问和修改。

所有模式使用统一的数据模型。

不同模式之间不能产生互相覆盖的独立副本。

## AC-08：批量修改

策划一次性修改多个章节。

系统可以统一展示修改 Diff、执行检查并保存。

不强制逐段审批。

## AC-09：人工修改保护

AI 重新生成时，不能直接覆盖已有人工修改。

发生冲突时必须输出冲突信息。

## AC-10：基座升级

杭州基座升级后，系统能够定位受影响的萧山规则、Block、Segment 和章节。

未受影响的人工修改必须保留。

## AC-11：版本追踪

每份变体文档都能够明确追溯其基座版本和变体版本。

## AC-12：质量检查

所有适用规则和配置均有文档落点。

公式和数值经过确定性检查。

未决事项不得被 AI 自动裁决。

# 十五、非功能需求与明确非目标

## 15.1 非功能需求

- 本地运行，浏览器访问 localhost。
- 第一阶段单人使用。
- 规则知识库 Markdown/YAML 保持唯一事实源。
- 生成结果必须可重复检查。
- 所有正式修改可追溯。
- 失败事务可以恢复。
- 大型文档支持分章节生成和增量处理。
- AI 生成过程需要能够观察阶段进度、输入输出和错误。
- 模型输出必须通过 Schema 和业务 Validator。
- 关键操作不得只依赖 Prompt 约束。

## 15.2 非目标

本阶段不建设：

- 多人在线协作。
- 账号体系和复杂 RBAC。
- 云数据库。
- 向量数据库。
- 独立通用知识图谱。
- 自动 Git Commit / Push。
- 通用 Agent 工作流平台。
- 原子需求提取与 Requirement Registry。
- 对基座继承内容的自由编辑。
- 逐段强制人工签核。
- 无人工确认的基座自动升级。
- AI 自动裁决未决规则。

# 十六、实施阶段建议

本节是产品实现建议，不替代现有执行计划。

## 阶段 0：底层契约与安全基础

沿用已冻结的 D0 和 K0。

- Document Block / Segment。
- Proposal / Transaction。
- 路径注册表。
- 权限矩阵。
- Artifact Graph。
- ID 生命周期。
- 契约测试。

不重新设计 D0 已冻结内容。

## 阶段 1：杭州基座 AI 文档生成

目标：真正生成完整需求文档。

交付：

- 输入版本锁定。
- 有效规则集读取。
- AI 章节规划。
- AI 章节生成。
- Document Block 装配。
- 来源追踪。
- 机器质量检查。
- Markdown 渲染。

验收重点：生成结果不再只是规则卡槽位展开。

## 阶段 2：萧山变体完整文档

目标：形成基座 + 差异的完整变体需求文档。

交付：

- 基座版本绑定。
- 差异规则整合。
- 继承内容只读。
- modified / added 内容可识别。
- 完整文档渲染。
- 基座与变体对照。

## 阶段 3：本地 Web 阅读与编辑工作台

目标：策划能够实际使用。

交付：

- 三栏文档界面。
- 完整文档阅读。
- 目录导航。
- 差异高亮。
- 来源侧栏。
- 变体编辑权限。
- 修改历史。

富文本、Markdown、AI 对话三种编辑方式保持统一接口，具体开发顺序通过技术评审确定。

## 阶段 4：批量编辑与审查机制

目标：支持策划大量修改需求。

交付：

- 批量修改。
- 自动保存草稿。
- Proposal / Diff。
- Transaction 应用。
- 文档级和可选章节级审查。
- 机器质量检查。
- 修改历史与回滚。

审查粒度通过真实使用验证，不提前固化逐段审批机制。

## 阶段 5：基座升级和变体增量生成

目标：解决长期维护问题。

交付：

- 基座升级影响分析。
- 变体锁定版本升级。
- 增量重新生成。
- 人工修改保护。
- 冲突识别。
- 人工冲突解决。
- 多变体独立维护。

# 十八、最终产品定义

Rule Studio 不应被建设成一个要求策划逐张确认规则卡的审批系统。

它应该是一个以完整需求文档为中心的策划工作台。

最终工作方式：

```
                杭州结构化规则
                       |
                       v
               AI 生成杭州基座文档
                       |
                       v
                杭州基座需求文档
                  （受保护）
                       |
                       |
            +----------+----------+
            |          |          |
            v          v          v
          萧山       绍兴       桐庐
          差异       差异       差异
            |          |          |
            v          v          v
        AI 生成完整变体需求文档
            |          |          |
            v          v          v
        Web 策划审查与编辑工作台
            |          |          |
            v          v          v
        人工修改、差异维护、历史记录
            |          |          |
            +----------+----------+
                       |
                       v
                规则与文档一致性检查
                       |
                       v
                完整需求文档交付
```

核心原则：

**基座统一维护，变体独立编辑，完整文档自动生成，人工修改受到保护。**

杭州基座负责提供统一规则基准。

地方变体只维护自己的玩法差异。

AI 负责把结构化规则组织成策划能够理解和使用的完整需求文档。

Web 工作台负责让策划方便地阅读、修改、审查和维护这些需求。

最终目标不是生成更多需求卡片，而是让策划真正获得一套可长期维护、可追溯、可迭代的完整游戏需求文档生产系统。
