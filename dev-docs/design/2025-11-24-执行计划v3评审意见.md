# 执行计划 v3 评审意见

> 评审对象：`dev-docs/planning/2025-11-24-执行计划.md`（v3）
> 评审日期：2025-11-24
> 结论：v3 已正确吸收上一轮全部架构评审意见（4 P0 + 6 P1）。本轮发现的是更深层的、可能影响规则编译结果和后续 PrdGameSkill 使用的问题。建议小幅修订为 v3.1，不重新设计架构。

## 一、总体评价

上一轮关键变化已全部落实：

- 杭州基础卡 `origin: base`，萧山差异卡 `origin: variant`
- `modified` 必须是完整有效规则卡
- 删除槽位级覆盖，MVP 只支持整卡替换
- 配置、Manifest 有明确继承机制
- 新增 `rule-index.json` 和编译后引用闭合检查
- Gold Set 增加 `ruleset_id` 和 Schema
- 新增 11 种类型的必填槽位定义
- 编译任务改为 `P2-C.*`

## 二、P0：三个技术问题

### P0-1 全仓库 ID 唯一检查会与编译产物冲突

`rule-ids.test.ts` 要求「全仓库 ID 唯一」，但目录设计中存在同一规则在不同数据集中的副本：

| 目录 | 内容 |
| --- | --- |
| `rulesets/hangzhou/` | 杭州原始结构化规则 |
| `compiled/hangzhou/` | 杭州编译产物，纯 pass-through |
| `variants/xiaoshan/` | 萧山差异卡 |
| `compiled/xiaoshan/` | 完整萧山规则集，包含继承的杭州卡 |

`HJ-R-BANK-01` 会同时存在于 `rulesets/hangzhou/`、`compiled/hangzhou/`、`compiled/xiaoshan/`。这不是 ID 冲突，是同一规则在不同数据集中的副本。全仓库唯一检查必然失败。

建议改为分数据集检查：

```
rulesets/hangzhou/   内部 ID 唯一
variants/xiaoshan/   内部 ID 唯一
compiled/hangzhou/   内部 ID 唯一
compiled/xiaoshan/   内部 ID 唯一
```

不跨原始数据集和编译产物检查唯一性。

### P0-2 `base_rule_ref` 不能参与普通引用重写

计划写「解析规则卡正文和 `base_rule_ref` 里的所有 ID 引用，按映射表重写为最终有效 ID」。逻辑错误：

```
id: XS-R-BANK-02
base_rule_ref: HJ-R-BANK-02
change_type: modified
```

映射 `{"HJ-R-BANK-02": "XS-R-BANK-02"}`。若连 `base_rule_ref` 一起重写，变成 `base_rule_ref: XS-R-BANK-02`，自引用，丢失原始继承关系。萧山卡的「杭麻」槽也是历史对照信息，不应被替换成萧山规则 ID。

建议区分引用类型：

| 引用类型 | 编译处理 |
| --- | --- |
| `base_rule_ref` | 永远保留原始 ID |
| 对照引用 `compares_to` | 保留原始 ID |
| 规则依赖 `depends_on` | 根据 `rule_aliases` 重写 |
| 最终有效规则引用 | 指向编译后的有效规则 |

在元数据里明确区分引用类型，不对 Markdown 正文里的所有 ID 做无差别替换。这关系到以后追溯某条萧山规则从哪条杭州规则演化而来。

### P0-3 Release Blocker 检查范围不完整

P2-C.7 定义「输出里带 `release_blocker: true` 且 `status != confirmed` 的规则」。但知识库不只有规则卡，还有 `config.yaml`、`manifest.yaml`、`unresolved.md`。

萧山当前三个阻塞来源：

| 问题 | 来源 |
| --- | --- |
| 翻财神归属冲突 | 配置与术语定义 |
| 飘财第三次及以上的豪杠倍数 | K-GANG |
| 十风倍数 | K-FAN |

翻财神问题计划已明确不能让 AI 自行推断，但编译器若只扫描规则卡，可能遗漏配置中的未决状态。

建议统一发布门槛检查：检查规则卡 → 检查配置项 → 检查 Manifest → 检查未决问题 → 汇总所有 `release_blocker` → 存在未解决 blocker 则 `releasable: false`。

Manifest 继承也要注意：不能因为杭州 `joker: white_dragon`，就把萧山有争议的财神定义自动变成已确认的白板财神。可以继续生成临时编译产物，但必须保留 `disputed` 状态，不能将未决配置伪装成确定配置。

## 三、P1：五处完善

### P1-4 Gold Set 的 status 定义存在冲突

当前 `status` 三值：`draft` / `verified` / `automated`。一个用例可能同时人工核对通过且自动化测试通过，但 Schema 只能选一个。最终验收又要求 60 条全部 `verified`，同时要求 P0 有自动化测试。

建议拆成两个独立维度：

```yaml
verification:
  status: verified
automation:
  status: automated
  test_ref: calc-banker-multiplier.test.ts
```

### P1-5 四个计算函数没有明确实现位置

Phase 3 要求庄闲倍率、承包赔付、拖底分配、跟庄赔付都有计算测试，但只有 `tests/regression/calc-*.test.ts`，没有函数放在哪、也没有开发任务。

建议增加：

```
calculators/
  banker-multiplier.ts
  contract.ts
  cap-distribution.ts
  genzhuang.ts
```

不开发完整麻将引擎，只把能确定性计算的公式写成纯函数：`calculateBankerMultiplier(input)` 等。用 Gold Set 验证。这样测试的是真正的计算实现，而不是在测试文件里重写一遍公式。

### P1-6 配置 Schema 示例缺少 origin

计划说「基础配置和差异配置使用同样的 origin / change_type 结构」，但示例没写 `origin`。建议统一：

杭州：

```yaml
- id: HJ-C-BASE-SCORE
  origin: base
  name: 底分
  value: 1
```

萧山：

```yaml
- id: XS-C-BASE-SCORE
  origin: variant
  name: 底分
  value: 1
  change_type: modified
  base_rule_ref: HJ-C-BASE-SCORE
```

同时明确配置 ID 唯一性、引用校验和继承关系。配置表中标注「沿用」的究竟是保留为显式继承项，还是省略后依靠默认继承，需要统一。建议保留显式继承声明便于审计，未点名的才走默认继承。

### P1-7 原始规则分类统计错误

萧山原始文档实际：判定 R 13、时序 T 5、计数 N 2、记录 M 4、公式 F 4、查表 K 3、入账 P 2、静态 V 5、交互 I 5、动效 A 4，总计 47。`需求分析.md` 写 R 12，应为 13。

### P1-8 规则分类和槽位的对应关系需要固定

有 `slot-definitions.ts`，但还需明确：哪些槽位所有规则都必须有、哪些只有差异卡才有、哪些只适用于某种类型、`inherited` 卡是否需要完整填写、`modified` 卡是否需要完整填写。

| 规则类型 | 校验策略 |
| --- | --- |
| base | 对应类型的基础必填槽位 |
| inherited | 检查继承关系和来源，不要求复制基础规则全文 |
| modified | 检查完整有效规则槽位 |
| added | 检查完整有效规则槽位 |

避免为了通过 Schema 大量复制无意义内容。

## 五、执行建议

不要因为这些问题继续无限扩展设计。最重要的是得到一份真正可用的麻将知识库，而不是打造一个复杂的知识库平台。

| 顺序 | 工作 | 重点 |
| --- | --- | --- |
| 1 | 修订 v3.1 | 修复上述问题 |
| 2 | Phase 1 | 完成杭州规则卡 |
| 3 | Phase 2 | 完成萧山差异卡 |
| 4 | Phase 2.6 | 实现最小编译器 |
| 5 | Phase 3 | Gold Set 和计算验证 |
| 6 | Phase 4 | Agent 接入 |

不要把 MahjongRuleKB 做成只服务杭州和萧山的文档仓库。它的价值是「一个麻将规则基础知识库 + 多个地方麻将派生规则集」，未来服务 PrdGameSkill / Cocos Creator 生成策划文档、实现游戏规则、验证游戏行为。

先完成 v3.1 小修订，然后正式冻结架构，开始拆杭州规则卡。不再讨论数据库、MCP、LLM Wiki，不增加新基础设施。
