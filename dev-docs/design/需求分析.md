## 一、需求文档的核心主张

需求文档主张把现有两份 Markdown 升级为「结构化规则知识库 + 规则派生引擎」，分四阶段：

| 阶段 | 目标 | 验收 |
| --- | --- | --- |
| Phase 1 | 建立规则标准（九大分类、数据模型、Rule ID、原始引用） | 杭州和萧山规则都通过 Schema 校验 |
| Phase 2 | 实现规则派生引擎（继承/覆盖/新增/禁用/依赖/冲突/导出） | 编译器生成完整萧山规则 |
| Phase 3 | 规则测试体系（Gold Set） | 派生规则准确 |
| Phase 4 | 接入 Agent（MCP） | 多 Agent 调用 |

技术选型：Markdown + YAML + JSON Schema/Zod + TypeScript 编译器 + Vitest。

## 二、对现有两份文档的实测

### 2.1 萧山文档：已经是可用的差异描述

| 指标 | 数值 |
| --- | --- |
| 规则卡总数 | 47 |
| 分类分布 | R 判定 12、T 时序 5、N 计数 2、M 记录 4、F 公式 4、K 查表 3、P 入账 2、V 静态 5、I 交互 5、A 动效 4 |
| 差异类型 | 新增 23、修改 20、沿用 4 |
| 卡间 ID 引用 | 全部闭合，0 处悬空引用 |
| 「原文未写/未定」 | 16 处 |

**结论：萧山文档的结构化程度已经很高，不需要重做。** 需求文档说它「单独拿出萧山文档不一定能还原全部规则」，这句话本身没错，但这正是差异描述的设计意图，不是缺陷。

### 2.2 杭州文档：完全没有结构化

杭州文档是一份传统 PRD，按「功能详情 → 对局流程 → 结算界面 → 辅助功能」组织。问题：

1. **没有规则 ID**。规则之间靠「见 2.3.2.8」这类章节号引用，改一个章节号全文档失效。
2. **规则和界面描述混在一起**。比如「三摊承包」一节里，承包判定、赔付公式、界面字效三件事写在同一段。
3. **数字参数散落全文**。底分 1、8 局、8 倍、留底 20 张、倒计时 10 秒、长按 500 毫秒——没有一处集中定义。

### 2.3 真正的缺口

需求文档把问题定位在「萧山差异描述不够机器可执行」，但实测后，缺口其实是：

| 缺口 | 影响 | 需求文档是否提及 |
| --- | --- | --- |
| 杭州侧没有结构化，萧山的「沿用/修改」没有明确的锚点 | 萧山说「沿用杭麻」，但杭麻那一侧没有 ID，无法自动核对 | 间接提到（Phase 1 任务 3） |
| 萧山 16 处「原文未写」 | 这些规则在源材料里就是空的，任何格式化都填不上 | 未提及 |
| 两人/三人局、翻财神、片数等附录 A 配置 | 杭州文档明确说「本期不包含」，但萧山用了翻财神 | 未提及 |

## 三、对需求文档各项建议的逐条评估

### 3.1 架构：四层 + 派生引擎

**评估：Phase 1-2 不需要「引擎」，需要「锚点」。**

需求文档的派生流程是：杭州基础规则集 + 萧山差异规则集 → 合并引擎 → 冲突检查 → 完整萧山规则集。

实测的萧山文档里，一张「修改」卡的典型写法是：

```
R-BANK-02 连庄与换庄
- 差异：修改
- 杭麻：胡牌者坐庄。流局由原庄连庄。连庄后仍是三牢、8 倍
- 结果：庄家继续坐庄。掷骰前牢数 = 上一小局实际牢数 + 1
```

这张卡自己已经包含了「杭麻原文」和「萧山结果」两部分。**合并的结果就是这张卡本身**，不需要再去杭州文档里取一遍。只要杭州侧给每条规则补上 ID，萧山的「修改」卡就能指向 `HJ-R-BANK-02`，人工核对即可。

真正的自动化价值在 Phase 3：用测试用例驱动，而不是用合并引擎驱动。

> v2 注：这一段只对「单张修改卡」成立。评审指出：完整萧山规则集 = 杭州 N 条 − 修改的 + 新增的，未提及的默认继承。生成完整规则集需要编译器，已提前到 Phase 2.6。原文保留作为分析过程记录。

### 3.2 差异操作：三种 vs 五种

**评估：保持三种，不扩。**

需求文档建议扩为 inherit / override / add / disable / configure。实测数据：

- 「沿用」4 张，占 9%，作用是显式声明「这条和杭麻一样」，防止遗漏。
- 「禁用」场景：萧山 R-HU-02「补杠不抢」，差异标「修改」，内容是「无抢杠分支，直接完成补杠」。这里用「修改」是对的，因为它不是简单关闭，而是替换了行为。
- 「配置」场景：萧山 1.1 配置表里 7 项，用的是「沿用/新增/修改」+ 独立列「杭麻取值 / 萧山取值」，已经表达了参数变更。

新增两种操作类型带来的收益（区分「关掉」和「改掉」）小于成本（每张卡多一层判断，且和现有 47 张卡不兼容）。

### 3.3 数据模型：15 字段

**评估：方向对，字段太多，Phase 1 砍到 7 个。**

需求文档提议每条规则 15 个字段。萧山文档每张卡按类型只有 5-8 个槽位（判定卡 7 个：差异/杭麻/触发/条件/否则/结果/验收），这是**按类型分槽**而不是**统一 15 字段**，更省。

建议 Phase 1 的最小模型：

| 字段 | 说明 |
| --- | --- |
| `id` | 规则 ID，带类型前缀 |
| `type` | 判定 / 时序 / 计数 / 记录 / 公式 / 查表 / 入账 / 静态 / 交互 / 动效 / 配置 |
| `name` | 中文名 |
| `slots` | 按类型不同的槽位（沿用萧山文档现有写法） |
| `sources` | 原始依据（杭州文档章节号 / 录屏编号） |
| `unresolved` | 原文未写的点（对应萧山 16 处） |
| `tests` | 验收用例 |

### 3.4 目录结构

**评估：Phase 1 不需要 `compiler/`、`compiled/`、`tests/unit` 等目录。**

需求文档的目录有 12 个顶层目录。Phase 1 实际需要的只有：

```
sources/          原始资料（两份文档移进去，不再动）
rulesets/hangzhou/   杭州基础规则（新建，结构化）
variants/xiaoshan/   萧山差异（现有文档移进去）
```

其余目录等 Phase 2/3 真正开始时再建。

### 3.5 技术选型

| 需求文档选型 | 评估 |
| --- | --- |
| Markdown + YAML | 同意。规则本体用 Markdown（人读），元数据用 YAML front matter（机读） |
| JSON Schema / Zod | 同意，但 Phase 1 只校验结构（ID 唯一、引用闭合、必填槽位），不校验语义 |
| TypeScript 编译器 | Phase 2 再说。Phase 1 用一个几十行的校验脚本即可 |
| Vitest + Gold Set | 同意，Phase 3 |
| SQLite / QMD / Neo4j / 向量库 | 同意需求文档的「暂时不需要」 |

## 四、修正后的执行路线

> v2 注：评审后调整——最小规则编译器从 Phase 4 提前到 Phase 2.6，杭州和萧山就是验证派生架构的第一组样本。详见 `dev-docs/planning/2025-11-24-执行计划.md` 与 `dev-docs/design/2025-11-24-执行计划评审意见.md`。

```mermaid
flowchart LR
    P0[Phase 0 固定原始资料] --> P1[Phase 1 杭州规则结构化]
    P1 --> P2[Phase 2 萧山差异结构化]
    P2 --> P26[Phase 2.6 最小规则编译器]
    P26 --> P3[Phase 3 规则测试体系]
    P3 --> P4[Phase 4 Agent 接入]
```

### Phase 0：固定原始资料（半天）

1. 新建 `sources/`，把两份原始文档 `git mv` 进去，重命名为英文文件名。
2. README 和 docs 里的文件引用同步更新。
3. 以后 `sources/` 只读。

### Phase 1：杭州规则结构化（核心，约 3-5 天）

目标：杭州文档从 PRD 变成和萧山同构的规则卡集。

1. **定 ID 规范**：杭州用 `HJ-` 前缀，萧山用 `XS-` 前缀（现有 ID 不带前缀，加前缀是为了避免两个玩法 ID 冲突）。类型前缀沿用萧山的 R/T/N/M/F/K/P/V/I/A。
2. **抽配置表**：把底分、局数、牌数、留底张数、禁杠张数、倒计时、长按时长等数字参数集中到一张配置表。
3. **拆规则卡**：按萧山的十类分槽，把杭州文档 2.3 节（规则详情）和 4.5-4.8 节（行牌、吃碰杠胡、多操作、通用提示）拆成规则卡。界面描述（3.x 节）单独成卡，不混进判定卡。
4. **标注未决项**：杭州文档里的「待确认」（如发牌音效）单独列出。
5. **写校验脚本**：检查 ID 唯一、引用闭合、必填槽位非空。几十行 Node 脚本，放 `dev-examples/`。

验收：杭州文档每个 2.3.x 小节和 4.5-4.8 小节都有对应规则卡；校验脚本通过。

### Phase 2：萧山差异对齐（约 1-2 天）

> v2 注：已扩展为「萧山差异结构化」+ 新增 Phase 2.6「最小规则编译器」，产出 `variants/xiaoshan/` 和 `compiled/xiaoshan/`。详见执行计划。

目标：萧山每张「修改」卡明确指向杭州卡 ID。

1. 给萧山 47 张卡加 `XS-` 前缀。
2. 每张「修改/沿用」卡的「杭麻」槽补充 `HJ-xxx` 引用。
3. 把 16 处「原文未写」汇总成一张未决清单，交给规则方裁决。
4. 处理附录 A 冲突：萧山用了翻财神，杭州正文是白板财神、附录 A 提到翻财神。需要决定翻财神规则的权威来源。

验收：所有「修改/沿用」卡都有有效的 `HJ-` 引用；未决清单有裁决结论。

### Phase 3：测试用例（约 2-3 天）

目标：关键判定和算分有可执行的验收用例。

1. 优先覆盖：庄闲倍率、三摊承包/反承包/链式、番型互斥、杠飘/飘杠、萧山的拖底分配、跟庄。
2. 用例格式：输入（局面状态）→ 期望输出（分数/按钮显隐）。先手写 Markdown 表格，Phase 3 后半段再决定是否转成可执行脚本。
3. 需求文档提到的 Gold Set 如果已有，此时并入。

验收：每个算分公式至少 3 个用例（含边界），每个判定规则至少 1 个正例 1 个反例。

### Phase 4：Agent 接入（按需）

> v2 注：评审后 Phase 4 增加 `AGENTS.md`；`compare_rulesets()` 由 Phase 2.6 的编译报告覆盖。

目标：Agent 能按 ID 查规则、按玩法拉完整规则集。

需求文档列了 7 个接口（get_ruleset / get_rule / get_rule_dependencies / compare_rulesets / compile_variant / validate_ruleset / generate_test_cases）。Phase 1-3 完成后，前 3 个接口用文件读取就能实现，不需要 MCP 服务。等有第二个玩法（桐庐/绍兴）要接入时再做 compare 和 compile。

| 1 | 翻财神规则的权威来源 | A. 杭州附录 A（翻出的牌不参与摸牌，白板按原牌面用）<br>B. 萧山 1.1 配置表（「翻财神：沿用，白板财神」——但萧山术语表又说「本局实际财神 = 翻财神确定的财神」，自相矛盾） | 先找规则方确认萧山到底用不用翻财神 |

| 3 | 杭州规则卡的粒度 | A. 一个 2.3.x 小节一张卡（约 16 张）<br>B. 按行为拆细（约 40-60 张，和萧山同量级） | B，否则萧山的「修改」卡无法一对一对齐 |
| 4 | 是否需要 TypeScript 编译器 | A. Phase 1-2 就建<br>B. Phase 3 用测试驱动，编译器推后 | v1 选 B；评审后改为 A（最小版本，Phase 2.6） |
| 5 | ID 前缀方案 | A. 杭州 `HJ-`、萧山 `XS-`<br>B. 不加前缀，靠目录隔离 | A，跨玩法对比时不用猜 |

## 六、类比理解

把这套知识库想成**菜谱**：

- 杭州文档现在是「一本散文式的菜谱」：红烧肉怎么做、火候多少、用什么锅、盛盘什么样，全混在一段文字里。
- 萧山文档是「一张修改单」：第 3 步糖改成冰糖、第 5 步多加一勺醋、其余照旧。
- 需求文档想建的是「一台自动做菜的机器」：把菜谱和修改单喂进去，自动输出萧山版红烧肉的完整步骤。
- 实际该做的是：**先把散文菜谱拆成编号步骤**（Phase 1），修改单上的「第 3 步」才有地方指向。至于自动做菜机，等有两三个修改单要合并时再考虑。
