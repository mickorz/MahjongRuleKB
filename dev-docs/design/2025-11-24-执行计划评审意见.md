# 执行计划评审意见

> 评审对象：`dev-docs/planning/2025-11-24-执行计划.md`、`dev-docs/design/需求分析.md`
> 评审日期：2025-11-24
> 结论：方向正确，调整后执行。约 80% 方向正确，不重新设计，修改 Phase 2、Phase 3 和验收标准。

## 一、应保留的四个决策

1. **先结构化杭州，再处理萧山**。萧山已有 47 张规则卡，真正的工作是为杭州建立稳定规则 ID。保留 `HJ-` / `XS-` 前缀方案。
2. **保留三种差异类型（沿用/修改/新增），不扩成五种**。差异类型是给人看的分类，规则引用关系是给机器用的结构，两者不能混为一谈。
3. **暂不使用数据库和知识图谱**。保留 Markdown（规则内容）、YAML（元数据和配置）、Node/TypeScript（校验和派生）、Vitest（测试）。
4. **暂不接 MCP，不接 LLM Wiki**。Agent 读取 Markdown 和 YAML 即可。Git 仓库是事实源。

## 二、必须调整的六个地方（按影响排序）

### P0-1 必须增加最小规则派生能力

现计划没有一个阶段真正完成规则派生。《需求分析.md》里「合并的结果就是这张卡本身」只解决了单张修改卡的表达，没解决完整规则集的生成。

例：杭州 100 条规则，萧山修改 20、新增 23、明确沿用 4，其余 53 条未提及（萧山原文规定未点名的能力仍按杭麻）。完整萧山规则 = 100 − 20 + 23 = **103 条**，不是只有 47 张差异卡。

建议增加 **Phase 2.6：规则派生编译**：

- 输入：杭州完整基础规则集、萧山差异规则集
- 处理：加载全部杭州规则 → 默认继承未修改的 → 按 `base_rule_ref` 替换被修改的 → 加入新增规则 → 检查引用、重复覆盖、未决规则 → 输出完整规则集
- 输出：`compiled/xiaoshan/`
- 验收：萧山规则可脱离杭州原始文档独立读取

这是确定性的规则展开合并，不是能执行所有麻将玩法的规则引擎。工作量不大，却能验证整个架构。

### P0-2 必须把原始资料与结构化差异分开

Phase 2 任务「萧山 47 张卡加 XS- 前缀，产出：更新后的 xiaoshan-rules.md」没明确产出路径。如果直接改 `sources/xiaoshan/xiaoshan-rules.md`，就破坏了原始资料只读原则。

建议目录：

```
sources/      原始证据，永不修改
rulesets/     基础规则
variants/     地方麻将差异
compiled/     编译后的完整规则
```

萧山 47 张卡也拆成独立规则文件，与杭州保持相同粒度。

### P0-3 增加机器可识别的继承关系

仅在正文写「杭麻：原本三牢，8 倍」不够，编译器需要明确知道修改的是哪条杭州规则。建议 YAML 元数据：

```yaml
id: XS-R-ZHUANGJIA-02
type: judgment
name: 连庄与换庄
change_type: modified
base_rule_ref: HJ-R-BANK-02
scope: four_player_friend_room
status: confirmed
sources:
  - source: sources/xiaoshan/xiaoshan-rules.md
    section: R-BANK-02
```

| change_type | base_rule_ref | 处理方式 |
| --- | --- | --- |
| inherited | 必须有 | 沿用基础规则 |
| modified | 必须有 | 替换对应规则 |
| added | 不需要 | 新增独立规则 |

补充规范：修改时要明确是覆盖整条规则，还是只覆盖部分槽位（加一个覆盖范围字段，不增加差异类型）。

### P1-4 统一规则分类和配置模型

现有不一致：README 写九类；《需求分析.md》用十种规则卡类型；执行计划又增加 `HJ-C-` 配置类型。萧山原始文档实际是 **4 个一级领域 + 11 个二级分类**（规则：配置/判定/时序；状态：计数/记录；算分：公式/查表/入账分配；界面：静态常显/交互/动效）。

建议统一为 4 + 11。配置项处理：

- 配置项统一存 `config.yaml`，每项有唯一 ID（如 `HJ-C-DIFEN`），不再重复建 Markdown 配置卡
- 其他十种规则类型继续用独立 Markdown 卡
- `turn_timer`、`long_press_ms` 是界面参数，和玩法参数区分存储

技术问题：Node 标准库没有内置 YAML 解析器，「无依赖校验 YAML」做不到。直接用 `yaml`（解析）+ `zod`（校验），不要自己写。

### P1-5 调整 Gold Set 执行方式

现计划矛盾：列出 60 条用例，又规定超过 50 条才考虑转可执行脚本；全部手写 Markdown 却称「可执行验收用例」。

建议区分两类：

A. **Gold Set 数据**，结构化保存：

```yaml
id: TC-F-BANK-001
rule_refs: [HJ-F-ZHUANGXIAN-BEILV]
input:
  banker: true
  win_type: self_draw
  fan_multiplier: 1
  banker_level: 3
expected:
  winner_score: 24
  other_scores: [-8, -8, -8]
status: verified
```

B. **自动化测试**（Vitest）：检查规则 ID 存在、测试引用完整、规则编译结果；对已实现的确定性计算函数做计算验证。不要求第一阶段开发完整麻将模拟器。

如果 Gold Set 只是 Markdown，就应称「人工验收案例」，不是可执行测试。

### P1-6 增加未决规则的发布门槛

现计划允许 16 处未决项里除拖底 3 项外标 `unresolved` 上线。需要更精细：

| 状态 | 说明 |
| --- | --- |
| confirmed | 已确认 |
| inferred | 根据其他资料推导 |
| unresolved | 尚未确定 |
| disputed | 存在冲突 |

增加 `release_blocker: true`。翻财神归属不清可能影响整个财神系统，应阻止完整规则集正式发布；拖底计算公式不清应阻止结算规则发布；某动效停留时间未写可不阻止。

萧山文档存在实际矛盾：配置表写「翻财神沿用白板财神」，术语定义写「本局实际财神由翻财神确定」。不能让 AI 自行推断，应明确设为阻塞项。

## 三、调整后的执行路线

1. **Phase 0**：保留。
2. **Phase 1**：保留并补充 60～80 张杭州规则卡、统一 ID、配置结构化、`manifest.yaml`、来源追溯、结构校验脚本、章节覆盖清单。
3. **Phase 2**：重点调整。萧山加 XS 前缀、建 `variants/xiaoshan`、加 `base_rule_ref`、保留三种差异、整理 16 个未决项、**开发最小规则编译器**、输出 `compiled/xiaoshan`。
4. **Phase 3**：补充自动化。Gold Set 结构化、核心结算用例、关键判定用例、继承和覆盖测试、冲突与未决项测试、回归测试。
5. **Phase 4**：基本保留。文件读取、Rule ID 查询、完整规则集读取、规则差异查询、增加 AGENTS.md 使用规范。MCP 暂不做。

## 六、评审结论

三个真正需要修改的核心问题：

1. 不能只有差异对齐，必须能生成完整萧山规则集
2. 不能只用文字描述继承关系，必须有机器可识别的规则引用和覆盖语义
3. 不能只有人工 Gold Set，必须有结构校验、编译测试和回归验证

第一点不要推迟到桐庐、绍兴接入时才做。杭州和萧山就是验证派生架构的最佳样本。先让 AI 能从杭州基础规则和萧山差异规则稳定生成一份完整萧山规则知识库，通过人工核对和 Gold Set 验证后，再考虑第三种麻将。

操作要求：六项调整合并到当前执行计划，保留原任务编号，重点修改 Phase 2、Phase 3 和验收标准，无需另起架构文档。
