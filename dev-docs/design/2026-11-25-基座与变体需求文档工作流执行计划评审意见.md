## 一、必须修改的 6 个问题（P0）

这些不是优化建议，而是我认为正式执行前必须解决的问题。

### P0-1：diff_status 的语义发生冲突

阻断

位置：W0-3、W2-2，第 124～131、236～247 行

这是我发现的最重要问题。

计划规定：

diff_status 只表示差异识别与机器检查结论，不表示人工已审查。

但是当前仓库的 diff-review.ts 已经明确规定：

- candidate：尚未人工确认。
- confirmed：人工确认差异成立。
- 没有人工确认记录时，modified / added 一律为 candidate。

而 W2-2 又提出：

默认 confirmed，告警才 candidate。

这相当于让机器检查代替人工确认，直接改变现有契约语义。

这也与你的 D0 冻结原则冲突：不能修改既有字段语义。

我的建议：保留 diff_status 原有含义，新增独立的机器检查状态。

例如：

```ts
type DiffStatus =
  | "not_applicable"
  | "candidate"
  | "confirmed";

type MachineCheckStatus =
  | "not_checked"
  | "passed"
  | "warning"
  | "failed";
```

两者职责：

| 字段 | 负责什么 |
| --- | --- |
| diff_status | 差异是否经过人工确认 |
| machine_check_status | 机器检查是否通过 |
| review_status | 策划是否完成文档审查 |

这样三个维度不会互相污染。

参考：现有 diff-review.ts

### P0-2：新增产物没有进入路径注册表

阻断

位置：W0、W1、W2、W5

计划新增了不少文件：

- generation.lock.json
- quality-report.json
- diff-warnings.json
- 差异视图.md
- 对照视图.md
- conflicts.json

但是当前 studio/paths/registry.ts 的 documentFileNames 只有：

- document.json
- document-outline.yaml
- editorial-overrides.yaml
- identity-map.json
- provenance.json
- changes.json
- 需求全文.md

Stage 写入权限也有自己的文件白名单。

因此，按照目前的权限矩阵，计划新增的这些文件不能直接通过现有路径校验。

这不是小问题，等 W1 开始实现才会遇到写入失败。

建议在 W0 增加一个明确任务：文档产物注册表扩展。

我建议不要简单地把所有文件都塞进 documentFileNames，而是区分：

| 产物类别 | 示例 | 生命周期 |
| --- | --- | --- |
| 正式文档 | document.json | 持久化 |
| 人工输入 | editorial-overrides.yaml | 持久化 |
| 生成锁 | generation.lock.json | 版本绑定 |
| 质量报告 | quality-report.json | 每次生成 |
| 差异报告 | diff-warnings.json | 每次检查 |
| 冲突报告 | conflicts.json | 升级期间 |
| 视图文件 | 差异视图.md | 可重建 |

所有产物都必须注册路径、写入主体和权限。

参考：registry.ts

### P0-3：ReviewRecord 的数据结构设计不合理

位置：W0-3，第 124～131 行

当前计划：

```ts
reviewStatusValues = [
  "unreviewed",
  "chapter_reviewed",
  "document_reviewed"
]
```

同时又准备把 reviewStatus 作为 Segment 的可选字段。

这里存在一个结构问题：

Segment 是段落，不能合理地同时表示：

- 章节已审查。
- 整篇文档已审查。

而且产品需求明确希望审查粒度可以变化。

建议：将 ReviewRecord 设计成独立记录，不要把文档级、章节级状态塞进 Segment。

例如：

```ts
interface ReviewRecord {
  review_id: string;

  target: {
    type: "document" | "section" | "segment";
    id: string;
  };

  status: "unreviewed" | "reviewed";

  document_version: number;

  reviewer: string;
  at: string;
  note?: string;
}
```

文档审查状态由对应的 ReviewRecord 汇总。

这样未来增加段落级审查，也不需要修改 Segment 核心契约。

### P0-4：AI 生成接口缺少结构化输出契约

阻断

位置：W1-1、W1-3，第 159～186 行

目前设计：

```ts
generate(request) => {
  text,
  citations
}
```

这个接口太简单了。

AI 最终生成的是章节内容，但是后续需要将内容装配成：

- Document Block
- Segment
- rule_refs
- config_refs
- source_evidence_refs
- logical_block_id

如果 Provider 只返回一段字符串，后面如何确定段落边界、身份、来源和规则归属？

计划没有明确。

我建议增加一个严格的结构化输出契约：

```ts
interface ChapterDraft {
  section_id: string;

  paragraphs: Array<{
    title?: string;
    text: string;

    claims: Array<{
      text: string;
      rule_refs: string[];
      config_refs: string[];
    }>;
  }>;
}
```

这只是建议的数据形状，最终可以用 Zod 定义。

关键要求：

1. 模型输出必须经过 Schema 校验。
2. 不允许模型自行创建规则 ID。
3. 所有引用必须在本次输入锁定的有效规则集中存在。
4. 引用由服务端校验后装配。
5. JSON 不合法允许有限重试。
6. 多次失败必须明确失败，不能偷偷生成不完整文档。
7. 保留原始模型输出、解析错误和重试记录，便于排查。

特别提醒：不要假设所有模型都支持原生 JSON Schema Structured Output。

Provider 应当能够区分模型能力，必要时使用 JSON 解析、校验和修复重试。

另外，考虑到你之前遇到的大型 JSON Schema 执行过程不可观察的问题，我建议在 W1 就增加章节级执行日志：

```
Generation Run
  ├── Input Lock
  ├── Chapter Planning
  ├── Chapter 1
  │     ├── Request
  │     ├── Raw Response
  │     ├── Parse
  │     └── Validation
  ├── Chapter 2
  ├── Chapter 3
  └── Quality Check
```

这不需要现在建设完整 Workflow Dashboard，但必须能够定位具体哪一章生成失败。

### P0-5：数值禁止规则过于严格

位置：W1-3，第 183～186 行

计划规定：

数值片段仍由 calculators 注入，provider 不得产出数值。

我认为这个定义需要调整。

麻将规则中有大量确定性的数值事实：

- 固定局数。
- 摸牌数量。
- 底分。
- 倍率。
- 房间人数。
- 时间限制。
- 规则配置值。

这些不全是计算器的计算结果。

如果完全禁止 AI 输出数值，反而会导致需求文档缺少重要信息。

建议区分：

| 类型 | 处理方式 |
| --- | --- |
| 规则卡中的固定数值 | 可以生成，但必须有来源 |
| 配置中的参数值 | 由结构化配置注入或校验 |
| 公式计算结果 | 必须由 Calculator 计算 |
| AI 自行推断的数值 | 禁止 |

例如：

AI 可以描述「每局固定 8 局」，前提是 8 来自可信规则或配置。

但不能自行推断结算倍率为 8 倍。

这比禁止所有数值合理得多。

### P0-6：继承内容逐字一致与 AI 完整文档生成之间缺少映射方案

位置：W2-4，第 255～261 行

计划要求：

default_inherited / explicit_inherited 的 text 必须与基座对应片段逐字一致。

这个要求有价值：避免变体生成时把杭州规则改写掉。

但这里还缺少一个关键设计：

如何找到变体 Segment 对应的基座 Segment？

目前 Segment 有 base_rule_ref，它指向的是规则卡，不是具体的基座文档段落。

一张规则卡可能拆成多个 Segment。

而 AI 又可能重新组织章节内容。

例如：

杭州：

```
第三章
  3.1 定庄
  3.2 发牌
  3.3 摸牌
```

萧山：

```
第三章
  3.1 开局流程
      定庄
      发牌
      萧山特殊处理
  3.2 摸牌
```

如果 AI 将多个规则整合成一个段落，就无法简单通过 base_rule_ref 判断每个段落是否逐字继承。

建议先明确两种内容的处理方式：

- 真正继承的 Segment：保留基座原文和稳定身份映射。
- modified / added Segment：独立生成，关联对应基座规则。

必要时增加 base_segment_ref，或建立明确的基座 Segment 映射表。

不能只在 W2-4 写一个逐字比较函数，就认为继承关系已经解决。

## 二、另外 5 个重要问题（P1）

这些不一定阻止 W0，但需要在相应阶段开发前补充。

### P1-1：Change ID 与现有契约不兼容

位置：第 87～97 行

计划使用：

```
CHG-2026-11-25-base-variant-workflow
```

但当前 archiveDir() 和 Proposal 契约使用的 Change ID 格式是：

```
CHG-001
CHG-002
```

现有路径函数要求：

```
/^CHG-\d{3}$/
```

因此，计划中的 ID 无法通过现有归档校验。

建议改成：

```
CHG-001
```

归档目录：

```
rulebook/changes/archive/
  2026-11-25-CHG-001/
```

不要为了这个 Change 破坏已经冻结的 ID 契约。

### P1-2：R1 的不适用声明没有数据契约

位置：W2-2，第 236～247 行

R1 规定：

基座卡槽位集合 - 变体卡槽位集合，非空报警，除非显式声明不适用。

但是没有说明：

- 不适用声明放在哪里？
- 是否需要原因？
- 是卡级还是槽位级？
- 是否需要引用原始证据？
- 谁可以确认不适用？

建议在规则卡 Schema 中增加明确的槽位级处理记录，例如：

```yaml
not_applicable_slots:
  - slot: 公式
    reason: "该玩法不存在该结算分支"
```

具体字段可以再设计，但不能只依赖 AI 或文档中的一句说明。

R2 也要注意：相似度检查只能提供疑似重复告警，不能直接判断两条规则是否相同。

### P1-3：W1 连贯性检查不能主要依赖关键词

位置：W1-4，第 188～197 行

例如：

```
文本不含 · 且长度 < 12
```

不能作为可靠的空壳段落判断。

另外：

```
规则卡存在触发、过程、结果槽位
```

也不代表 AI 已经把三个内容正确组织到需求文档。

我建议将检查拆为三类：

| 检查 | 方法 |
| --- | --- |
| 结构完整性 | 确定性程序 |
| 规则事实一致性 | 结构化规则对照、计算器、Gold Set |
| 文档可读性与流程连贯性 | 人工验收为主，AI 评估辅助 |

特别建议 W1 把 Gold Set 纳入强制验收，而不是可选。

验收时随机选取典型玩法问题，让阅读者仅依赖生成的需求文档回答。

如果还必须回去翻规则卡才能理解玩法，说明 AI 生成质量仍然不够。

### P1-4：Mutation 与现有 Proposal 契约不一致

位置：W3-3，第 289～300 行

计划设计：

```ts
{
  target_kind: "segment" | "section" | "document",
  op,
  payload,
  base_revision,
  source
}
```

但是现有 DocumentProposalInput 的目标是：

```ts
{
  block_id,
  segment_id
}
```

现有操作类型也已经固定：

- append
- replace-text
- hide
- move-block
- edit-outline

另外，base_revision 必须由服务端计算，不能由前端或 Agent 提供。

我的建议：

不要再设计一套与 Proposal 平行的文档变更协议。

让 Mutation 负责表达编辑意图，服务端将它转换成已有 Proposal。

服务端负责：

- 解析目标。
- 确认编辑权限。
- 计算 base_revision。
- 确认目标文件。
- 生成 Diff。
- 交给 Transaction。

还有一点：需求全文.md 是渲染产物，不是事实源。Markdown 编辑器必须能够把编辑内容准确映射回 Document Block / Segment 身份，不能直接把 Markdown 文件当作事实源修改。

参考：proposal.ts 和 render.ts

### P1-5：本地 Web 服务的安全要求还不够

位置：W3-1，第 269～280 行

计划规定：

- 绑定 127.0.0.1。
- 不需要鉴权。
- 拒绝非本机请求。

作为本地单人工作台，这个方向合理。

但是后续会增加写入 API。

需要考虑恶意网页向本地服务发起请求的情况。

建议补充：

- Host 白名单。
- Origin 校验。
- 写入 API 的 CSRF 防护。
- CORS 默认拒绝。
- 服务端重新验证每次 Mutation 的权限。

尤其不能因为绑定 localhost，就认为所有请求都可信。

## 三、W5 基座升级还有一个架构问题

W5 的三方合并方向正确：

```
base_old
   |
   +---- current（包含人工修改）
   |
base_new
   |
   v
  merge3
   |
   v
 conflict report
```

但现在存在一个需要明确的地方：

你的系统本来就有 editorial-overrides.yaml，人工表达修改并不应该直接污染生成器的原始产物。

所以三方合并应该明确：

- base_old：上次正式生成的变体文档。
- base_new：基于新杭州基座和当前变体规则重新生成的候选文档。
- current：当前正式生成文档加人工表达修改层。

合并时必须考虑：

1. 生成内容变化。
2. 人工表达修改。
3. Segment 身份变化。
4. Block 拆分和合并。
5. 章节移动。
6. 被删除或隐藏的内容。

目前只设计 Segment 文本级合并还不够。

尤其是人工修改保存在独立 override 文件时，不能只比较 document.json 的文本。

建议把这一部分留到 W5 专项设计，不要在 W0 就实现复杂的三方合并。

## 四、我建议修改后的执行顺序

不需要推翻原来的 W0～W5。

我认为总体架构已经足够好，主要是修正一些契约和验收细节。

调整后的执行路线：

1. W0：契约和安全基础
   - 编辑权限与变体隔离
   - 产物路径注册
   - ReviewRecord 独立契约
   - 基座版本绑定
   - 输入版本锁定
   - 修复 Change ID

   可以优先启动

2. W1：杭州基座 AI 生成
   - Structured Output
   - 章节规划
   - 分章生成
   - 来源校验
   - 质量门禁
   - 执行日志
   - Gold Set 验收

   首个关键里程碑

3. W2：萧山变体生成
   - 基座版本绑定
   - 继承身份映射
   - R1/R2/R3 检查
   - 差异状态与机器检查分离
   - 完整、差异、对照三视图

4. W3：Web 阅读与编辑
   - 只读工作台
   - Markdown 编辑
   - 统一 Mutation / Proposal
   - 富文本编辑
   - AI 对话编辑
   - 服务端权限与本地安全

5. W4：批量编辑和审查
   - 编辑会话
   - 草稿保存
   - 批量事务
   - 审查状态
   - 历史与回滚

6. W5：基座升级
   - 影响分析
   - 增量生成
   - 三方合并
   - 冲突处理
   - 多变体验证

## 五、最终评审结论

| 评审项目 | 结论 |
| --- | --- |
| 产品方向 | 通过 |
| W0～W5 分阶段设计 | 通过 |
| AI 生成 Pipeline | 修改后通过 |
| 基座与变体权限 | 补强后通过 |
| 差异审核契约 | 必须修改 |
| Web 编辑架构 | 补充契约后通过 |
| 增量生成与合并 | 后续专项设计 |

我的核心建议是：不要继续扩大功能范围，而是先把 W0 和 W1 做扎实。

尤其是 W1。

你现在最需要验证的不是 Web 能不能编辑 Markdown，也不是能不能做出漂亮的三栏界面，而是：

AI 能不能把杭州麻将现有的 61 张规则卡、25 个配置项，真正组织成一份策划人员可以独立阅读、理解和修改的完整需求文档。

这个问题验证成功，后面的变体生成和 Web 编辑才有坚实的基础。

我建议先把上述 P0 问题修订到执行计划中，再启动 W0。不要让开发 Agent 在实现过程中自行决定这些契约问题。
