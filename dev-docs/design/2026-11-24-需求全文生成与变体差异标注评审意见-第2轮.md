## 评审对象与初步判断

重新读取了 `main` 上的最新版《需求全文生成与变体差异标注》（v1.2）。

这份文档已经不只是一个规则 Markdown 导出方案，而是在设计 MahjongRuleKB 的第二个核心能力：**结构化规则知识库 → 完整需求文档 → 变体差异追溯 → AI 对话式编辑。**

初步判断：整体方向正确，尤其是引入 Document Block、片段级来源追踪、增量重生成和人工提案机制。这些设计能够支撑后续 RuleStudio 从规则管理工具发展为真正的 AI 需求工作台。

但发现了几处需要在进入开发前解决的设计一致性问题。

## 一、必须修正的 4 处文档内部冲突

这些不是功能方向问题，而是会直接影响后续开发人员如何理解 Schema 和验收标准。

| 优先级 | 位置 | 问题 | 建议 |
| --- | --- | --- | --- |
| P0 | FR-32 / I-37 / AC-45 | FR-32 仍允许 `remove`，但其他章节明确不支持删除 | 删除 FR-32 中的 `remove` |
| P0 | AD-22 / AD-30 | AD-22 仍规定 `block_id` 使用章节+序号，AD-30 又规定与章节解耦 | 废弃 AD-22 的旧定义，以 AD-30 为准 |
| P0 | FR-38 / AC-32 | 仍使用旧的 `source_refs`、`provenance` 字段，而新版模型已经拆成四类引用 | 统一使用新版字段 |
| P0 | I-23 / FR-31 / 3.2 | 前面称五种标记，后面又定义三维独立标记 | 明确五种展示标签与三维数据的映射关系 |

尤其是第三项。新版模型已经确定：`requirement_refs`（原子需求）、`rule_refs`（规则卡）、`config_refs`（配置项）、`source_evidence_refs`（原始证据）。但 FR-38 和 AC-32 仍然要求 `source_refs`、`provenance`。如果开发人员按照验收标准实现，就会重新引入已经被 v1.2 淘汰的旧模型。

**建议先统一文档，再冻结 JSON Schema。**

## 二、4 个架构问题

### 1. 三维标记还缺少发布阻塞状态

文档要求支持这种组合：`modified + disputed + release_blocker`。但目前 Document Block 的字段只有 `lineage`、`decision_status`、`diff_status`，没有 `release_blocker` 或其来源引用。

这意味着 AC-39 要求展示的状态，目前在数据模型中还无法完整表达。建议增加独立的阻塞信息：

```json
{
  "lineage": "modified",
  "decision_status": "disputed",
  "diff_status": "candidate",
  "release_blocker_refs": ["XS-U-001"]
}
```

这样可以知道具体是哪一个未决项导致阻塞，而不是简单增加一个无法追溯的红色标签。

另外，基础杭州文档并没有变体继承关系。建议明确：

- 杭州基座：`lineage = base`
- 萧山继承：`explicit_inherited` / `default_inherited`
- 萧山修改：`modified`
- 萧山新增：`added`

否则杭州全文也无法使用同一套 Document Block Schema。

### 2. 片段级追溯还没有真正完整

文档已经正确地将一个段落拆成多个 `segment`，并允许每个片段有不同来源。但示例中 `requirement_refs`、`rule_refs`、`config_refs` 在片段级，`source_evidence_refs` 却只在段落级。

这会造成一个问题：一个段落同时引用杭州原始资料和萧山补充资料时，我们知道整段引用了哪些资料，却未必知道具体哪句话来自哪个原文位置。

建议四类引用全部下沉到片段级，段落级引用作为聚合索引。同时明确一个规则：**不同来源、不同状态的内容，必要时必须拆成不同 Segment**，不能为了减少片段数量，把多个来源混成一句无法准确追溯的文本。

### 3. ID 稳定性还缺少具体实现机制

已经确定：`block_id` 永久稳定、`segment_id` 片段级稳定、`logical_block_id` 跨变体稳定、`section_id` 可以变化。方向很好，但还缺一个关键问题：**第二次重新生成文档时，系统怎么知道新生成的段落对应原来的哪个 block？**

例如第一次生成：

```text
DOC-XS-000123
  SEG-000456
  SEG-000457
```

第二次生成时 AI 把两句话合并成一句，或把一句拆成三句，系统如何判断哪些 ID 应该保留、哪些应该新建？

建议补充 ID 生命周期规则：

1. `block_id` 由确定性 ID 分配器分配，禁止通过文字 Hash 生成。
2. `logical_block_id` 由章节模板与规则映射层维护。
3. 重生成时先进行逻辑块匹配，再处理片段匹配。
4. 被修改的片段保留原 ID；拆分、合并产生的新片段建立关联记录。
5. 原有人工修改的目标片段无法匹配时，进入「失效待处理」，禁止自动迁移到相似文本。

不必现在就实现复杂的语义匹配，但必须先确定身份和失效规则。

### 4. 与 RuleStudio 主架构存在存储边界问题

对照主需求文档和最新技术路线：RuleStudio 已确定「先做 Skill + CLI 内核，再叠加本地 Web 工作台」，主需求文档已设计 `<kb>/.rule-studio/proposals/` 作为统一提案存储位置。但这份增补文档又设计了 `documents/<variant>/` 下的 `editorial-overrides.yaml`、`proposals/`、`history/`。

需要明确区分：

| 数据 | 建议归属 |
| --- | --- |
| 规则修改提案 | `.rule-studio/proposals/` |
| 文档修改提案 | 统一提案存储，增加文档提案类型 |
| 当前 Document Block | `documents/<variant>/document.json` |
| 人工表达修改 | `documents/<variant>/editorial-overrides.yaml` |
| 生成历史 | `documents/<variant>/history/` |
| Stage 中间产物 | 独立 workflow 运行目录 |

尤其不能出现两套独立的提案生命周期。另外，主需求文档的文件写入白名单目前主要包括 `rulesets/`、`variants/` 和 `.rule-studio/`。新增 `documents/` 后，需要同步调整 CLI 的路径白名单和事务写入规则。这项架构对齐最好在开发前完成。

## 三、3 个验收与数据模型细节

1. **AC-28 漏掉了一个阻塞配置。** 前文提到 3 条阻塞未决项、2 张阻塞卡和 1 条阻塞配置，但验收只明确写了前两类。应补上 `XS-C-CAISHEN`。
2. **AC-24 对原子需求的要求过于绝对。** 上游有六种覆盖状态，其中明确排除、原文缺失和原文冲突不一定能作为正常规则写进正文。建议改成：每条需求必须在全文中有规则表达，或者在待裁决、明确排除等位置有明确记录，不能遗漏。
3. **FR-37 的可复现性定义不够准确。** LLM 重新生成的自然语言不保证字节级一致。AC-43 已经区分历史结果复现和重新生成后的结构、规则事实、数值校验，建议同步修订 FR-37，避免验收标准冲突。

## 四、建议补充的 4 项设计

### 1. 人工修改应该支持 Segment 定位

目前 `editorial-overrides.yaml` 示例只通过 `block_id` 定位，但 FR-47 已经要求选中句子时传入 `segment_id`。建议改为：

```yaml
- block_id: DOC-XS-000123
  segment_id: SEG-000456
  mode: replace-text
  text: 修改后的说明
  based_on_document_version: 3
```

这样才能真正实现句子级编辑，而不是选中一句话却替换整个段落。

### 2. 明确 changes.json 的事实来源

目前 `document.json` 是唯一事实源，`changes.json` 也包含差异及人工确认状态，`document.json` 的 Segment 又有 `diff_status`。建议明确：`document.json` 是唯一事实源，包含人工确认后的差异状态；`changes.json` 是可重建的差异索引。

### 3. 输入版本锁定还需要加强

`input-manifest.json` 已设计得比较完整，但建议增加：

- 原始资料的内容 Hash
- 原子需求登记表的快照 Hash
- 章节映射文件 Hash
- 计算器版本及计算输入
- 仓库生成时的 Git commit SHA

这样将来发现一条规则生成错误时，才能准确复现当时的输入环境。

### 4. P0-A 不应该假装验证了变体差异

P0-A 的实验对象是杭州 2.3.3 算分规则 —— 这是基座文档，不存在杭州与萧山之间的差异。建议明确：

- P0-A：验证 Document Block、原子需求追溯、计算器调用、完整性校验和 Markdown 渲染
- P0-B：验证杭州全文覆盖
- P1：正式验证变体继承、修改、新增、文字级 Diff 和人工确认

不要为了让 P0-A 看起来完成 Stage 0-6，就提前实现一个没有实际验证意义的差异引擎。

## 五、最终建议

这份设计最有价值的不是 Markdown 生成，而是三个能力：完整需求生成、变体差异追溯、AI 需求编辑器。

实施顺序保持不变，但进一步明确工程边界：

| 阶段 | 只解决什么 | 不做什么 |
| --- | --- | --- |
| P0-A | 单章节 Document Block 生成闭环 | 不做对话编辑 |
| P0-B | 杭州完整需求全文 | 不做萧山差异 |
| P1 | 萧山全文及段落级差异 | 不做复杂编辑器 |
| P2 | 对话式编辑、提案、增量重生成 | 不做在线多人协作 |

并沿用最新技术路线：先把能力做成 CLI 内核，后续 Web 工作台只是展示和操作入口。

**最终结论：v1.2 的产品架构可以保留，但还不适合直接冻结 Schema 并开始全面开发。优先修正四处 P0 冲突，补齐阻塞状态、片段引用和文档提案存储边界，再形成 v1.3。**

这样能避免后面做到 P1、P2 时，因为早期 Document Block 设计不完整而返工。
