### Rule Studio 需求全文生成与变体差异标注（2026-11-24，设计文档待评审）

第二个核心能力：不是把 Markdown 卡拼起来，而是「结构化规则 → 完整需求文档」的生成引擎。

- 复用既有 Compiler 得有效规则集（萧山 86 条），不重写继承机制、不改编译器
- 两种能力：完整需求全文（按对局流程分章）/ 全文差异标注（五种标记：基座沿用、变体修改、变体新增、默认继承、待裁决）；明确继承与默认继承分开
- 四个缺口：① 卡没有文档章节顺序（需独立章节映射层）② 差异只到卡级，需段落级 `changes.json`（`XS-R-ZHUANGJIA-02` 与 `HJ-R-LUNZHUANG` 为例）③ 配置差异元数据在编译后丢失（实测 `XS-C-QIANGGANGHU`：源有 `change_type: modified`，产物只剩 `origin: base`，故需三方比对，不改编译器）④ 未决项不得伪装成完整（3 条 blocker + 2 张卡 + 1 条配置）
- Stage 0-6 逐阶段落盘，支持增量重跑；数值与公式由确定性模板渲染，AI 只组织自然语言
- 三个正式产物：`需求全文.md`、`provenance.json`、`changes.json`；全文是产出物**不是事实源**（I-24）
- 上游质量门：需求覆盖与补齐（覆盖未完成不得宣称全文完整）
- 范围提醒：策划给的格式模板含 2/3/4 人与 40/50/60 片，与本仓库四人好友房范围不同，只能当格式模板

定稿补充（同日 v1.1）：并入「Document Block + 对话式段落编辑 + 增量重生成」——

- Stage 3 改为生成结构化文档块（`block_id` 与文字解耦、`content` 为片段数组以便一段内混合基座与变体来源）、Stage 6 改为渲染、新增 Stage 7 对话式段落编辑
- 四种编辑行为必须分流：表达调整（`editorial-overrides.yaml`）/ 规则修改（走既有提案门禁事务）/ 内容补充（先判断有无原文依据）/ 结构调整（章节映射层）；未归类不执行
- 重生成不得覆盖人工修改：段落四态（自动生成 / 人工表达修改 / 人工补充说明 / 上游变化失效），失效显式待处理
- 修改范围必须确认：仅萧山 / 改杭州基座（底座变更，要升版重算 hash 做下游影响）/ 仅文档说明
- 多对多：段落可依赖多张卡（实测 `XS-R-ZHUANGJIA-02` 依赖 `XS-R-ZHUANGJIA-03`、`XS-N-LAOSHU`），修改前列全来源
- 实施分 P0（文档块与来源追踪，必须预留 `block_id`/`section_id`/`source_refs`/`provenance`/`editable`/`document_version`）、P1（萧山差异与片段级追溯）、P2（对话编辑与增量重生成）
- 产品定位为三层（规则知识库 / 文档生成引擎 / AI 需求编辑器）+ 闭环原则：AI 可改需求，但不得绕过规则库直接改最终事实

评审后修订（v1.2，`dev-docs/design/2026-11-24-需求全文生成与变体差异标注评审意见.md` 存档）：

- 杭州与萧山共用同一套章节模板（`section_id` 跨变体一致），不再按「继承/修改/新增」重组萧山章节
- 差异标记拆三维：`lineage`（来源关系）/ `decision_status`（规则状态）/ `diff_status`（差异审核）。实测 `changeTypes` 只有 inherited/modified/added，**无 removed**，故第一版明确不支持删除
- Document Block：引用拆四类（`requirement_refs` / `rule_refs` / `config_refs` / `source_evidence_refs`）并接入原子需求；`block_id` 与章节解耦（`DOC-XS-000123`），另设 `segment_id`、`logical_block_id`；`editable` 下沉到片段级；`document.json` 为唯一事实源、`provenance.json` 为可重建派生索引
- 三个修改通道（规则 / 表达 / 结构）统一走提案 + `based_on_document_version` 版本校验；AI 不得直写
- 算例数值改由 `calculators/` 纯函数生成（实测 6 个导出函数），AI 只写解释
- 实施与上游节奏对齐：P0-A 单章节（2.3.3）跑通 Document Block 全流程 → P0-B 杭州全文（AC-24 同时检查卡/配置与原子需求）→ P1 萧山 → P2 对话编辑

交付：`dev-docs/design/2026-11-24-需求全文生成与变体差异标注.md`（v1.2：FR-29 至 FR-50、I-22 至 I-41、AD-15 至 AD-33、AC-24 至 AC-45）+ 评审意见存档；主需求文档升 v2.0。

### K0-3 事务契约与提交（2026-11-24）

新增 `studio/transaction/`：

| 文件 | 内容 |
| --- | --- |
| `journal.ts` | 两套状态机分离：Proposal `draft→ready→approved→applied`（另有 rejected/stale/failed）与 Transaction `preparing→prepared→writing→committed/rolled_back/recovery_failed`；非法迁移抛 `TxStateError`；事务清单 Schema（含 `existed_before` / `original_sha256` / `new_sha256` 一致性校验、路径去重） |
| `apply.ts` | `applyDocumentProposal`：先取单写者标记 → 文档版本 + 目标文件 Hash 双校验 → 备份并核对 → `writing` 阶段逐文件写入前复查原始 Hash → 临时文件 + rename 原子替换 → 写入后校验新 Hash → `committed`；任一失败回滚（已存在文件恢复、新建文件删除、清理空目录） |

关键约束：
- 顺序固定为「取锁 → 校验 → 备份 → 写入」，不允许先校验后取锁
- `intent` 由调用方声明（`apply-expression` / `apply-structure`），与目标路径不匹配时被权限矩阵拒绝，避免「op 与文件」错配
- `document.json` 与目标文件在同一事务内更新，文档版本 +1 后写入，保证版本与文件内容双重校验闭合
- 恢复：`preparing`/`prepared` 未写入任何文件→丢弃；`writing`→按 originals 回滚，备份缺失或 Hash 不符→`recovery_failed` 并保留现场、不自动重试

测试 10 条：状态机合法/非法迁移、正常提交（版本 +1）、版本不符拒绝、写入中断回滚、新建文件回滚删除、intent 与路径错配拒绝、三类崩溃恢复场景。

### Change Manager 吸收 OpenSpec 方法论（2026-11-24，已纳入开发计划）

OpenSpec 已作为 REF-003（MIT、只读参考）加入 `thirdparties/OpenSpec`。经源码与 docs 核对，吸收的是 **Change Package、Artifact Graph、Lifecycle、Archive** 的组织方法，而不是 OpenSpec CLI 或 Delta Spec 运行时。

- Change / Proposal / Transaction 三层分工：Change 组织一次跨对象变更、Artifact 依赖、跨会话恢复、Verify、Archive；Proposal 仍是单操作审批事实源；Transaction 仍是唯一写入与恢复机制

- Change Package 放 `<kb>/.rule-studio/changes/{active,archive}/`，Proposal 仍统一放 `<kb>/.rule-studio/proposals/`，避免两套 Proposal 生命周期
