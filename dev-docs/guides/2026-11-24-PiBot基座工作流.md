## 目录与仓库约定

| 位置 | 是什么 | 提交到哪 |
| --- | --- | --- |
| `E:/WorkProjects/MahjongRuleKB` | 知识库主仓库（本仓库），`$KB` | `origin` = `mickorz/MahjongRuleKB` |
| `E:/WorkProjects/MahjongRuleKB/thirdparties/PiBot` | PiBot fork 的 submodule，`$FORK` | `origin` = `mickorz/PiBot`，`upstream` = `w01fb0ss/PiBot` |

- 在 `$FORK` 里 `git commit` 提交的是 **fork 的代码**；在 `$KB` 里提交的是 **submodule 指针 + KB 自己的改动**。
- 两个仓库的 `origin` 都指向 `mickorz`，都直接推 `main`，不另设开发分支。
- `.gitmodules` 里 `thirdparties/PiBot` 的 `branch = main`：`git submodule update --remote` 会跟 fork 的 `main`。

## 两仓库提交顺序（硬规定）

**先 fork，后 KB。** 顺序反了会造成「KB 提交了指针、但 fork 上没有这个 commit」——别人克隆拿不到代码。

```sh
# 1. fork 内：改代码、验证、提交、推送
cd $FORK
pnpm check                 # 见下文「提交前的检查」
git add -A && git commit -m "..."
git push origin main

# 2. KB 内：固定新指针，连同 KB 侧文档一起提交
cd $KB
git add thirdparties/PiBot                 # 只加 gitlink
git add dev-docs/...                       # 该阶段文档
git commit -m "..."
git push origin main
```

禁止：
- 在 `$FORK` 里有未提交改动就去 `$KB` 提交指针（工作区会漂移）
- 只提交 gitlink 不推 fork
- 在 `$KB` 根目录用 `git add -A` 把 fork 内的半成品一起吞进去（先跑 `git status` 看清 gitlink 变化）

## 分叉状态检查

```sh
cd $FORK
git log --oneline -3                      # fork 自己的提交
git log --oneline origin/main..HEAD       # 还没推的提交（应为空）
git rev-list --left-right --count upstream/main...HEAD   # 落后/领先上游多少
```

## 上游同步（合并 `upstream/main`）

```sh
cd $FORK
git fetch upstream
git merge upstream/main          # 冲突点记进本节「已知冲突点」
pnpm install                     # 上游可能改了依赖
pnpm check                       # 必须过；只接受基线内的既有失败
git push origin main

cd $KB
git add thirdparties/PiBot && git commit -m "chore: 同步 PiBot 上游"
```

合并后必须更新 `thirdparties/REFERENCES.md` 里 REF-001 的固定 commit。

**已知冲突点**（每次合并后追加，供后来者预判工作量）：

| 位置 | 我们改了什么 | 冲突风险 |
| --- | --- | --- |
| `apps/desktop/electron-builder.yml` | `appId` / `productName` / `artifactName` / `shortcutName` / `executableName` | 中：上游改打包配置时同一批行 |
| `apps/desktop/src/main/index.ts` | `app.setName(...)`、`setAppUserModelId` | 低 |
| `packages/storage/src/database/data-dir.ts` | 数据目录名 | 低（但改错会让老数据读不到） |
| `packages/i18n/src/{en,zh}.ts`、`sections/*.ts` | 应用名全量替换（约 130 处） | 高：上游任何文案改动都会撞 |
| `NOTICE`、`README.md` | 派生声明与 fork 说明 | 低 |
| `packages/brain-app/src/index.ts` | Capability 列表（裁剪） | 中 |

文案替换用脚本按词替换即可，不要手工逐条 merge：

```sh
node -e 'const fs=require("fs");const f=process.argv[1];fs.writeFileSync(f,fs.readFileSync(f,"utf8").split("Pi Bot").join("Mahjong Rule Studio"))' <文件>
```

## 开发期常用命令（都在 `$FORK`）

```sh
export PATH="/c/Users/<用户名>/AppData/Local/nvm/v26.11.1:$PATH"   # Node 26.11.1
node -v && pnpm -v                                                # v26.11.1 / 12.14.0

PIBOT_DATA_DIR=E:/WorkProjects/MahjongRuleKB/dev-examples/pibot-env/data pnpm dev
pnpm typecheck
pnpm lint
pnpm test
pnpm check                 # frozen install + typecheck + lint + policy matrix + 测试
pnpm check:changed         # 只查改动的包，迭代时用
pnpm build                 # 生成 apps/desktop/out（smoke 前必须先跑）
pnpm smoke                 # renderer smoke 通过；owner smoke 在 Windows 上会因 ENOTEMPTY 失败（基线）
```

## 提交前的检查

| 检查 | 要求 |
| --- | --- |
| `pnpm check` | 通过，或只有基线内既有失败（见下表） |
| 新增 UI 文案 | `packages/i18n` 中英同改 |
| 新增颜色 | 只用 `packages/ui` 主题 token |
| 新依赖 | 在提交信息里说明理由（PiBot 规则） |
| `PIBOT_DATA_DIR` | 测试与冒烟都用独立目录，不碰真实用户数据 |

**基线内既有失败**（Phase 0 记录，commit `152425f` + 本分支改名之前，Node 26.11.1 / Windows / zh-CN）：

| 项 | 现象 |
| --- | --- |
| `pnpm test`（`@pibot/brain` T8） | 断言英文提示词 `Commands: ask`，zh-CN 机器拿到中文 |
| `pnpm smoke:owner` | 清理临时目录时 `ENOTEMPTY`（应用本身正常） |

基线之外的新失败一律归我们的改动，必须修。

## 环境变量

| 变量 | 用途 |
| --- | --- |
| `PIBOT_DATA_DIR` | 数据目录覆盖。开发统一指向 `dev-examples/pibot-env/data`（已 gitignore） |
| `PATH` | 前置 Node 26.11.1 目录；全局默认是 24.18.0 |
| `ELECTRON_MIRROR` | Electron 二进制下载镜像（国内网络需要）：`https://npmmirror.com/mirrors/electron/` |
