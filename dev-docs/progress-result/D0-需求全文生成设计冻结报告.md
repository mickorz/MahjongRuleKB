## 一、冻结结论

### 1.1 两条工作流边界

- 需求全文生成线输入 `rulebook/specs/` 的已结构化规则、配置和未决项。
- 原子需求覆盖线直接读取 `rulebook/sources/`，独立生成 Requirement Registry 和六态覆盖报告。
- 原子需求覆盖不是 P0-A/P0-B 的前置或验收阻塞。
- Document Block 预留可选 `requirement_refs`，未来两线通过它关联。

### 1.2 资产目录

```text
rulebook/
  sources/                     原始证据，只读
  specs/base/hangzhou/         基础正式规范
  specs/variants/xiaoshan/     派生正式规范
  changes/archive/             已归档 Change，入库审计
  compiled/                    编译产物，禁手改

<kb>/.rule-studio/
  changes/active/               活动 Change，运行时
  proposals/                   规则/文档 Proposal，共用
  transactions/                唯一写入/恢复机制
  workflow/                    Stage 中间产物
```

### 1.3 写入主体

| 主体 | 能力 |
| --- | --- |
| Agent | 只能读取并产生 Proposal / Change，不得直接写事实或 documents |
| Stage Executor | 通过受控 Stage Run / Regenerate RPC 写生成产物白名单 |
| UI Apply + Transaction | 经过批准后写规则、配置或人工文档修改；先锁、校验版本/Hash、备份、写入、验证、可恢复 |

## 二、核心契约

### 2.1 Document Block

- `document.json` 是结构、身份、`segment_lineage` 的唯一事实源。
- `editorial-overrides.yaml` 是人工表达修改的权威输入。
- `provenance.json`、`identity-map.json`、P1 的 `changes.json` 是可重建索引或产物。
- `block_id` 与 `section_id` 解耦；`segment_id` 是片段身份；`logical_block_id` 用于跨变体对照。
- 四类引用：`requirement_refs`（可选）、`rule_refs`、`config_refs`、`source_evidence_refs`。
- 数值/公式片段不可由 AI 自由改写，使用 `calculators/` 或确定性模板。

### 2.2 文档 Proposal

- 文档与规则 Proposal 共用 `<kb>/.rule-studio/proposals/`。
- Proposal 状态：`draft / ready / approved / applied / rejected / stale / failed`。
- Transaction 状态：`preparing / prepared / writing / committed / rolled_back / recovery_failed`。
- 文档 Proposal 用 `baseRevision.documentVersion` 与 `baseRevision.files[].sha256` 双校验。
- Agent 不提供落盘路径；服务端根据 `op` 和目标 Block/Segment 推导目标文件。
- `documents/` 白名单分级，普通文件工具无直接写权限。

### 2.3 Change Manager

- 吸收 OpenSpec 的 Change Package、Artifact Graph、Lifecycle、Archive 方法论。
- 不引入 OpenSpec CLI、运行时、通用 Schema 引擎或 Markdown Delta 解析器。
- Change 组织多个 Proposal、依赖产物、跨会话 Resume、Verify、Archive。
- Proposal 负责单操作审批；Transaction 负责唯一写入；Archive 只归档，不再次写事实。
