## 一、计划目的与开发边界

本文只规划「需求全文生成与变体差异标注」从设计收敛到 P0-A、P0-B、P1、P2 的开发路径，不在本次计划中直接实现代码。

### 1.1 最终产品定位

MahjongRuleKB 的 Rule Studio 分为三层：

```text
结构化规则知识库
  基础规则、地方变体、配置、来源、依赖
        ↓
需求文档生成引擎
  Stage Workflow、Document Block、来源追踪、变体差异
        ↓
AI 需求编辑器
  选中段落、对话修改、Proposal、Diff、人工审核、增量重生成
```

核心原则：

> AI 可以通过对话修改需求，但不能绕过结构化规则知识库直接修改最终事实。

### 1.1.1 与「原子需求覆盖」线的边界（v4 冻结）

本计划只交付「结构化规则 → 完整需求文档」。它**不依赖**原子需求提取：

| 维度 | 本计划线 | 原子需求覆盖线 |
| --- | --- | --- |
| 输入 | `rulebook/specs/`（已结构化规则、配置、未决项） | `rulebook/sources/`（原始资料） |
| 任务 | 按对局流程组织完整需求文档 | 独立提取原子需求并做六态覆盖判定 |
| 验证 | 规则卡与配置项是否完整落入文档 | 原文需求是否被识别与覆盖 |
| 依赖 | **不依赖对方** | 需要规则结构化结果参与映射 |

两条线只通过 Document Block 的可选字段 `requirement_refs` 关联：本计划**预留该字段但不要求填值、不要求验证**。

两个概念必须分开：

- **完整需求文档**（本计划交付物）：当前 Rule KB 中已结构化的规则与配置，完整转化为文档。
- **原始需求的完整覆盖**（另一条线）：原始资料中的要求没有被结构化过程遗漏。

### 1.2 本计划不做什么

- 不重新实现 `compiler/compile.ts` 的规则继承。
- 不修改规则卡 Schema 的既有语义。
- 不实现规则删除能力；当前 `changeTypes` 只有 `inherited`、`modified`、`added`。
- 不在 P0-A 实现萧山差异引擎。
- 不在 P0-A 实现对话编辑 UI。
- 不在 P0-A 至 P1 实现 Change Manager；仅在 D0 / K0 完成契约设计，P2 才实现。
- 不引入 OpenSpec CLI、运行时依赖、通用工作流 Schema 引擎或 Markdown Delta Spec 解析器。
- 不开发原子需求提取，不建立 Requirement Registry，不把原子需求覆盖作为任何阶段的门禁。
- 不引入数据库。
- 不实现在线多人协作。
- 不把生成的 `需求全文.md` 当作事实源。
- 不允许 AI 直接写规则卡、配置、`rulebook/compiled/` 或文档产物。
- 不在设计评审通过前冻结 JSON Schema。

## 五、K0：领域接口、数据模型与路径边界

K0 只定义接口和边界，不写完整生成流程，也不实现 Change Manager。

### 5.1 Document Block 最小模型

```text
Document
  document_version
  template_version
  ruleset_id
  ruleset_version
  blocks[]
  identity_lineage[]

Block
  block_id                 永久稳定，不含 section_id
  logical_block_id         跨变体逻辑身份
  section_id               当前章节
  type                     paragraph/table/formula/list/callout
  document_version
  content[]
  requirement_refs[]      可选预留字段：结构存在即可，P0 不填值不校验
  rule_refs[]             必填字段，可为空数组
  config_refs[]           必填字段，可为空数组
  source_evidence_refs[]  必填字段，可为空数组

Segment
  segment_id
  text
  editable
  lineage                  base/explicit_inherited/default_inherited/modified/added
  decision_status          confirmed/unresolved/disputed
  diff_status              not_applicable/candidate/confirmed
  release_blocker_refs[]
  requirement_refs[]      可选预留（同上）
  rule_refs[]
  config_refs[]
  source_evidence_refs[]
  segment_lineage[]        split/merge 关系
```

### 5.2 身份生命周期

采用 `document.json` 单一事实源方案：

- `block_id`、`segment_id` 由确定性分配器分配，但不由文本 Hash 生成。
- `logical_block_id` 由共享章节模板和规则映射层维护。
- `document.json` 保存完整块身份、片段身份和 `segment_lineage` 历史。
- `identity-map.json` 只是索引，可从 `document.json` 重建。
- 重生成先按 `logical_block_id` 匹配，再按来源卡、槽位和顺序匹配片段。
- 不使用文本相似度自动迁移人工修改。
- 无法匹配时进入「失效待处理」，不自动迁移 override。
- `segment_lineage` 支持：
  - `split`: 一个旧片段 → 多个新片段。
  - `merge`: 多个旧片段 → 一个新片段。

### 5.4 Change Manager 契约（吸收 OpenSpec 方法论）

`thirdparties/OpenSpec`（REF-003，MIT）只作为方法论参考：吸收 **Change Package、Artifact Graph、Lifecycle、Archive**，不依赖其 CLI、不复制 Markdown Delta Spec 解析器、不引入其通用 Schema 引擎。

```text
<kb>/.rule-studio/
  changes/
    active/CHG-001/
      change.json               # Change 的唯一事实源：意图、范围、成员 Proposal、生命周期
      artifacts/
        diff.json               # 派生
        validation-report.json  # 派生
        impact-report.json      # 可选派生
        approval.json           # 人工审批记录
        verify-report.json      # 最终验证记录
  proposals/DOC-P-001.json      # Proposal 仍是操作事实源，Change 仅引用
  transactions/TX-001/
  workflow/task-001/

rulebook/changes/archive/2026-11-24-CHG-001/   # 归档全量包（入库，审计留痕）
```

**活动区与归档区分离**：活动 Change 只在 `.rule-studio/changes/active/`（不入库）；Verify 通过后整包单向导出到 `rulebook/changes/archive/`（入库）。不建 `rulebook/changes/active/`，避免两套活动变更生命周期。

| 层 | 职责 | 不负责 |
| --- | --- | --- |
| Change | 一次业务变更的容器；组织多个 Proposal、产物依赖、跨会话恢复、Verify、Archive | 不直接写权威文件 |
| Proposal | 一个结构化操作的审批对象 | 不组织跨文件变更包 |
| Transaction | approved Proposal 的安全文件写入、回滚、崩溃恢复 | 不管理 Change 的业务意图或归档 |

轻量 Artifact Graph（固定，不实现通用配置引擎）：

```text
Change proposal → Diff + 可选 Impact → Validation → Human Approval
  → Transaction Apply → Incremental Regenerate → Verify → Archive
```

- 纯表达变更跳过 Impact。
- 规则/配置变更需要 Impact 和 G1-G4。
- Artifact 依赖表示「可以继续产生什么」，不是强制瀑布阶段门。
- `update`：意图仍成立时更新同一 Change；旧 Diff/Validation/Impact 按输入 Hash 失效。
- `continue` / `resume`：从 `change.json` 和 Artifact Graph 恢复下一个可执行项。
- `archive`：Verify 后移动完整包到 archive；**不得再次修改规则、配置或文档事实**。

### 5.5 Proposal 与 Transaction 契约

#### Proposal 状态

```text
draft → ready → approved → applied
             ↘ rejected
             ↘ stale
             ↘ failed
```

#### Transaction 状态

```text
preparing → prepared → writing → committed
                              ↘ rolled_back
                              ↘ recovery_failed
```

文档提案示意：

```json
{
  "id": "DOC-P-001",
  "type": "document",
  "rulesetId": "xiaoshan-friends-4p",
  "targetVariant": "xiaoshan",
  "baseRevision": {
    "documentVersion": 3,
    "files": [
      {
        "path": "documents/xiaoshan/editorial-overrides.yaml",
        "sha256": "sha256:..."
      }
    ]
  },
  "target": {
    "blockId": "DOC-XS-000123",
    "segmentId": "SEG-000456"
  },
  "op": "replace-text",
  "before": {
    "text": "旧文本",
    "sha256": "sha256:..."
  },
  "after": {
    "text": "新文本",
    "sha256": "sha256:..."
  },
  "status": "ready"
}
```

约束：

- `type: document` 与规则提案共用 Proposal Schema 的外层生命周期。
- `baseRevision.documentVersion` 与当前文档版本比较。
- `baseRevision.files[]` 每个文件逐一计算 Hash。
- 版本或任一文件 Hash 不匹配，Proposal 标记 `stale`，不进入写入。
- `approved` 后创建 Transaction；Transaction 结果再回写 Proposal。
- `op` 与目标文件由服务端推导，Agent 不得任意传路径。

### 5.6 操作与目标文件

| 操作 | 层 | 目标 |
| --- | --- | --- |
| `append` | 文档表达 | `editorial-overrides.yaml` |
| `replace-text` | 文档表达 | `editorial-overrides.yaml` |
| `hide` | 文档表达 | `editorial-overrides.yaml` |
| `move-block` | 章节结构 | Stage 2 章节映射文件 |
| `edit-outline` | 章节结构 | Stage 2 章节映射文件 |
| 规则事实修改 | 结构化规则 | `rulebook/specs/base/hangzhou/` / `rulebook/specs/variants/<玩法>/` / manifest / config，由规则提案处理 |

## 九、P2：对话式段落编辑与增量重生成

### 9.1 四种编辑行为

| 行为 | 落点 | 流程 |
| --- | --- | --- |
| 表达调整 | `editorial-overrides.yaml` | 文档提案 → 版本/Hash 校验 → 人工确认 → Transaction |
| 规则修改 | 规则卡 / 配置 | 规则提案 → G1-G4 → 人工确认 → Transaction → Stage 1-6 |
| 内容补充 | 表达层或规则层 | 先判断是否有原文依据；无依据进 unresolved，不得 confirmed |
| 结构调整 | Stage 2 章节映射 | 文档提案 → 版本/Hash 校验 → 人工确认 → Stage 2-6 |

### 9.2 对话输入

选择段落或句子时，必须传给 Agent（`requirement_refs` 为可选）：

```text
block_id
segment_id
logical_block_id
section_id
document_version
selected_text
rule_refs                 // 必传
config_refs               // 必传
source_evidence_refs      // 必传
requirement_refs          // 可选：原子需求覆盖线接入后才使用
```

### 9.3 增量回流

| 变更 | 最小回流 |
| --- | --- |
| 规则卡 / 配置变化 | Stage 1 → 2 → 3 → 4 → 5 → 6 |
| 文档表达变化 | 更新 override → Stage 6 |
| 章节结构变化 | Stage 2 → 3 → 4 → 5 → 6 |
| （未来）原子需求变化 | 属另一条线；本计划只在 `requirement_refs` 回填后按引用反查受影响 Block |

### 9.4 P2 验收

- Proposal `status` 与 Transaction 状态分离。
- V3 提案无法应用到 V4 文档。
- 目标文件任一 Hash 变化都会拒绝应用。
- 表达修改不会修改规则卡。
- 规则修改不会写入 editorial override。
- 规则提案、文档提案共用同一 `.rule-studio/proposals/` 和 Transaction 目录。
- 一个 Change 可包含多个关联 Proposal；Proposal 更新后，旧 Diff / Validation / Impact 自动失效。
- Artifact 依赖未满足时 Change 不能批准或应用；Change 可跨会话 Resume。
- Transaction 成功后可恢复 Verify；Verify 通过后才能 Archive；Archive 不得再次修改正式规则或文档。
- Archive 可追溯对应 Transaction、Proposal 与最终文档版本。
- split / merge / 无法匹配四种身份场景全部通过.
- 无法匹配时人工修改进入「失效待处理」，不自动迁移。

## 十二、风险与停止条件

| 风险 | 应对 | 停止条件 |
| --- | --- | --- |
| 误把「规则已进文档」当成「原始需求已覆盖」 | 文档明确区分两个概念；覆盖结论只能由另一条线给出，本计划不得声称「需求已全部覆盖」 | 在交付说明里把完整需求文档等同于原始需求完整覆盖 |
| 文档块身份错配 | 只用持久化结构映射，不自动语义迁移 | 任何人工修改被静默迁移或丢失 |
| Proposal/Transaction 混用 | 两层状态机、双校验、共用事务 | Proposal 出现事务状态 |
| Change 退化为第二套提案 | Change 只做容器和生命周期，Proposal / Transaction 仍是唯一审批与写入层 | Change 直接写权威文件，或出现第二套 Proposal 状态机 |
| 人工 override 被重建覆盖 | override 作为权威输入，重建只读 | 任何重生成覆盖人工文字 |
| LLM 改写数值 | 模板/计算器确定性生成 | 文档数值与计算器不一致 |
| 变体差异越级 | P0-A 明确 `not_applicable`，P1 才实现差异 | P0-A 出现未经需求的差异结论 |
| 目录边界不清 | `.rule-studio` 统一运行数据与提案；`documents` 明确白名单 | 出现第二套 Proposal 或绕过事务写入 |
| 路径再次扩散 | 根路径只在 `compiler/paths.ts` 定义，`tests/compiler/paths.test.ts` 强制 | 代码或测试里重新出现 `rulesets/`、`variants/`、`compiled/` 字面量 |
| 规则集类型靠路径猜 | 已改为显式 `kind`（P1-A），新增规则集必须显式传 kind | 再次出现 `dir.startsWith("variants")` 类判断 |
