# 二、总体策略

## 2.1 顺序原则

先验证 AI 能不能写出连贯文档，再动编辑器。理由：若底层文档结构不适合策划阅读，先做编辑器等于给错结构做漂亮外壳。

```
W0 契约与安全基础（含产物注册、状态三维分离）
   |
   v
W1 杭州基座 AI 生成（Structured Output + 质量门禁 + 执行日志）   <-- 强制暂停点 M1
   |
   v
W2 萧山变体完整文档（继承复用基座片段 + R1/R2/R3 + 三视图）
   |
   v
W3 本地 Web 阅读与编辑（只读先上，服务端权限复验）
   |
   v
W4 批量编辑与审查记录
   |
   v
W5 基座升级与增量重生成（专项设计后实施）
```

## 2.2 与 D0 冻结的关系

| 动作 | 是否允许 |
| --- | --- |
| 新增契约文件（`machine-check.ts`、`review.ts`、`chapter-draft.ts`、`edit-scope.ts`） | 允许，作为新 Change 增量 |
| 给既有 Schema 增加**可选**字段（`base_binding`、`machine_check_status`、`base_segment_ref`） | 允许，需 K0 补丁 + 兼容性测试 |
| 收紧权限矩阵（加变体前缀、加产物白名单） | 允许（只收紧不放宽） |
| 修改既有字段语义、改变既有枚举取值 | **不允许**（v1.0 的 `diff_status` 改动因此撤回） |
| 新增 actor / intent 枚举成员（如 `server` + `apply-review`） | 允许，但必须证明是增量：旧值仍全部合法 |

## 2.3 变更承载方式

本工作流自身用一个 Change 走完整流程，作为 Change Manager 的首次真实使用（Change ID 修正为符合 `/^CHG-\d{3}$/`）：

```
CHG-001
   ├── 提案组：W0 契约增量
   ├── 提案组：W1 生成层
   ├── ...
   └── 归档至 rulebook/changes/archive/2026-11-25-CHG-001/
```

## W1 杭州基座 AI 生成（关键里程碑 M1）

**目标**：让杭州全文从「槽位展开」变成「按玩法流程组织的连贯文档」，且连贯性可被机检 + 人读双重判定。

### W1-1 生成 provider 抽象与能力分级

> 对应评审 P0-4 第 8 点：不假设所有模型支持原生 Structured Output。

- 文件：`studio/generate/provider.ts`（新增）
- 接口：

  ```ts
  interface GenerationCapabilities {
    structured_output: "native" | "json_mode" | "text_only";
    max_output_tokens?: number;
  }
  interface Generator {
    name: string;
    version: string;
    capabilities: GenerationCapabilities;
    generateChapter(req: ChapterRequest): Promise<ChapterResponse>;
  }
  ```

- 实现：
  - `DeterministicGenerator`（复用现有槽位展开，降级路径，`capabilities = text_only`）
  - `LlmGenerator`（供应商无关；按 capability 选择原生 schema / JSON mode / 文本 + 提取）
- 失败策略：单章失败 → 重试 ≤ 2（仅 JSON 不合法时）→ 仍失败则**整体失败并落日志**，不得静默降级出残缺文档；降级只能由调用方显式开关触发，且产物记 `degraded: true`。
- 测试：fake generator（≥ 7 条，含 capability 分支、重试上限、失败必须冒泡）

### W1-2 结构化输出契约（ChapterDraft）

> 对应评审 P0-4。

- 文件：`studio/contracts/chapter-draft.ts`（新增，Zod）

  ```ts
  ChapterDraft = {
    section_id: string,
    paragraphs: Array<{
      title?: string,
      text: string,
      claims: Array<{ text: string, rule_refs: string[], config_refs: string[] }>
    }>
  }
  ```

- 服务端校验（**引用不接受模型自报**）：
  1. Schema 校验
  2. `rule_refs` / `config_refs` 必须存在于本次锁定的有效规则集
  3. 每个 `paragraph` 至少有一处 citation 命中
  4. 数值 token 必须能在所引规则卡正文或配置值中找到（见 W1-5）
  5. 校验失败保留原始响应，用于排查
- 测试：`tests/studio/contracts/chapter-draft.test.ts`（≥ 8 条，含「模型编造规则 ID 被拒」）

### W1-3 章节规划

- 文件：`studio/pipeline/plan.ts`（新增）

### W2-2 继承片段复用（解决 P0-6 的映射问题）

> 对应评审 P0-6。**结论：继承内容不重新生成**，因此不需要「查找对应基座段落」的算法。

- 规则：
  1. 变体文档的继承片段**直接复用基座 `document.json` 中的 Segment**，保留原 `segment_id` 与 `block_id` 前缀，`lineage` 记为 `default_inherited` / `explicit_inherited`
  2. AI 只为 `modified` / `added` 卡生成内容
  3. `Segment` 新增可选 `base_segment_ref?: string`，**仅用于 `modified` 段落追溯**（C4）：

     | lineage | `segment_id` | `base_segment_ref` |
     | --- | --- | --- |
     | `default_inherited` / `explicit_inherited` | 保留基座原 `segment_id` | 不填（身份已相同） |
     | `modified` | 新建 | 填，指向被改写的基座 `segment_id` |
     | `added` | 新建 | 不填 |
  4. 若某章既含继承又含变体内容：继承片段置前，变体片段置后；章节标题可重写，但继承片段正文与顺序不得变
- 由此，「逐字一致」从**校验目标**变为**构造结果**；W2-5 仍保留断言作为回归护栏
- 测试：`tests/studio/pipeline/inherit-reuse.test.ts`（≥ 8 条，含「变更基座片段会导致变体重新绑定」）

### W2-3 差异检查 R1 / R2 / R3

- 文件：`studio/pipeline/diff-checks.ts`（新增，纯函数，无 AI）
- R1 槽位差集：基座卡槽位 − 变体卡槽位；非空报警，除非命中 `not_applicable_slots` 声明（W2-4）
- R2 疑似重复：`added` 卡与基座卡名称 / 正文相似度（字符 3-gram Jaccard），阈值先松（名称 0.85 / 正文 0.6），报警附最相近卡 ID。**只报疑似，不判定相同**
- R3 归类自洽：
  - `inherited` 必有 `base_rule_ref`，且正文不得含改写内容
  - `modified` 必有 `base_rule_ref` 且 `compares_to` 非空，正文不得与基座完全一致
  - `added` 不得有 `base_rule_ref` / `compares_to`
- 顺带修 `compiler/validator.ts` 空转三元（`change_type === "inherited" ? baseIds : baseIds`）
- **输出落 `machine_check_status` 与 `diff-warnings.json`，不改 `diff_status`**
- 测试：`tests/studio/pipeline/diff-checks.test.ts`（≥ 14 条）

## W3 本地 Web 阅读与编辑

### W3-1 服务端

- 目录：`server/`
- 技术：Node 内置 `http`，监听 `127.0.0.1`，不引入框架
- 安全（对应评审 P1-5）：

  | 项 | 要求 |
  | --- | --- |
  | Host | 白名单 `localhost:PORT` / `127.0.0.1:PORT`，其余 403 |
  | Origin | 写入请求必须 Origin 同源或缺失同源标记；跨源一律拒绝 |

  | 绑定 | 仅 `127.0.0.1`；不监听 `0.0.0.0` |

### W3-3 统一变更层（不新建平行协议）

> 对应评审 P1-4。

- 文件：`studio/edit/mutation.ts`（新增）：`Mutation` 只表达**编辑意图**

  ```ts
  Mutation = {
    target: { block_id?: string, segment_id?: string, section_id?: string },
    op: "append" | "replace-text" | "hide" | "move-block" | "edit-outline",
    text?: string,
    source: "richtext" | "markdown" | "ai-dialog"
  }
  ```

- 服务端 `mutationToProposal(mutation, context)`：
  1. 解析目标到 `block_id` / `segment_id`
  2. `edit-scope.canEdit` 校验
  3. 映射到既有 `DocumentProposalInput`（op 与目标粒度必须符合契约）
  4. **服务端计算 `base_revision`**（document_version + 目标文件 sha256）
  5. 生成 Diff → 等用户 Apply → `transaction.apply`
- 禁止：`Mutation` 携带 `base_revision`、`diff`、`transaction_id`（这些由服务端产出）
- Markdown 编辑：解析后必须映射回 Segment 身份；无法映射的文本变更（凭空新增段落）→ 拒绝并提示走 `edit-outline` 或结构提案，**不得直接改 `需求全文.md`**
- 测试：`tests/studio/edit/mutation.test.ts`（≥ 10 条，含「越权被拒」「无法映射被拒」「base_revision 由服务端覆盖前端值」）

# 七、风险与停止条件

| 风险 | 应对 | 停止条件 |
| --- | --- | --- |
| AI 内容「通顺但改事实」 | 引用由服务端校验；数值四类分级；Gold Set 强制 | 出现无 citation 的事实性断言 |
| 结构化输出不稳定 | capability 分级 + 有限重试 + 保留原始响应 | 同一章重试 2 次仍不合法 |
| 连贯性检查退化为关键词 | A/B 两类程序检查 + C 类人工问答 | 检查项无法构造反例 |
| 状态字段再次混淆 | 三维各写各的，测试锁死 | 任一字段被用来表达另一维含义 |
| 先做编辑器、结构不对 | 严格 W1→W2→W3 | M1 未通过就启动 W3 |
| 权限靠前端拦 | 服务端复验 + Host/Origin/CSRF | 任一越权靠 UI 隐藏实现 |
| 三方合并丢人工修改 | W5-0 先设计；冲突禁止自动取边 | 人工修改被静默覆盖 |
| 检查阈值被调松 | 阈值变更单独提交 | 同次提交既改代码又放宽阈值 |
| 产物未注册导致写盘失败 | W0-6 与 W0-1/2 同批完成 | W1 开写前产物注册表缺项 |
