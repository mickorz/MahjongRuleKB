# 二、总体策略

## 2.1 顺序原则

按产品需求文档第十九节，**先验证 AI 能不能写出连贯文档，再动编辑器**。理由：若底层文档结构不适合策划阅读，先做编辑器等于给错结构做漂亮外壳。

```
W0 契约增量与安全加固
   |
   v
W1 杭州基座 AI 生成（含质量门禁）      <-- 首个可判断成败的里程碑
   |
   v
W2 萧山变体完整文档（含 R1/R2/R3、三视图）
   |
   v
W3 本地 Web 阅读与编辑（只读先上，再编辑）
   |
   v
W4 批量编辑与审查状态
   |
   v
W5 基座升级与增量重生成（三方合并）
```

## 2.2 与 D0 冻结的关系

| 动作 | 是否允许 |
| --- | --- |
| 新增契约文件（如 `review.ts`、`edit-scope.ts`） | 允许，作为新 Change 的增量 |
| 给既有 Schema 增加**可选**字段（如 `review_status`） | 允许，需 K0 补丁 + 契约测试 |
| 修改既有必填字段语义、改变枚举 | **不允许**，需走设计修订评审 |
| 重写生成 Pipeline | 允许，属实现层 |
| 修改 `compiled/`、权限矩阵语义 | 权限矩阵可**收紧**（加变体前缀），不可放宽 |

## 2.3 变更承载方式

本工作流自身用一个 Change 走完整流程，作为对 Change Manager 的第一次真实使用：

```
CHG-2026-11-25-base-variant-workflow
   ├── 提案组 P1：W0 契约增量
   ├── 提案组 P2：W1 生成层
   ├── ...
   └── 归档至 rulebook/changes/archive/2026-11-25-CHG-2026-11-25-base-variant-workflow/
```

副产品：验证 Change Manager 在真实规模下是否可用。

# 三、工作包

## W0 契约增量与安全加固

**目标**：在不改 D0 语义的前提下，补齐「谁能编辑」「什么状态」两类缺失契约，并堵住跨变体写入。**W0 未完成不得进入 W3**（Web 编辑必须建立在权限强制之上）。

### W0-1 编辑范围策略（纯函数）

- 文件：`studio/policy/edit-scope.ts`（新增）
- 内容：
  - `editScopeOf(lineage, targetVariant)` → `base` / `inherit` / `variant`
  - `canEdit({ segment, context })` → `{ ok, reason }`
  - `escalateHint(segment)` → 给 UI 的两种正确处理方向（建 modified / 走基座）
- 规则：`base` / `explicit_inherited` / `default_inherited` 恒不可编辑；`modified` / `added` 仅在其 `target_variant` 上下文内可编辑；杭州基座文档整体不可编辑。
- 测试：`tests/studio/policy/edit-scope.test.ts`（≥ 8 条，含越权用例）

### W0-2 变体隔离（权限矩阵收紧）

- 文件：`studio/paths/registry.ts`
- 内容：`documents/<variant>/` 的写入校验增加「当前提案声明的 variant 必须与路径中 variant 一致」；新增 `assertVariantScoped(actor, intent, path, variant)`。
- 兼容：现有 `run-p0b` / `run-p1` 直接写盘不经矩阵，需改为显式传 variant 后走校验（否则规则只在新路径生效，等于没做）。
- 测试：`tests/studio/paths/registry.test.ts` 增 4 条（跨变体拒绝、同变体放行、基座拒绝、通配拒绝）

### W0-3 审查状态契约（与 `diff_status` 解耦）

- 文件：`studio/contracts/review.ts`（新增）
- 内容：
  - `reviewStatusValues = ["unreviewed", "chapter_reviewed", "document_reviewed"]`
  - `ReviewRecord`：`target`（document / section / segment）、`status`、`reviewer`、`at`、`note`、`document_version`
  - `reviewStatus` 作为 **Segment 可选字段**（K0 补丁），默认 `unreviewed`
- 明确写入契约注释：`diff_status` 只表示差异识别与机器检查结论，**不表示人工已审查**。
- 测试：`tests/studio/contracts/review.test.ts`（≥ 6 条）

### W0-4 文档版本与基座绑定字段

- 文件：`studio/contracts/document.ts`
- 内容（全部可选，向后兼容）：
  - `base_binding?: { ruleset_version, content_hash, document_version }`
  - `generation?: { model, prompt_version, locked_at, input_hash }`
- 测试：既有 document 测试加「无该字段仍合法」用例

### W0-5 输入版本锁定

- 文件：`studio/pipeline/lock.ts`（新增）
- 内容：`buildInputLock(...)` 汇总 ruleset 版本 + `content_hash` + config Hash + unresolved 版本 + outline 版本 + model/prompt 版本 → `input_hash`；`assertLockUnchanged(lock, current)`。
- 产出：`documents/<variant>/generation.lock.json`
- 测试：`tests/studio/pipeline/lock.test.ts`（≥ 6 条，含「生成中途输入变更即失败」）

**W0 验收**：`npm test` 全绿且新增 ≥ 24 条；`edit-scope` 与 `registry` 的越权用例必须失败（拒绝写入），不是警告。

## W1 杭州基座 AI 生成（关键里程碑）

**目标**：让杭州全文从「槽位展开」变成「按玩法流程组织的连贯文档」，且机器可判定它是否连贯。

> 判断标准（避免自我感动）：拿现在的 `documents/hangzhou/需求全文.md` 与 W1 产物对比，若读者仍需按规则卡逐条对照才能理解流程，则 W1 失败。

### W1-1 生成 provider 抽象

- 文件：`studio/generate/provider.ts`（新增）
- 内容：
  - `Generator` 接口：`name`、`version`、`generate(request) → { text, citations }`
  - 两种实现：`DeterministicGenerator`（复用现有槽位展开，**保留为降级路径**）、`LlmGenerator`（HTTP 调用，供应商无关，配置从环境变量读）
  - 失败策略：LLM 失败 → 重试 1 次 → 降级 `DeterministicGenerator` 并在产物标记 `degraded: true`
- 边界：provider **不得直接写盘**，只返回文本；装配由 W1-3 负责。
- 测试：fake provider 单测（≥ 6 条）

### W1-2 章节规划

- 文件：`studio/pipeline/plan.ts`（新增）
- 内容：
  - 输入：有效规则集 + 现有 `document-outline.yaml`
  - 输出：每章 `plan`（目标读者、要覆盖的规则、必须出现的边界、跨章引用）
  - AI 只提**建议**，落地仍写 `document-outline.yaml` 并走权限矩阵
- 降级：无 AI 时用 `outline-hangzhou.ts` 的关键词映射（现状）
- 测试：`tests/studio/pipeline/plan.test.ts`（≥ 5 条）

### W1-3 章节内容生成与装配

- 文件：`studio/pipeline/generate-ai.ts`（新增），改造 `generate.ts` 为装配器
- 内容：
  - 逐章调用 provider，产出候选文本 + citation
  - 装配为 Segment：`rule_refs` / `config_refs` / `source_evidence_refs` 必须来自 citation，**不接受 provider 自报**
  - 数值片段仍由 `calculators/` 注入（`editable=false`），provider 不得产出数值
- 测试：`tests/studio/pipeline/generate-ai.test.ts`（≥ 8 条，含「provider 编造规则 ID 被丢弃」）

### W1-4 连贯性检查（机器可判）

- 文件：`studio/pipeline/coherence.ts`（新增）
- 检查项：
  1. 空壳段落 = 0（`text` 不含「·」且长度 < 12 的段落一律报警）
  2. 每章必须交代：触发条件、处理过程、结果（按规则卡槽位是否存在判断）
  3. 跨章引用必须指向存在章节
  4. 同一规则的事实描述不得与规则卡冲突（关键词级：数值、条件名）
  5. 章节顺序符合流程（开局在行牌前、行棋在结算前）
- 测试：`tests/studio/pipeline/coherence.test.ts`（≥ 8 条，每条对应一类坏文档构造）

### W1-5 质量总门禁

- 文件：`studio/pipeline/quality.ts`（新增）
- 汇总：覆盖（现有）+ 连贯性（W1-4）+ 来源完整（每段至少 1 个 evidence）+ 数值（Gold Set 可选）+ 未决项未裁决
- 输出：机器可读报告 `quality-report.json`，`ok=false` 时禁止产出最终文档
- 测试：≥ 6 条

### W1-6 入口与对比

- 文件：`studio/pipeline/run-w1.ts`（新增）
- 产出：`documents/hangzhou/{document.json, 需求全文.md, generation.lock.json, quality-report.json}`
- 附：`studio/pipeline/compare-docs.ts` 输出「槽位展开版 vs AI 版」差异摘要（段数、平均段长、空壳数、章节覆盖）
- 测试：端到端 1 条

**W1 验收（阻断式）**

| 项 | 门槛 |
| --- | --- |
| 空壳段落 | 0 |
| 每章三要素（触发/过程/结果） | 缺失为 0，或缺失项全部有「不适用」声明 |
| 覆盖 | 61/61 规则、25/25 配置 |
| 连贯性检查 | 全通过 |
| 降级标记 | 若走 deterministic，产物必须显式 `degraded: true`，且不算通过 W1 |
| 人工判断 | 用户独立阅读全文后确认「按流程能读懂」 |

## W2 萧山变体完整文档

**目标**：完整变体文档 + 差异可定位 + 三类检查 + 三视图。

### W2-1 基座绑定

- `document.json` 写 `base_binding`（W0-4 字段）：基座 `ruleset_version` + `content_hash` + `document_version`
- 基座文档缺失时拒绝生成（不允许无基座绑定）
- 测试：≥ 3 条

### W2-2 差异检查 R1 / R2 / R3

- 文件：`studio/pipeline/diff-checks.ts`（新增，纯函数，不依赖 AI）
- R1 槽位差集：基座卡槽位集合 − 变体卡槽位集合；非空报警，除非变体卡显式声明不适用
- R2 疑似重复：`added` 卡与基座卡的名称 / 正文相似度（字符 3-gram Jaccard）；阈值先松（名称 0.85 / 正文 0.6），报警附最相近卡 ID
- R3 归类自洽：
  - `inherited` 必有 `base_rule_ref`，且正文不得自写改写内容
  - `modified` 必有 `base_rule_ref` 且 `compares_to` 非空，正文不得与基座完全一致
  - `added` 不得有 `base_rule_ref` / `compares_to`
- 顺带修 `compiler/validator.ts` 空转三元（`change_type === "inherited" ? baseIds : baseIds`）
- 输出：`diff-warnings.json` + `diff_status` 由检查器决定（默认 `confirmed`，告警才 `candidate` + `review_reason`）
- 测试：`tests/studio/pipeline/diff-checks.test.ts`（≥ 12 条，三类各含正例反例）

### W2-3 三视图渲染

- 文件：`studio/pipeline/render.ts` 扩展
- 产出三份：`需求全文.md`（完整）、`差异视图.md`（只列 modified/added/alert）、`对照视图.md`（基座 vs 变体并排）
- 测试：≥ 5 条

### W2-4 继承内容一致性断言（强校验）

- 断言：`default_inherited` / `explicit_inherited` 片段的 `text` 必须与基座文档对应片段**逐字一致**；不一致即失败
- 目的：从生成侧保证「继承内容不可漂移」，而不是只靠 UI 锁
- 测试：≥ 3 条（含人为篡改必失败）

**W2 验收**：萧山 86 卡全覆盖；`inherited` 逐字一致断言通过；R1/R2/R3 告警清单可读（每条有原因与建议）；三视图产出。

## W3 本地 Web 阅读与编辑

**目标**：策划可用。**只读先上线**，编辑随后。

### W3-1 服务端

- 目录：`server/`
- 技术：Node 内置 `http` + 现有 TS，监听 `127.0.0.1`，无鉴权（单人本地），拒绝非本机请求
- API（只读先行）：
  - `GET /api/doc/:variant` → document.json
  - `GET /api/doc/:variant/outline`
  - `GET /api/doc/:variant/diff`
  - `GET /api/segment/:id/sources`
  - `GET /api/checks/:variant` → quality-report.json + diff-warnings.json
- 安全：所有路径经 `registry` 推导；不接受客户端传路径
- 测试：`tests/server/api.test.ts`（≥ 8 条，含路径注入用例）

### W3-2 前端

- 目录：`web/`（Vite + React + TS）
- 三栏：导航 / 文档 / 信息面板
- 只读阶段功能：章节折叠、搜索、差异高亮、来源侧栏、检查告警、锁定标记
- 测试：组件测试（≥ 10 条，重点：只读区域不可编辑、差异高亮正确）

### W3-3 统一变更层

- 文件：`studio/edit/mutation.ts`（新增）
- 内容：三种编辑入口都产出同一 `Mutation` 结构：
  ```
  { target_kind: "segment" | "section" | "document",
    op: "replace-text" | "append" | "move-block" | "edit-outline",
    payload, base_revision, source: "richtext" | "markdown" | "ai-dialog" }
  ```
- `Mutation` → `Proposal` → Diff → Apply（复用 `transaction/apply.ts`）
- 强制：`Mutation` 必须过 `edit-scope.canEdit`，否则拒绝（服务端校验，不依赖前端）
- 测试：≥ 8 条（越权 mutation 必须被拒）

### W3-4 编辑器接入（顺序待 D-02 决策）

- Markdown 编辑（`README` 中最快落地，先做）
- 富文本编辑（段落级，基于同一 Mutation）
- AI 对话编辑（复用 `edit/router.ts` + provider）

**W3 验收**：AC-02 / AC-05 / AC-07 通过；越权写入在 API 层被拒绝（有测试）；策划能读完萧山全文并定位来源。

## W5 基座升级与增量重生成

### W5-1 影响分析

- 文件：`studio/pipeline/impact.ts`
- 输入：旧基座文档 + 新基座文档
- 输出：受影响规则 → 受影响 Block/Segment/章节清单
- 测试：≥ 6 条

### W5-2 三方合并

- 文件：`studio/pipeline/merge3.ts`
- 三方：`base_old`（上次生成）、`current`（含人工修改）、`base_new`
- 规则：
  - 仅生成变化 → 采用新生成
  - 仅人工变化 → 保留人工
  - 两者都变 → `conflict`，进冲突报告，**禁止自动取一边**
- 合并粒度：先 Segment 文本级；`editorial-overrides.yaml` 优先于生成结果
- 测试：≥ 10 条（三类情形各含边界：仅删除、仅新增、文本重叠）

### W5-3 冲突报告与人工解决

- `conflicts.json` + Web 视图（取左 / 取右 / 手改）
- 测试：≥ 5 条

### W5-4 多变体扩展验证

- 用假变体（fixture，不建真实规则）验证隔离与影响分析不串
- 测试：≥ 5 条

# 五、测试与门禁策略

## 5.1 分层

| 层 | 要求 |
| --- | --- |
| 契约 | 每个新字段必带「旧产物仍合法」用例 |
| 纯函数 | 阈值、相似度、三方合并必须可达边界用例，不允许只测 happy path |
| 权限 | 每条拒绝路径一个用例（越权、跨变体、基座写入） |
| 端到端 | 每阶段 1~2 条，产物写临时目录并清理 |

## 5.2 阶段门禁

每阶段必须同时通过：

```text
npm test
npm run typecheck
node compiler/validator.ts
node compiler/validator.ts rulebook/specs/variants/xiaoshan --kind variant
node compiler/compile.ts && git diff --exit-code rulebook/compiled/
node studio/pipeline/run-w1.ts --check           # W1 起
node studio/pipeline/run-p1.ts --check           # W2 起（含 R1/R2/R3 与继承一致性）
```

`quality-report.json` 或 `diff-warnings.json` 为 `ok=false` 时，**禁止**标记阶段完成。

## 5.3 反自欺条款

1. 不允许用「门禁通过」替代「内容可读」。W1/W2 完成必须有人工阅读结论。
2. 不允许 AI 生成结果直接进 `documents/` 而不经过 provider 降级标记与 quality 门禁。
3. 不允许为了过检查而放宽阈值——阈值变更必须单独提交并注明原因与样本。
4. 不允许把 `diff_status` 当作人工审查结论（D-04）。

# 七、风险与停止条件

| 风险 | 应对 | 停止条件 |
| --- | --- | --- |
| AI 生成内容「读起来通顺但改了事实」 | provider 不得自报引用；事实必须由 citation 反查；数值由计算器注入 | 出现无 citation 的事实性断言 |
| 连贯性检查退化为「能过就行」 | 每条检查必须有反例测试 | 检查项无法构造反例 |
| 先做编辑器、结构不对 | 严格 W1→W2→W3 顺序 | 在 W1 人工确认前启动 W3 |
| 权限靠前端拦 | 服务端必须校验 `canEdit` | 任一越权写作靠 UI 隐藏实现 |
| 三方合并悄悄丢人工修改 | 冲突必须显式报告，禁止自动取一边 | 合并后人工修改被静默覆盖 |
| 检查阈值被调松以过关 | 阈值变更单独提交 + 样本说明 | 同一次提交里既改代码又放宽阈值 |
| 变体数量增长后检查爆炸 | 检查按变体增量执行，不做全量重跑 | 单变体生成超过 10 分钟 |
