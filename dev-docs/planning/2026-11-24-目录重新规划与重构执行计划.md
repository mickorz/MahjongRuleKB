## 一、问题与目标

### 1.1 现状问题

当前根目录把四类生命周期完全不同的产物平铺在一起，看不出「原始证据 / 正式规范 / 待审批变更 / 编译产物」的分层：

| 目录 | 实际职责 | 产物性质 |
| --- | --- | --- |
| `sources/` | 规则方原始 PRD 与规则文档 | 原始证据（只读） |
| `rulesets/` | 杭州基础规则卡与配置 | 正式规范 |
| `variants/` | 萧山等地方玩法差异 | 派生规范 |
| `compiled/` | 合并后的完整规则集 | 编译产物（禁手改） |

另散落 `tests/gold-set/`、`calculators/`、`schemas/`、`dev-examples/` 等，缺少统一的资产边界。

### 1.2 目标

用 `rulebook/` 收纳四层规则资产，并按生命周期分层：

```text
原始证据（只读） → 待审批变更 → 正式规范（事实源） → 编译产物（生成物）
```

### 1.3 非目标

- 不重写 Compiler 逻辑、不改规则 Schema 语义、不改规则 ID。
- 不重命名 `compiled/` 为 `dist/`（`.gitignore` 已忽略 `dist/`，而 `compiled/` 是入库交付产物）。
- 不在本次迁移中调整规则内容或裁决未决项。
- 不引入 OpenSpec CLI。

### 2.1 三个必须在这里定死的决策

#### 决策 1：Change 存储只有一处活动区，归档区入库

| 数据 | 位置 | 是否入库 |
| --- | --- | --- |
| 活动 Change（`change.json` + artifacts） | `<kb>/.rule-studio/changes/active/<id>/` | 否（运行时，加入 `.gitignore`） |
| Proposal（规则 / 文档） | `<kb>/.rule-studio/proposals/` | 否 |
| Transaction | `<kb>/.rule-studio/transactions/` | 否 |
| Stage 中间产物 | `<kb>/.rule-studio/workflow/<taskId>/` | 否 |
| **已归档 Change（全量包）** | `rulebook/changes/archive/<date>-<id>/` | **是**，审计留痕 |
| 规则 / 配置事实 | `rulebook/specs/` | 是 |

规则：

1. **不建 `rulebook/changes/active/`**。活动变更只存在于 `.rule-studio/`，避免两套活动变更生命周期。
2. Archive 是**单向导出**：Verify 通过后把完整包复制到 `rulebook/changes/archive/`，并提交入库；运行时目录可清理。
3. Archive 不得回写规则、配置或文档事实（与既有 `Archive 不修改事实` 一致）。
4. 若将来需要在 PR 里评审变更说明，从 `.rule-studio/changes/active/<id>/` 导出评审包（`proposal.md` / `design.md` / `tasks.md`）到 PR 描述或 `rulebook/changes/archive/`，**不新建第三处活动存储**。

> 说明：这一步替换了原提案里的 `rulebook/changes/<change-id>/`（活动区）。原因是它和 `2026-11-24-需求全文生成执行计划` 已冻结的 `.rule-studio/changes/active/` 重复。

#### 决策 2：`variants/` 是正式规范，不是 Change

萧山是长期存在的正式地方玩法（差异化派生规范），归属 `rulebook/specs/variants/`；`changes/` 只放一次性、未合并的修改。两者生命周期不同，不得混放。

#### 决策 3：类型判定改为显式 `kind`，不再看路径前缀

现状（迁移后必须改）：

- `compiler/validator.ts:106` `const isVariant = rs.dir.startsWith("variants")`
- `compiler/validator.ts:180` `if (dir.startsWith("variants"))`

迁移后改为显式传参：

```text
loadRuleset({ dir, kind: "base" | "variant" })
validateRuleset(rs, base?, { baseIdPrefix, variantIdPrefix })
cli: node compiler/validator.ts rulebook/specs/base/hangzhou --kind base
```

不允许再用 `startsWith("variants")` 或 `startsWith("rulesets")` 判类型。

## 六、风险与回滚

| 风险 | 应对 |
| --- | --- |
| 108 张卡 provenance 批量替换出错 | 只替换 2 个唯一字符串；改完 `grep` 计数校验 + 编译 + 测试三重验证 |
| `content_hash` 与版本不同步 | P1-C 单独立项，提交前用脚本重算并与 manifest 比对 |
| 历史文档被误改（含旧路径的评审原文） | 只改现行文档；历史评审原文保留旧路径并加注 |
| 目录移动导致 git 历史断裂 | 全程 `git mv`，不用「复制+删除」 |
| 迁移与 Change Manager 交叉污染 | P1 禁止创建任何 `changes/` 活动目录；P2 才接入归档 |
| Agent 依据旧 `AGENTS.md` 走错路径 | P1-B 内同步改 `AGENTS.md`，与迁移同一次提交 |

回滚：每个阶段独立提交；P1-B 回滚 = `git revert` 单次提交；P1-C 回滚需同时回滚版本与 `content_hash`（脚本化）。

## 八、执行顺序建议

```text
P1-A 类型判定解耦（代码）
  ↓
P1-B 规则与产物目录迁移（不含 sources）
  ↓
P1-C sources 迁移 + 版本/hash 升级（独立提交）
  ↓
P2 Change 归档目录接入（依赖 Change Manager）
  ↓
P3 路径常量集中化
```

**不要跳过 P1-A 直接移动目录**：现状代码靠路径前缀判断规则集类型，先移目录会同时破坏校验和编译。

**不要合并 P1-B 与 P1-C**：前者不动规则内容，后者必然改 `content_hash` 与版本，混在一起会无法判断回归失败来自哪一步。
